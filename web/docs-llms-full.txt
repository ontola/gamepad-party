# Splitscreen Club developer docs

> Splitscreen Club puts local multiplayer games in one room: players pick a game, keep their controller and profile, and go back to the room with Back. These docs show how to connect a game made in any engine and share it through the platform. Start with Share your game.

# Bring your game to the couch

Splitscreen Club puts local multiplayer games in one room. Players pick a game, keep their controller and profile, and return to the room with Back. Your game keeps its engine and runs in its own process.

**To share a game, follow [Share your game](https://splitscreen.club/docs/share).** It is the whole path in six steps, from connecting your engine to the store, with a command and a "done when" for each step. The rest of these docs is reference for one of those steps.

## Pick your engine

Starting a new game? The [Game playbook](https://splitscreen.club/docs/playbook) gets you from an idea to the store with a Godot template, headless tests and one-command publishing.

| Engine | Starting point | What is included |
| --- | --- | --- |
| [Warp / Luau](https://splitscreen.club/docs/warp) | The `warp` runtime, our own open-source engine | Lifecycle, seats, controllers, window, names and colours built in; Luau scripts with hot reload, no compiling |
| [LÖVE / Lua](https://splitscreen.club/docs/love) | Shared party runner | Lifecycle, controller mapping, window handling and faces |
| [Bevy](https://splitscreen.club/docs/bevy) | Bevy plugin and demo game | Lifecycle, controllers per seat, window and audio handling, settings, faces and phone screens |
| [Rust](https://splitscreen.club/docs/rust) | Rust SDK | Typed protocol events; your engine handles input consumption and rendering |
| [Godot 4](https://splitscreen.club/docs/godot) | Godot addon | Lifecycle, controllers per seat, window handling, settings, faces and phone screens |
| [C / C++](https://splitscreen.club/docs/c) | Single-header adapter | TCP transport and lifecycle; no controller stream or face decoder yet |
| [Unity](https://splitscreen.club/docs/unity) | Unity package and the Orb Rush demo | Lifecycle, controllers per seat, window handling, settings, faces, phone screens and saves; new, not yet tested on hardware |
| [Unreal Engine 5](https://splitscreen.club/docs/unreal) | Unreal plugin and the Dash Derby demo | Lifecycle, controllers per seat, window handling, world pause, settings, faces, phone screens and saves; new, not yet built in CI |
| [Other engines](https://splitscreen.club/docs/other-engines) | Wire protocol | Implement the connection and engine adapter yourself |

These are implementation starting points, not certifications. [Engine support](https://splitscreen.club/docs/engines) compares every engine feature by feature and lists the open work.

## What a good integration does

Prepare a playable frame while hidden and silent. Show it when the host says Start. Pause simulation and audio when players return to the lobby, then resume the same state. Keep processing host messages throughout.

Controllers follow player seats. Faces, names and colours follow player IDs. Your game owns the rounds and score screens; finishing a round does not end the Splitscreen Club session.

Read [Game lifecycle](https://splitscreen.club/docs/lifecycle), then [Controllers & players](https://splitscreen.club/docs/controllers). Add [faces and colours](https://splitscreen.club/docs/faces) once play is reliable.

## Have a game already?

[Add your game in the developer portal](https://splitscreen.club/developers). Sign in with your email; a title, a short pitch and a player count are enough to start. We can help with integration, or you can follow [Share your game](https://splitscreen.club/docs/share) yourself.

## For AI agents

Read [Share your game](https://splitscreen.club/docs/share) first. [llms.txt](https://splitscreen.club/docs/llms.txt) lists every page and [llms-full.txt](https://splitscreen.club/docs/llms-full.txt) has all of them as Markdown in one file.

## How these docs stay current

These pages are built from Markdown in the public repository. Code excerpts are read from source, not pasted copies. CI checks generated pages, internal links and watched implementation files. The Rust example compiles against the SDK; the C example compiles against the header. The Bevy demo is built with Bevy and passes the conformance harness in CI. The Unity demo's rules play against a fake host without Unity, and its Unity code compiles against Unity's reference assemblies. The Unreal plugin's protocol core passes its unit tests and the conformance harness in CI; its Unreal code is not compiled there yet.

An implementation change makes the docs check fail until someone reviews and regenerates the affected pages. This catches drift; it cannot prove every explanation is correct. Godot snippets are source-checked, not runtime-certified. Physical controller and window tests still matter.

# Share your game

This page is the whole path from a local multiplayer game on your machine to a
game that groups can play in Splitscreen Club. Follow the steps in order. Each
step ends with **Done when**: do not move on before that is true. The other
pages are reference for one step; this page links to them where you need them.

People and AI agents can follow it the same way. Every step runs from the
command line. An agent can read all docs at once in
[llms-full.txt](https://splitscreen.club/docs/llms-full.txt).

## What you need

- A game for 1 to 8 players on one screen, played with controllers.
- A Windows build of it. Hosts run on Windows today; you can add `mac` and
  `linux` builds next to it.
- An email address, for the [developer portal](https://splitscreen.club/developers).

You do not need Splitscreen Club support in your game to start. You can send a
game first and add support later, or ask us to help (step 1).

## 1. Tell us about the game

Sign in to the [developer portal](https://splitscreen.club/developers) with your email and choose
**Add your game**. A title, a one-line pitch and a player count are enough.

From here you have two equal options:

- **Do it yourself** (or with your AI tools): continue with step 2.
- **Let us help**: ask in the game's **Help** tab. We agree on repository
  access and AI use first, prepare the changes in a pull request, and you
  review and merge it. Your repository can stay private.

**Done when** the game is in the portal with its id, such as `my-game`. Use
that id everywhere below.

## 2. Connect your engine

Splitscreen Club starts your game as a separate program and talks to it over
a local connection: it tells the game who plays on which seat, sends each
seat's controller, and says when to prepare, start, pause, resume and stop.
Your engine's SDK does that work. Pick your engine:

| Engine | Guide | You add |
| --- | --- | --- |
| Warp (Luau) | [Warp / Luau](https://splitscreen.club/docs/warp) | nothing: the `warp` runtime does it. The quickest start for a new game |
| Godot 4 | [Godot](https://splitscreen.club/docs/godot), or start from the [template](https://splitscreen.club/docs/playbook) | the `sdk/godot` addon |
| Unity | [Unity](https://splitscreen.club/docs/unity) | the `sdk/unity` package |
| Unreal Engine 5 | [Unreal](https://splitscreen.club/docs/unreal) | the `sdk/unreal/GameNight` plugin |
| Bevy | [Bevy](https://splitscreen.club/docs/bevy) | the `gamenight-bevy` crate |
| LÖVE / Lua | [LÖVE](https://splitscreen.club/docs/love) | your game as a module of the shared runner |
| Rust, no engine | [Rust](https://splitscreen.club/docs/rust) | the `gamenight-sdk` crate |
| C / C++ | [C / C++](https://splitscreen.club/docs/c) | the `sdk/c/gamenight.h` header |
| Anything else | [Other engines](https://splitscreen.club/docs/other-engines) | your own adapter for the [protocol](https://splitscreen.club/docs/protocol) |

[Engine support](https://splitscreen.club/docs/engines) says per engine what the SDK does and what
you still write yourself.

Whatever the engine, the game must do five things. They are what players notice:

1. **Start in the game.** No title screen or player setup: the room already
   picked the game and the players.
2. **Read each seat's own controller** from the SDK, never a joystick
   index. See [Controllers & players](https://splitscreen.club/docs/controllers).
3. **Prepare hidden, show on Start.** Load while hidden and silent, report
   ready, take the screen when the host says Start. See
   [Game lifecycle](https://splitscreen.club/docs/lifecycle).
4. **Pause and resume the same state.** Back (Select) takes everyone to
   the room; your game freezes, also its audio and timers, until it is
   resumed. Never use Back for anything else. Start opens your own menu.
5. **Keep playing rounds.** Show a result briefly and start the next round.
   Players leave with Back, not through a game over screen.

Add players' [faces and colours](https://splitscreen.club/docs/faces) and [settings](https://splitscreen.club/docs/settings)
once this works.

**Done when** your game starts inside Splitscreen Club, every seat moves its
own player, and Back and Resume work.

## 3. Test it

Run the certifier against your built game. It plays the host: it seats
players, sends controller input and runs the whole lifecycle several times.

```sh
git clone https://github.com/ontola/gamepad-party
cd gamepad-party
cargo run --release -p gamenight-certify -- my-game --players 2 --report report.json -- path/to/MyGame.exe
```

Everything after `--` is the command that starts your game. Then play it once
with real controllers: two people, unplug a pad, press Back and Resume a few
times, switch to another game and back. The certifier cannot see your screen
or your pads. More checks: [Test your integration](https://splitscreen.club/docs/testing).

**Recommended layout check.** Choose a design aspect ratio that suits the game,
such as 16:9 or 4:3. When the browser window changes shape, adjust the camera
and HUD to fit. Keep the whole shared arena in view at its original proportions,
using extra space for scenery or margins.

During a round, resize the window from 4:3 to ultrawide (21:9). Try rotating a
phone too if your game supports portrait. Move players to opposite edges and
open the pause menu. Can everyone see their character, read the score and reach
the menu controls?

**Done when** the certifier reports no failures and the real-controller round
went right.

## 4. Upload a preview build

A preview is private: only you and your testers see it. In the portal, open
your game, then **API keys**, and create a key. Store it as
`GAMENIGHT_API_TOKEN` (in your shell, or as a CI secret). Then upload a ZIP of
the exported game:

```sh
curl -O https://splitscreen.club/developers/gamenight-publish.py
python3 gamenight-publish.py push --game my-game --platform windows --file dist/my-game-windows.zip --entrypoint MyGame.exe --version 0.1.0
```

`--entrypoint` is the executable's path inside the ZIP. Every upload needs a
new `--version`. To upload from GitHub Actions on every push instead, see
[Connect GitHub Actions](https://splitscreen.club/docs/publishing#connect-github-actions).

**Done when** the portal's **Builds** tab shows the build as ready.

## 5. Fill the store page

Put two things in your repository:

- `gamenight.json`, the facts about the game:

  ```json
  {
    "$schema": "https://raw.githubusercontent.com/ontola/gamepad-party/main/catalog/schema.json",
    "id": "my-game",
    "title": "My Game",
    "tagline": "One line that says why it is fun with friends.",
    "developer": "Your name",
    "players": { "min": 1, "max": 4 },
    "match_minutes": 5,
    "price": "free",
    "tags": ["party", "co-op"],
    "integration": { "level": "integrated", "protocol": 1 }
  }
  ```

- `assets/gamenight/` with `cover.png` (portrait 360x480), `icon.png`
  (128x128) and `gameplay.png` (16:9).
- `preview.json`, the recipe for five seconds of real gameplay. `python3
  gamenight-publish.py clip --publish` renders and uploads it (see the
  [store clip guide](https://splitscreen.club/docs/store-clip#keep-the-recipe-not-the-video)).

Then, in that folder:

```sh
python3 gamenight-publish.py store
```

Edit these files and run `store` again to change the page. Do not copy the
text or media anywhere else.

**Done when** the portal's **Store page** tab shows your title, clip and art.

## 6. Playtest, review, publish

1. **Playtest.** In the **Playtest** tab, create an invite link and send it
   to friends. When you or a tester joins a Splitscreen Club table with a
   phone, the table gets your preview. Afterwards every phone asks how it went;
   the answers appear in the tab.
2. **Send for review.** In the **Review** tab. We play the exact build and
   check that you may distribute it.
3. **Publish.** Once approved, choose **Publish to players**. Every host
   picks it up from the catalog; nothing needs to change in any Splitscreen
   Club repository.

Later versions: upload a new build (step 4) and publish it. Rolling back is
choosing an older build. Details, the API and pricing:
[Publish a game](https://splitscreen.club/docs/publishing).

**Done when** your game is on the shelf in Splitscreen Club rooms.

## For AI agents

- Read this page first, then only the guide for your engine from step 2.
  [llms-full.txt](https://splitscreen.club/docs/llms-full.txt) has every page as Markdown in one file;
  [llms.txt](https://splitscreen.club/docs/llms.txt) lists them.
- Work through the steps in order and check each **Done when** yourself,
  with commands and screenshots, before you report a step as finished.
- Where [Engine support](https://splitscreen.club/docs/engines) says "You" or "No", write that part
  against the [protocol](https://splitscreen.club/docs/protocol). Do not invent SDK functions.
- Never put the `GAMENIGHT_API_TOKEN` in the repository, a log or a pull
  request. Publishing to players (step 6) is for the game's owner to approve.

# Game playbook

How to go from an idea to a game in the Splitscreen Club store quickly. It is written
for AI coding agents as much as for people: every step can run headless, from
the command line, without someone watching the screen.

## Start from the template

```sh
git clone https://github.com/ontola/gamepad-party
python3 gamepad-party/scripts/new-godot-game.py my-game my-game "My Game"
cd my-game && git init && git add -A && git commit -m "Start My Game"
```

You get a small, working Godot 4 couch game with:

| Part | What it does |
| --- | --- |
| `main.gd` | the game: Splitscreen Club lifecycle, seats, faces, settings and a Start menu, bots, dev flags |
| `gamenight.json` | the game's metadata: title, tagline, developer, players, tags; the only place you edit them |
| `tests/lifecycle.py` | a fake Splitscreen Club host drives prepare, start, controller input, pause, resume, dispose |
| `tools/capture_preview.sh`, `tools/encode_preview.py` | the five-second store clip, frame by frame |
| `.github/workflows/ci.yml` | tests, Windows export, release, store page |
| `AGENTS.md` | the commands and rules for whoever works on it next |

The Splitscreen Club addon is installed from the SDK. CI fails when your copy falls
behind; run `python3 gamepad-party/sdk/godot/sync.py my-game` to update it.
Keep one repository per game.

Replace the orb game with yours one step at a time, and keep the tests green
after every step. Other engines work too (see [Engine support](https://splitscreen.club/docs/engines)).
For Unity, copy the Orb Rush project in `examples/unity-demo` instead; the
[Unity guide](https://splitscreen.club/docs/unity) walks through it and its headless test.

## The loop

Run all three after every change:

```sh
godot --headless --import                                         # parse errors
godot --headless --fixed-fps 60 --path . -- --sim 4000 --seed 1   # bots play a round
python3 tests/lifecycle.py --godot godot                          # fake Splitscreen Club host
```

- **Import first.** A GDScript parse error makes later headless runs hang
  instead of failing. Look for `SCRIPT ERROR` or `Parse Error`.
- **Bots play the real game.** The sim counts what happened (dashes, pickups,
  rounds) and fails when something never did. Add a counter for every mechanic
  you build, so a broken mechanic fails CI.
- **The fake host checks what players notice.** Extend `tests/lifecycle.py`
  for each control: send controller frames, wait for the trace line.

Put rules that need many cases (damage tables, combinations) in plain
scripts and test them with `godot --headless --script`.

## Make it deterministic from day one

Seed the global RNG once from `--seed` and move the simulation only in
`_physics_process`. With `--fixed-fps`, the same seed then replays the same
run: the template's sim prints a state hash, and its store clip comes out
bit for bit the same. A second unseeded `RandomNumberGenerator`, or gameplay
that reads the clock, breaks this quietly. Retrofitting it into a big game is
much harder than starting with it.

## See the game without a person

Build flags for everything you would otherwise set up by hand:

- `--shot out.png --frames 90`: bots play and frame 90 is saved. Render
  under `xvfb-run` for a real GPU path.
- `--players N`, `--seed N`, and as the game grows: where to start (a level,
  metres along a path), what to spawn round the players, a closer camera.
- `GAME_TRACE=1` prints what happens, for tests and for debugging.

Look at the screenshots yourself after visual changes. Text over characters
and HUD clutter read badly on a TV; let shapes and colour carry the state.

## Make 3D models

Image-to-3D tools (Tripo, Meshy, Hunyuan3D, Hyper3D) give a quick first shape
but rarely exactly what you want, and an agent driving Blender tends to lose
detail. What works better for hard-surface models (props, vehicles, buildings):

1. Generate a rough model from a concept image with one of those tools.
2. Import it into the Godot project as a reference only.
3. Have the agent build a new model next to it in Godot itself, from CSG
   shapes or a `SurfaceTool`/`ArrayMesh` in code, adding the details and
   proportions you need. No Blender, no plugin or MCP is required.
4. Render it with `--shot` from a few angles, compare it with the reference
   and iterate. A second agent that only reviews the screenshots catches more
   than the builder checking its own work.

Bake CSG into a plain mesh (`CSGShape3D.bake_static_mesh()`) before it ships:
CSG is slow at runtime. Code-built meshes need no baking and stay easy to
change; most of our games already build their models this way. Rigged
characters (bones, weight painting) still need a real modelling tool.

From an [r/aigamedev workflow post](https://www.reddit.com/r/aigamedev/comments/1xa3gju/new_crazy_workflow_for_making_3d_assets/), October 2026.

## Design for the couch

Players sit on a sofa, a few metres from the TV, holding controllers, and
switch games often. The template does all of this; keep it as you build.

- **Start playing at once.** No title screen, no setup screen before the
  first round. The lobby already picked the game and the players.
- **Settings live in the Start menu, and in Splitscreen Club.** Declare every
  option with `GameNight.declare_settings` and apply `setting_changed`, so
  players can change them from the Splitscreen Club app, the lobby, or by asking
  an LLM. Show the same settings in a small menu on Start. Apply a change
  from the next round when changing it mid-round would be unfair. The menu
  sends its changes with `GameNight.set_setting`, so the app shows them too.
- **The Start menu follows one layout.** The game's name heads it every time
  Start opens it, also mid-game, so everyone in the room learns what they are
  playing. Then Resume, then New round (apply options), then the settings.
  No button hints in the menu (choose, change, select, resume): a highlighted
  row and ‹ › around its value speak for themselves.
- **The Start menu shows the controls.** Draw the button mapping beside the
  menu, or add a Controls row that opens it. This is the one place a player
  who joined mid-game, or never played before, can look up what each button
  does. During play there are still no control hints.
- **Keyboard support is a plus.** Not every room has a controller for
  everyone, so let one player play on the keyboard when you can, and say so
  with `"keyboard": true` under `players` in `gamenight.json`, so the
  catalog records which games work that way. Keys alone and keyboard plus
  mouse are not the same: add `"mouse": true` only when the mouse is part of
  play (aiming, looking around). A keyboard player in a game with neither is
  told the game is made for controllers. If two players can share one
  keyboard (one on WASD, one on the arrows, a few buttons each), add
  `"shared_keyboard": 2`: a second player joins the keyboard with G.
- **Leave Back alone.** Back (Select) returns to the party; Splitscreen Club handles
  it and pauses your game. Never bind it to anything in the game.
- **Use the players' colours, names and faces.** Each player picks them once
  in Splitscreen Club. Colour the player's character, draw their face on it with the
  SDK's `face.gd`, and name them where it matters, such as the results screen.
- **Don't flood the screen.** No text over characters, no labels on every
  thing. A clock, a score per player and clear shapes and colours read from the
  sofa; menus and explanations do not. No control hints during play either:
  players figure out A and B in seconds.
- **Rounds keep going.** Show the result briefly, call `notify_finished`,
  then start the next round. Players leave with Back, not with a game over
  screen. Let players keep moving while the result shows.
- **A calm camera.** Everyone shares one screen: keep the camera still or
  slow, keep players leashed together so nobody leaves the frame, and snap
  (don't glide) when someone teleports or respawns.
- **Punish the failure, not the action.** Trying something should never hurt;
  missing it may. Keep the visible causes of failure to a few that everyone
  can read at a glance.
- **Fewer, clearer mechanics.** Cut mechanics that look alike but behave
  differently; simple spatial rules win.
- **Start sparse.** Effects, screen shake and audio beds were toned down in
  every playtest. Add spectacle when a playtest asks for it.
- **Asymmetric games:** private information goes to each player's phone
  (see Phone screens in the [protocol](https://splitscreen.club/docs/protocol)), shared state stays on
  the TV, and the TV shows what the phone players chose.
- **Bots fill empty seats.** The host can seat AI players, so a game works with
  one person. The same bots run your sim and your store clip.
- **Controllers follow seats.** Read `GameNight.frame_for_seat(seat)` when
  Splitscreen Club launched the game, never joystick indices.
- **Prepare quietly.** Load everything in Prepare while hidden, then call
  `notify_ready`. Start shows it; Pause freezes play, timers and audio.

More detail: [Game lifecycle](https://splitscreen.club/docs/lifecycle), [Controllers & players](https://splitscreen.club/docs/controllers),
[Faces & colours](https://splitscreen.club/docs/faces) and [Game settings](https://splitscreen.club/docs/settings).

## The store clip

The store needs a five-second clip of real gameplay. Read the
[gameplay preview guide](https://github.com/ontola/gamepad-party/blob/main/docs/gameplay-previews.md):
quick, varied, readable cuts.

```sh
GODOT=godot tools/capture_preview.sh /tmp/takes
python3 tools/encode_preview.py /tmp/takes assets/gamenight
```

Each take is the real game with bots, rendered with `--write-movie` at a
fixed 30 FPS, so it is slow to record but exact. The cut list in
`encode_preview.py` is the whole edit, and encoding is bit-exact. Write down
the seeds and commit next to the clip, so anyone can make it again.

Add `cover.png` (portrait 360x480), `icon.png` (128x128) and `gameplay.png`
(16:9) to `assets/gamenight/`.

## Release and store page

1. [Register the game](https://splitscreen.club/developers) in the developer portal and create a
   publish key. Save it as the `GAMENIGHT_API_TOKEN` secret of the repository.
   The first stable release needs Splitscreen Club's distribution approval.
2. Run the CI workflow by hand with `release` set to `v0.1.0`. It tests,
   exports Windows, publishes the GitHub release and fills the store page.
3. Or fill the store page from your machine:

```sh
GAMENIGHT_API_TOKEN=gn_pub_... python3 gamenight-publish.py store
```

It reads `gamenight.json` and uploads what is in `assets/gamenight/`. See
[Publish a game](https://splitscreen.club/docs/publishing) for builds, channels and review.

Everything players see lives in Splitscreen Club production, filled from your
repository by these commands. Do not add the game to `ontola/gamepad-party`'s
`catalog/games` or to any store file in another repository: installed hosts
get stable releases from the hosted catalog. Store visibility (listed or
hidden) is a Splitscreen Club staff setting.

## Pitfalls we hit

- Game data copied into other repositories drifts. Bombing Bugs ended up with
  its tagline in three places. Edit `gamenight.json` and `assets/gamenight/`
  only, and let the publish commands carry them to production.
- Headless Godot hangs on a parse error; untyped values from arrays and
  dictionaries are the usual cause. Give them a type (`var c: Vector3 = ...`).
- Agents often cannot push git tags. Release with the workflow input instead.
- Never run a downloaded script with your publish key in CI. Check out a
  pinned copy of `ontola/gamepad-party` and run its `scripts/gamenight-publish.py`.
- The first frames of a `--write-movie` take can show the engine warming up.
  Start cuts at frame 20 or later.
- A big level needs the camera close enough to read on a phone; check the clip
  at phone size.
- Test the exported build, not only the project: files under `tests/` are left
  out of exports, and game code that loads them breaks only there. The
  template's CI runs the lifecycle test against the exported pack.
- On Windows, a test host that reads Godot through `stdout=PIPE` can stall the
  game once the pipe fills. Write the output to a file (the template does), and
  pick a free port instead of a fixed one.
- `secrets: inherit` does not pass secrets to a reusable workflow in another
  organisation. Pass each secret by name.
- Build versions are immutable: give every preview upload a unique version,
  such as one with the CI run id.
- TVs often run at 120 Hz: turn on physics interpolation
  (`physics/common/physics_interpolation`), or motion judders.
- Prewarm shaders and particles during Prepare, before `notify_ready`, so the
  first seconds of play don't stutter.

# Engine support

Which engines Splitscreen Club supports, how far, and where to start. Pick the row for
your engine, then follow its guide. If your engine is not listed as
**Full**, read its open work before you start: you write that part yourself.

## Support levels

- **Full**: an SDK in this repository handles the connection, lifecycle,
  per-seat controllers and the game window. Released games use it and CI runs
  its contract tests.
- **New**: an SDK covers everything Full does, but no released game uses it
  yet. Its open work below says what CI checks and what still needs hardware.
- **Partial**: an SDK handles the connection and lifecycle. You wire controllers,
  windows or faces into your engine yourself.
- **Protocol only**: no SDK. Write an adapter against the [protocol](https://splitscreen.club/docs/protocol).

| Engine | Level | Start with | Games using it |
| --- | --- | --- | --- |
| [Warp / Luau](https://splitscreen.club/docs/warp) | Full | `warp new`, no SDK to add | Neon Siege, Dead Miles, Relay Keepers, Stack Together, Neon Trails |
| [Godot 4](https://splitscreen.club/docs/godot) | Full | [Godot template](https://splitscreen.club/docs/playbook) and `sdk/godot` addon | Spaceracer, Ballkickers, Spellstorm, Hexstead, Downhill Rush, Bombing Bugs, The Builders, Growing Guns, Frog Fighter, The Voice and the Will |
| [LÖVE / Lua](https://splitscreen.club/docs/love) | Full | Shared party runner | Blast Party, Neon Trails, Neon Siege, Volley Trouble, Stack Together, Bubble Buddies |

## Open work

This list doubles as the roadmap for engine support.

- **Unity**: the package and the Orb Rush demo are new. CI runs the SDK core
  and the demo rules against a fake host and `gamenight-certify` with dotnet,
  and compiles the Unity layer against reference assemblies, but no Unity
  build has been tested on hardware yet: window handling, faces on screen and
  pads. Linux has no window hiding. The Input System code path is not compiled
  in CI.
- **Unreal**: the plugin and the Dash Derby demo are new. CI unit tests the
  plugin's C++ protocol core and runs `gamenight-certify` against it headless,
  but has no Unreal build: the module and the demo are not compiled there, and
  window handling, audio, the world pause, faces on screen and pads are not
  tested on hardware yet.
- **C / C++**: the header has no controller tokens, controller frames, colours
  or faces, and no phone screens. Games still have to parse those messages
  themselves.
- **Bevy**: the plugin and the Star Catch demo are new. CI builds them with
  Bevy and runs the demo through `gamenight-certify` on Linux with software
  rendering, but Windows and macOS window behaviour, the Windows foreground
  helper, audio devices and physical pads are not tested on hardware yet.
- **Warp (Luau)**: match settings, phone buttons and phone screens, faces
  and performance samples are not exposed to Luau yet. There is no prebuilt
  `warp` download yet: build it from source.
- **Rust without an engine**: the SDK delivers typed events; input, windows and
  faces are left to the game.
- **Godot 4**: Godot has no package manager, so each game vendors the addon.
  Run `sdk/godot/sync.py` and the CI check to keep copies current.

# Integrating your game with Splitscreen Club

Splitscreen Club supplies the party, seats and lifecycle. Your game owns gameplay,
rounds and results. Players can stay in a game until they choose another one.

Start from the [shared LÖVE runner](https://github.com/ontola/gamenight-games/blob/main/love-party/README.md) for a Lua game.
The [wire reference](https://splitscreen.club/docs/protocol) defines messages; the
[release requirements](https://github.com/ontola/gamepad-party/blob/main/contract/requirements.json) define what must work.
A successful handshake alone is not a complete integration.

## Submit a game

Start in the [developer portal](https://splitscreen.club/developers). Sign in
with your email and announce your game: a title, a short pitch and a player count
are enough. No protocol integration is required to start. Questions go to the
portal's **Help** tab; replies appear there and in your inbox.

We can help with integration, or you can use this guide with your own developers
or AI tools. For assisted work, agree repository access, code handling and any AI use
first. Private repositories can stay private. Splitscreen Club prepares a pull request;
you review and merge it, then supply the resulting build for testing.

When ready for review, open your game in the portal and use its **Review** tab.
Submit one platform build with a version, player limits and controls. Its SHA-256
is required before approval. The portal keeps private feedback and revisions;
each revised build needs a new review. Code access does not grant distribution
permission. Staff review the package, rights and test evidence before approving
catalog publication. Listing is free. The first flow supports free releases;
commercial interest is accepted, but purchases, payouts and timed trials are not
enabled by submitting a game.

Run the [contract checks](https://splitscreen.club/docs/testing) before review and share
their results. Also test physical controllers, joining/leaving, pause/resume and
returning to the lobby on each supported platform. Automated test coverage varies
by engine and runner; untested requirements are not passes. Do not treat the
certifier as a complete controller or commercial trial test environment.

## Connect

The host launches your process with `GAMENIGHT=1`, `GAMENIGHT_ADDR`,
`GAMENIGHT_GAME_ID` and `GAMENIGHT_TOKEN`. In managed mode, skip your title,
sign-in and controller-assignment screens. Keep standalone behavior separate.

Connect to the address over WebSocket, or send newline-delimited JSON over TCP.
Both transports use the same port, normally `127.0.0.1:7912`.

```json
{"type":"hello","role":"game","game":"my-game","token":"<GAMENIGHT_TOKEN>"}
```

The host returns `welcome` with `protocol_version` and the party snapshot.
Use the token supplied for this launch. One connected process serves one title;
that process may receive several sessions over its lifetime.

## Prepare before taking the screen

On `prepare`, retain the session ID, seats, player profiles and settings. Load
assets, compile shaders and prepare a real frame before replying `ready`.
Keep the window hidden and audio silent. Do not steal focus during launch.

```json
{"type":"progress","session":"<session UUID>","percent":40,"label":"Loading arena"}
{"type":"ready","session":"<session UUID>"}
```

Progress is optional. Ready must mean that Start can show playable content
without another loading screen. Do not require player input to finish preparing.
Keep the connection and lifecycle handling active while hidden or paused.

A long load (a large world, a first-time shader build) needs more care:
report a stage at least every five seconds, keep handling roster changes and
`dispose` while loading, and when the roster changes during loading, prepare
for the latest one rather than queueing every request. See
[Performance](https://splitscreen.club/docs/performance#load-everything-before-ready).

On `start`, show the prepared window and begin play. On `pause`, stop simulation,
timers and audio, then hide the game so the lobby can appear. On `resume`, show
the same game state and continue. Pause and resume are required for release,
including when the game is showing results rather than active gameplay.

On `dispose`, stop the session, hide the window, silence audio and release session
resources. Wait for another Prepare: the same process usually serves several
sessions in one evening, so keep the game running and reuse what you loaded. If the host connection is lost, exit cleanly
rather than leaving a game window or background process behind.

## Controllers belong to players

A seat is a playable position. Its occupant identifies a player; its `controller`
is an opaque host device token. Neither the seat index nor an `ordinal:N` token
is an index into SDL or another engine's local gamepad list.

Managed bundled games consume the host's `controller_frame` stream and match
`controllers[].controller` to `seats[].controller`. Do not enumerate local pads
and assign the first pad to the first seat. Enumeration can differ between the
host and game, especially after disconnects.

Use [the shared input adapter](https://github.com/ontola/gamenight-games/blob/main/love-party/shared/input.lua) or implement
[the frame contract](https://splitscreen.club/docs/protocol#bundled-games-authoritative-controller-input).
Rust games receive the same stream as `GameEvent::ControllerFrame` from
`GameNight::next_event()`. Keep the latest frame and look up each non-AI seat by
its `seat.controller` token. An empty frame, absent token or a frame older than
250 ms means neutral input. `controller_input` is a separate activity report
for presence and joining; calling it does not supply movement to the game.
Process released buttons and disconnected devices; stale input must become
neutral. Never assign one device to two players or substitute another player's
controller when a device disappears. Standalone input is a separate path.

Create bots for `ai` seats and no controllable pawn for `empty` seats. Player
profiles are keyed by player ID, not array position. Preserve that association
when seats or profiles change.

## Back, focus and fullscreen

Back/Select requests the lobby with `request_overlay`. The host pauses the game.
From the lobby, Back/Select can resume a paused game. Accept one transition per
press, require release, and guard against the same held press reaching the newly
focused window. The bundled [Back gate](https://github.com/ontola/gamenight-games/blob/main/love-party/shared/back_gate.lua)
requires one second of release before another accepted press.

**Never start or resume automatically on window focus.** Focus can change while
the host is opening the lobby. Only explicit host Start/Resume commands change
the running state. `request_start` exists for an explicit user request, not as a
focus-event handler.

Use a borderless window covering the display, not exclusive fullscreen. Configure
it before reporting Ready so switching does not change display resolution. The
bundled [window helper](https://github.com/ontola/gamenight-games/blob/main/love-party/shared/window.lua) prepares off-screen,
then hides/shows the window. Its Windows path adds one off-screen pixel row to
avoid exclusive-like presentation on affected drivers. Retain that behavior when
reusing the helper. Test focus changes on the target OS; one platform's result is
not proof for another.

## Rounds continue inside the session

Your game shows its own scores, winner names and results screen, then starts the
next round. Pause also freezes the results countdown. Do not wait for Splitscreen Club
to create a fresh session after every round.

You may send `finished` as a round notification. It keeps the active session,
pause state and prepared next game intact. It opens voting state but does not
force a vote, return to the lobby or advance the playlist. Explicit votes may
still request a transition.

Play next switches games. Skip only replaces the upcoming game. An explicit
replay command creates a new session; an ordinary next round stays in the same
session. Do not confuse either with an automatic end-of-match transition.

## Live players and settings

After Prepare, send `participation` before Ready to receive `party_updated`.
Set `instant_join` to true if your running match can accept new players, or false
for a fixed roster. Apply profile changes without resetting the match. Report
real human activity through `controller_input`; see the
[presence contract](https://splitscreen.club/docs/protocol#player-activity-sleep-and-joining-during-play).
`party_state` is the overlay snapshot, not a substitute for the game update API.
Every game also receives `players_updated` when someone picks up a profile in
the lobby mid-match: same seats, new name, colour, face or `profile_key`. Apply
it in place; the session resumes, it is never a restart.

`declare_settings` exposes game options. Handle `setting_changed` and document
which settings apply immediately or at the next round. See
[match settings](https://splitscreen.club/docs/protocol#match-settings). Log protocol errors and ignore
unknown fields rather than crashing.

## Player faces and colours

Name, clothing colour, skin colour and artwork are separate player fields.
Show the actual player name and preserve profile ownership. Draw skin beneath
the transparent face artwork; do not recolour the artwork with the clothing tint.

```lua
local Face = require("shared.face")
Face.drawFace(player, x, y, radius)
```

The [face API](https://splitscreen.club/docs/faces) uses a head centre and radius, preserving hat padding.
It supports mirroring, rotation and live artwork changes. Rust integrations use
`gamenight_protocol::Avatar::parse` and `head_layout()`.
A player portrait is appropriate for vehicles or other non-human characters.

Faces, names and colours have separate checks. First-party games must pass all
three for release; a colour check does not prove that a face was rendered.

## Artwork for the catalog and lobby

Supply separate fields in the shelf entry:

```json
{
  "id":"my-game",
  "title":"My Game",
  "cover":"art/cover.png",
  "icon":"art/icon.png",
  "screenshot":"art/gameplay.png"
}
```

Use a portrait cover for Up next, a square icon for case spines, and a real
gameplay screenshot for the TV. They are distinct assets. Colour is an optional
accent, not a replacement for artwork. Missing artwork should retain a readable
title fallback.

Shelf-relative PNG paths are resolved by the host and sent as data URIs. For
catalog publication, follow the [catalog guide](https://github.com/ontola/gamepad-party/blob/main/catalog/README.md) and the
current manifest validation. Do not put launch paths or credentials in profile
messages.

## Verify before shipping

Run the [contract checks](https://splitscreen.club/docs/testing) against packaged builds.
The versioned requirements distinguish essential play behavior, personalisation
and optional party extras. The catalog score uses matching platform/build evidence;
source declarations alone do not earn a pass.

Also follow the [desktop checklist](https://github.com/ontola/gamepad-party/blob/main/docs/desktop-integration-checklist.md) with real
controllers. Test two different profiles, reversed connection order, unplugging
a pad, nonzero stick input while the lobby is unfocused, live artwork updates,
repeated Back/Resume and several game switches.
Synthetic input checks cannot prove physical controller ownership on your machine.

# Warp / Luau

[Warp](https://github.com/ontola/warp-game-engine) is the open-source (MIT)
game engine that Splitscreen Club's own games are made in, such as Neon
Siege, Dead Miles and Relay Keepers. Support for Splitscreen Club is built
in. With the `warp` executable a game is only Luau scripts, synth sound
patches and glTF models: there is nothing to compile, and a file you save
reloads in the running game. That makes it the shortest path for a new game,
and a good fit for making one with an AI agent.

## What the runtime does for you

When Splitscreen Club starts a Warp game, the runtime handles the whole
[lifecycle](https://splitscreen.club/docs/lifecycle) without any code from you:

- The window stays hidden while the game prepares, and goes fullscreen on Start.
- Every seat in the room becomes a player in your game, with the name and
  colour from their profile. AI seats become bots.
- Each player's controller arrives as `input[id]` in your `tick`.
- Back goes to the room and pauses the game, Resume continues it, and players
  who join or leave mid-game do so without a restart.
- Start opens a menu with your game's title, Resume and New round.

You call `game.finish()` when a match is over, `game.log(text)` to write a
line in the room log, and `players.rumble(id, strength, seconds)` to buzz a
controller.

Not yet available from Luau: match settings in the app, phone buttons and
phone screens, and online play.

## Get the warp executable

There is no download yet: build it from source with
[Rust](https://rustup.rs).

```sh
git clone https://github.com/ontola/warp-game-engine
cd warp-game-engine
cargo build --release -p warp --bin warp
```

The executable is `target/release/warp` (`warp.exe` on Windows). Build on
Windows to get the `warp.exe` that you ship.

## Make a game

```sh
warp new my-game            # a small working starter game
warp run my-game            # play it, windowed with --windowed
warp check my-game          # load and run 120 ticks without a GPU: the fastest check
```

A game is a folder:

```text
my-game/
  game.toml           title, players, bots, sky (all optional)
  main.luau           the game: init, tick(dt, input), and more hooks
  sounds/*.luau       synth patches: sounds/pickup.luau is the sound "pickup"
  assets/             glTF models (.glb, .gltf)
  scripts/*.json      headless playtests
  types.d.luau        the whole API, for reading and editor completion
  gamenight.json      the store facts, as for any game
```

Set `id` in `game.toml` to your game's id from the [developer portal](https://splitscreen.club/developers).
The full Luau API, `game.toml` keys and the rules for deterministic games are
in the engine's
[warp executable guide](https://github.com/ontola/warp-game-engine/blob/main/engine/docs/warp-cli.md).
Read `types.d.luau` in your game folder for every function.

## Work with an AI agent

`warp run my-game --live` serves the running game over MCP. An agent can
then read its state, run Luau in it, edit files (the game reloads and keeps
its state), take screenshots and play sounds, while you play. See
[live control](https://github.com/ontola/warp-game-engine/blob/main/engine/docs/live-control.md).

Without a screen, `warp script my-game my-game/scripts/smoke.json --out out`
plays a scripted test, saves frames and sound, and fails when a check fails.
Add `KERN_ADAPTER=software` on a machine without a GPU.

## Test and package

1. Play it inside Splitscreen Club, or run the certifier as in
   [Share your game](https://splitscreen.club/docs/share#3-test-it), with the game's command after `--`:

   ```sh
   cargo run --release -p gamenight-certify -- my-game --players 2 -- path/to/warp my-game
   ```

2. Package on Windows: the package is `warp.exe` next to a `game/` folder
   with your game. The engine has a script for it:

   ```powershell
   ./engine/crates/warp/tools/package-windows.ps1 -Game my-game -Executable target/release/warp.exe -OutDirectory build/my-game
   ./build/my-game/warp.exe check build/my-game/game --ticks 600
   Compress-Archive -Path build/my-game/* -DestinationPath build/my-game-windows.zip
   ```

3. Upload it with `--entrypoint warp.exe` and fill the store page, as in
   [Share your game](https://splitscreen.club/docs/share#4-upload-a-preview-build) steps 4 to 6.

## In the browser

The [browser lobby](https://splitscreen.club/play/) has a curated shelf. It
loads Warp games, including Luau games and selected built-in Rust games, and
can embed same-origin HTML games with their own browser runtime. A browser
release is added to the shelf separately from publishing a desktop build.
For a Godot game, [embed its Web export](https://splitscreen.club/docs/godot#embed-a-web-export-in-the-browser-lobby)
to use the lobby's players, controllers and pause/resume flow.

## A game in Rust on Warp

For more than Luau allows, write the game as a Rust crate on the engine and
use its `splitscreen-club` crate for the connection, as Growing Guns,
Spellstorm and Sideways do. Start with
[Making a game on Warp](https://github.com/ontola/warp-game-engine/blob/main/engine/docs/making-a-game.md).

# LÖVE / Lua

Use the [shared runner](https://github.com/ontola/gamenight-games/tree/main/love-party) in the separate `ontola/gamenight-games` repository. It handles the Splitscreen Club connection, hidden preparation, pause/resume, window switching and host controller input. The bundled games use this path.

## Run the reference game

Install LÖVE 11.5, clone the repository and run from its root:

```sh
python scripts/fetch-game-sources.py
love ../gamenight-games/love-party
```

The fetch command checks out the revision in `game-sources.json` beside the host repository. For local edits, set `GAMENIGHT_GAMES_DIR` to your game checkout before testing or packaging.

This starts the standalone menu. The host supplies `GAMENIGHT=1`, its address, game ID and launch token when launching a managed build. Do not set a made-up token yourself.

## Add your game module

Keep simulation in a game module and leave lifecycle handling in the runner. A module defines `new(players, rng)` and `update(state, dt, inputs)`. This is the beginning of the real Neon Trails module:

```lua
function M.new(players, rng)
	local s = { players = players, rng = rng }
	reset(s)
	return s
end
function M.update(s, dt, inputs)
	if s.intermission then
		s.intermission = s.intermission - dt
		if s.intermission <= 0 then
			reset(s)
		end
		return
	end
	for i, p in ipairs(s.players) do
		local c = inputs[i]
		local dx, dy = 0, 0
		if math.abs(c.x) > math.abs(c.y) and math.abs(c.x) > 0.3 then
			dx = c.x > 0 and 1 or -1
		elseif math.abs(c.y) > 0.3 then
			dy = c.y > 0 and 1 or -1
		end
		if dx ~= 0 or dy ~= 0 then
			if dx ~= -p.dx or dy ~= -p.dy then
				p.nextX, p.nextY = dx, dy
			end
		end
	end
```

[Source: games/love-party/games/trails.lua](https://github.com/ontola/gamenight-games/blob/59afa33129507a745b1bcef2a42b59dc0016d105/love-party/games/trails.lua#L30)

The input entries belong to the supplied player slots. Do not replace them with `love.joystick.getJoysticks()` in managed mode. The shared input adapter neutralises disconnected devices and frames older than 250 ms.

Register a new module in `modes` in [main.lua](https://github.com/ontola/gamenight-games/blob/main/love-party/main.lua), add its renderer and add its ID to `GAMES` in [the packaging script](https://github.com/ontola/gamepad-party/blob/main/scripts/package-love-party.py). These are explicit registries, not automatic plugin discovery. Use an existing game as the full worked example.

## Draw a player face

```lua
local Face = require("shared.face")
Face.drawFace(player, x, y, 24, { facing = -1 })
```

`x` and `y` are the centre of the head. The helper draws the skin circle before the transparent artwork, retains space for hats and handles live artwork changes. See [Faces & colours](https://splitscreen.club/docs/faces).

## Keep the shared window path

Use `shared.window` and `shared.back_gate`. Prepare before showing the window. Back needs a fresh press after release, and a focus event must never resume a paused game. Keep borderless fullscreen and the helper’s Windows presentation workaround.

## Package and test

```sh
python scripts/test-love-simulation.py
python scripts/package-love-party.py --output dist/my-party-build
```

The output directory must be new. Packaging builds the registered titles; it does not automatically publish them. Run the [integration suite](https://splitscreen.club/docs/testing) against the resulting packages, then check real controllers and window switching on each target OS.

## Optional performance diagnostics

The bundled launcher samples application frame intervals while running and reports them every ten active seconds. It includes GPU, OS and pixel dimensions; CPU and RAM are unavailable. Standalone games send nothing. See the [protocol reference](https://splitscreen.club/docs/protocol#session-diagnostics) for counters, limits and missing-data semantics. These diagnostics contain no accounts, behavioral history or recommendation logic.

## Game settings

Use the [settings helper and game reference](https://splitscreen.club/docs/settings) to expose choices, toggles and bounded numbers to the lobby and phone. Validate each change and snapshot round rules when creating a round.

# Bevy

`gamenight-bevy` is a Bevy plugin that does the Splitscreen Club side of a game for
you. Add it next to `DefaultPlugins`, read `GameNightEvent` messages and ask
`GameNight` for each seat's controller. The plugin:

- connects when Splitscreen Club launched the game and runs standalone otherwise,
  with the keyboard and every local gamepad as seats, so your input code is
  the same in both modes;
- follows Prepare, Start, Pause, Resume and Dispose, and sends Ready two frames
  after you call `ready()`, so the first frame of your level exists before Start;
- keeps the window hidden and unfocused while warming, shows it borderless
  fullscreen on Start and Resume and hides it on Pause and Dispose;
- pauses every playing `AudioSink` while you are not on the TV and updates at
  10 fps while warm or paused, while still hearing Resume;
- gives each seat its own controller by host token, with deadzones, press
  edges and a release required after Start and Resume;
- reports activity so nobody is marked asleep, and rumbles a seat's pad;
- re-declares your settings, phone buttons, phone screen and text commands
  after every reconnect, and replays setting changes from your own menu;
- reports frame timing every ten seconds of play, with CPU, GPU, OS, memory
  and window size;
- sends F1 to the party (physical Back is the host's own) and exits when the
  host goes away.

The demo game in [`sdk/bevy/demo`](https://github.com/ontola/gamepad-party/blob/main/sdk/bevy/demo/src/main.rs), Star
Catch, uses every feature on this page. Each excerpt below is read from it.
CI runs it through the [conformance harness](https://splitscreen.club/docs/testing) against a real
host on every push.

## Add the plugin

The plugin targets Bevy 0.20 (Rust 1.97.1 or newer). Pin a reviewed commit of
the public repository:

```toml
[dependencies]
bevy = "0.20"
gamenight-bevy = { git = "https://github.com/ontola/gamepad-party", rev = "YOUR_REVIEWED_COMMIT" }
```

Replace `YOUR_REVIEWED_COMMIT` with an actual commit hash.

## Set up the app

Wrap your window in `managed_window`, so a game Splitscreen Club launched starts

## Follow the session

Every message from Splitscreen Club arrives as a `GameNightEvent`. On Prepare, build
the level for exactly the seats you were given, then call `ready()`. Opt into
live roster changes with `participation(true)` first if new players can join
mid-round, as here. Nothing restarts on `RosterChanged` or `PlayersUpdated`:
newcomers get a pawn, leavers lose theirs, and a new name, colour or face is
painted onto the same pawn.

```rust
fn gamenight_events(
    mut commands: Commands,
    mut gn: ResMut<GameNight>,
    mut events: MessageReader<GameNightEvent>,
    mut game: ResMut<Match>,
    mut menu: ResMut<Menu>,
    art: Res<Art>,
    mut images: ResMut<Assets<Image>>,
    mut materials: ResMut<Assets<ColorMaterial>>,
    balls: Query<(Entity, &Ball)>,
    stars: Query<Entity, Or<(With<Star>, With<Bomb>, With<Blast>)>>,
    mut music: Query<&mut AudioSink, With<Music>>,
) {
    // Pawns despawned earlier in this batch (Dispose then Prepare arrive together).
    let mut gone = Vec::new();
    for event in events.read() {
        match event {
            GameNightEvent::Prepare { seats, players, .. } => {
                // Load everything while hidden. New players can drop in mid-round.
                gn.participation(true);
                *menu = Menu::default();
                let rules = game.rules.clone();
                *game = Match { rules, ..default() };
                clear(&mut gone, &mut commands, &balls, &stars);
                spawn_balls(
                    &mut commands,
                    &gn,
                    seats,
                    players,
                    &art,
                    &mut images,
                    &mut materials,
                    &mut game,
                );
                new_round(&mut commands, &mut game, &art);
                game.started = true;
                gn.ready();
            }
            // The plugin shows the window and plays audio on Start and Resume,
            // and hides and pauses them on Pause. Simulation systems run only
            // while `gameplay_runs`, so there is nothing else to do here.
            GameNightEvent::Start { .. }
            | GameNightEvent::Pause { .. }
            | GameNightEvent::Resume { .. } => {}
            GameNightEvent::Dispose { .. } => {
                clear(&mut gone, &mut commands, &balls, &stars);
                game.started = false;
            }
            GameNightEvent::RosterChanged { seats, players, .. } => {
                // Keep the match going: add newcomers, drop pawns of those who left.
                let mut known = Vec::new();
                let alive: Vec<(Entity, &Ball)> =
                    balls.iter().filter(|(e, _)| !gone.contains(e)).collect();
                for (entity, ball) in alive {
                    let still = seats
                        .iter()
                        .any(|s| s.index == ball.seat && s.occupant.player_id() == ball.player);
                    if still {
                        known.push(ball.seat);
                    } else {
                        commands.entity(entity).try_despawn();
                        gone.push(entity);
                    }
                }
                let fresh: Vec<Seat> = seats
                    .iter()
                    .filter(|s| !known.contains(&s.index))
                    .cloned()
                    .collect();
                spawn_balls(
                    &mut commands,
                    &gn,
                    &fresh,
                    players,
                    &art,
                    &mut images,
                    &mut materials,
                    &mut game,
                );
            }
            GameNightEvent::PlayersUpdated { players } => {
                // A new name, colour or face for the same player: repaint, never restart.
                for (entity, ball) in balls.iter().filter(|(e, _)| !gone.contains(e)) {
                    if let Some(player) = players.iter().find(|p| Some(p.id) == ball.player) {
                        commands.entity(entity).despawn_children();
                        dress(
                            &mut commands,
                            entity,
                            Some(player),
                            ball.seat,
                            &gn,
                            &art,
                            &mut images,
                            &mut materials,
                        );
                    }
                }
            }
            GameNightEvent::SettingChanged { key, value } => {
                game.rules.apply(key, value);
            }
            GameNightEvent::PlayerSettings { player_id, .. } => {
                for (entity, ball) in balls.iter().filter(|(e, _)| !gone.contains(e)) {
                    if ball.player == Some(*player_id) {
                        commands.entity(entity).despawn_children();
                        let player = gn.player(*player_id).cloned();
                        dress(
                            &mut commands,
                            entity,
                            player.as_ref(),
                            ball.seat,
                            &gn,
                            &art,
                            &mut images,
                            &mut materials,
                        );
                    }
                }
            }
            GameNightEvent::ActionTriggered { key, player_id } if key == "new_round" => {
                let who = gn
                    .player(*player_id)
                    .map_or("Someone".into(), |p| p.name.clone());
                info!("{who} asked for a new round");
                new_round(&mut commands, &mut game, &art);
            }
            GameNightEvent::CompanionMessage { player_id, data } => {
                if data.get("action").and_then(|a| a.as_str()) == Some("dash") {
                    for (entity, ball) in balls.iter().filter(|(e, _)| !gone.contains(e)) {
                        if ball.player == Some(*player_id) {
                            commands
                                .entity(entity)
                                .entry::<Ball>()
                                .and_modify(|mut b| b.phone_dash = true);
                        }
                    }
                }
            }
            GameNightEvent::CompanionPresence {
                player_id,
                connected: true,
            } => {
                let view = phone_view(&gn, &game, *player_id);
                gn.companion_message(Some(*player_id), view);
            }
            GameNightEvent::GameCommand { id, text, .. } => {
                let (ok, answer) = command(&mut gn, text);
                gn.command_result(id.clone(), ok, answer);
            }
            GameNightEvent::HostMusic { playing } => {
                if let Ok(mut sink) = music.single_mut() {
                    sink.set_volume(Volume::Linear(if *playing { 0.0 } else { 0.35 }));
                }
            }
            _ => {}
        }
    }
}
```

## Read each seat's controller

`gn.pad(seat)` returns the seat's controller for this frame: neutral when the
seat has none, when input is more than 250 ms old and while the game is not
running. `stick` applies a radial deadzone (up is positive y, as in Bevy's
world), `trigger` a trigger deadzone. `just_pressed` is true once per press,
and a button still held from the lobby has to be released before it counts.
Never use Bevy's gamepad order under Splitscreen Club: a seat's controller is a host
token.

```rust
fn steer(
    gn: Res<GameNight>,
    mut game: ResMut<Match>,
    mut balls: Query<&mut Ball>,
    time: Res<Time>,
) {
    let dt = time.delta_secs();
    game.present = balls.iter().map(|b| b.seat).collect();
    for mut ball in &mut balls {
        ball.dash = (ball.dash - dt).max(-0.6);
        ball.stunned = (ball.stunned - dt).max(0.0);
        if ball.bot || ball.stunned > 0.0 {
            continue;
        }
        let pad = gn.pad(ball.seat);
        let target = pad.stick(0)
            + Vec2::new(
                pad.pressed(PadButton::Right) as i32 as f32
                    - pad.pressed(PadButton::Left) as i32 as f32,
                pad.pressed(PadButton::Up) as i32 as f32
                    - pad.pressed(PadButton::Down) as i32 as f32,
            );
        let target = target.clamp_length_max(1.0) * SPEED;
        ball.velocity = ball.velocity.lerp(target, (dt * 12.0).min(1.0));
        let dash = pad.just_pressed(PadButton::A) || std::mem::take(&mut ball.phone_dash);
        if dash && ball.dash <= -0.6 {
            let dir = if target != Vec2::ZERO {
                target.normalize()
            } else {
                ball.velocity.normalize_or(Vec2::X)
            };
            ball.velocity = dir * DASH_SPEED;
            ball.dash = 0.18;
        }
    }
}
```

```rust
fn command(gn: &mut GameNight, text: &str) -> (bool, String) {
    let text = text.to_lowercase();
    if let Some(n) = text
        .split(|c: char| !c.is_ascii_digit())
        .find_map(|w| w.parse::<i64>().ok())
    {
        let n = n.clamp(20, 180);
        gn.set_setting("round_seconds", SettingValue::Number(n));
        return (
            true,
            format!("Rounds last {n} seconds from the next round."),
        );
    }
    for (word, value) in [
        ("few", "few"),
        ("less", "few"),
        ("lots", "lots"),
        ("more", "lots"),
        ("normal", "normal"),
    ] {
        if text.contains(word) && text.contains("star") {
            gn.set_setting("stars", SettingValue::Choice(value.into()));
            return (true, format!("Stars: {value}."));
        }
    }
    if text.contains("bomb") {
        let on = !(text.contains("no ") || text.contains("off") || text.contains("geen"));
        gn.set_setting("bombs", SettingValue::Toggle(on));
        return (true, format!("Bombs {}.", if on { "on" } else { "off" }));
    }
    (
        false,
        "I can change the round length, the stars and the bombs.".into(),
    )
}
```

## The Start menu

Start opens your own menu, for everyone; Back belongs to Splitscreen Club. The game's
name heads the menu, then Resume, then New round, then the settings, without
button hints. The menu changes settings through `set_setting`, so the change
also shows in the apps and comes back as `SettingChanged` (standalone too).

```rust
/// Start opens and closes the menu for everyone; any player can use it.
/// Back is never read: it belongs to GameNight.
fn menu_input(
    mut commands: Commands,
    mut gn: ResMut<GameNight>,
    mut menu: ResMut<Menu>,
    mut game: ResMut<Match>,
    art: Res<Art>,
) {
    if !gn.is_running() {
        return;
    }
    let seats: Vec<u8> = gn.seats.iter().map(|s| s.index).collect();
    for seat in seats {
        let pad = gn.pad(seat);
        if pad.just_pressed(PadButton::Start) {
            menu.open = !menu.open;
            menu.row = 0;
            continue;
        }
        if !menu.open {
            continue;
        }
        let vertical =
            pad.just_pressed(PadButton::Down) as i32 - pad.just_pressed(PadButton::Up) as i32;
        menu.row = (menu.row as i32 + vertical).rem_euclid(MENU_ROWS.len() as i32) as usize;
        let step =
            pad.just_pressed(PadButton::Right) as i64 - pad.just_pressed(PadButton::Left) as i64;
        let row = MENU_ROWS[menu.row];
        match row {
            "Resume" if pad.just_pressed(PadButton::A) || pad.just_pressed(PadButton::B) => {
                menu.open = false
            }
            "New round" if pad.just_pressed(PadButton::A) => {
                menu.open = false;
                new_round(&mut commands, &mut game, &art);
            }
            "Resume" | "New round" => {
                if pad.just_pressed(PadButton::B) {
                    menu.open = false;
                }
            }
            key => {
                let step = if pad.just_pressed(PadButton::A) && step == 0 {
                    1
                } else {
                    step
                };
                if step != 0 {
                    let next = next_value(key, &game.rules.value(key), step);
                    // Through GameNight, so the apps show the same value.
                    gn.set_setting(key, next);
                }
                if pad.just_pressed(PadButton::B) {
                    menu.open = false;
                }
            }
        }
    }
}
```

## Rounds keep going

At the end of a round, show the result briefly, put the winner in the room log,
save each player's progress and call `finished()`. Then start the next round
yourself: `finished()` does not end the session. Players leave with Back.

```rust
fn round_clock(
    mut commands: Commands,
    mut gn: ResMut<GameNight>,
    mut game: ResMut<Match>,
    art: Res<Art>,
    time: Res<Time>,
) {
    let dt = time.delta_secs();
    if game.in_results() {
        game.results -= dt;
        if game.results <= 0.0 {
            new_round(&mut commands, &mut game, &art);
        }
        return;
    }
    game.clock -= dt;
    if game.clock > 0.0 {
        return;
    }
    // Round over: show the result, tell GameNight, save stats, go again.
    game.clock = 0.0;
    game.results = RESULTS_SECONDS;
    let best = game.scores.iter().max_by_key(|e| e.stars).copied();
    if let Some(best) = best.filter(|e| e.stars > 0) {
        let name = best
            .player
            .and_then(|id| gn.player(id))
            .map_or("A bot".into(), |p| p.name.clone());
        gn.room_log(format!(
            "{name} wins round {} with {} stars",
            game.round, best.stars
        ));
    }
    // Lifetime stars and wins follow each profile to the next game night.
    for entry in game.scores.clone() {
        let Some(id) = entry.player else { continue };
        let old = gn.player_data(id).cloned().unwrap_or_else(|| json!({}));
        let total = old.get("stars").and_then(|v| v.as_u64()).unwrap_or(0) + entry.stars as u64;
        let won = best.is_some_and(|b| b.player == Some(id) && b.stars > 0);
        let wins = old.get("wins").and_then(|v| v.as_u64()).unwrap_or(0) + u64::from(won);
        gn.save_player_data(id, json!({ "stars": total, "wins": wins }));
    }
    gn.finished();
}
```

## Faces, colours and couch order

`avatar_image(player)` decodes a player's drawn face into a nearest-filtered
`Image` plus where the head sits in it. Draw a circle in the skin colour and
put the drawing's head centre on it. `hex_color` reads profile colours.

```rust
/// The body in the player's colour, a head in their skin colour and their face.
fn dress(
    commands: &mut Commands,
    entity: Entity,
    player: Option<&Player>,
    seat: u8,
    gn: &GameNight,
    art: &Art,
    images: &mut Assets<Image>,
    materials: &mut Assets<ColorMaterial>,
) {
    let fallback = bot_color(seat);
    let color = hex_color(player.and_then(|p| p.color.as_deref()), fallback);
    let skin = hex_color(
        player.and_then(|p| p.skin_color.as_deref()),
        Color::srgb(0.96, 0.8, 0.66),
    );
    let square = player
        .and_then(|p| gn.player_setting(p.id, "shape"))
        .is_some_and(|v| v == SettingValue::Choice("square".into()));
    let body = if square {
        art.square.clone()
    } else {
        art.circle.clone()
    };
    commands.entity(entity).with_children(|parent| {
        parent.spawn((
            Body,
            Mesh2d(body),
            MeshMaterial2d(materials.add(color)),
            Transform::from_scale(Vec3::splat(BODY)),
        ));
        parent.spawn((
            Mesh2d(art.circle.clone()),
            MeshMaterial2d(materials.add(skin)),
            Transform::from_xyz(0.0, 4.0, 0.1).with_scale(Vec3::splat(HEAD)),
        ));
        match player.and_then(avatar_image) {
            Some((image, head)) => {
                // Put the head centre of the drawing on the head circle.
                let scale = HEAD / head.radius;
                let size = Vec2::new(image.width() as f32, image.height() as f32);
                let offset = (size / 2.0 - Vec2::from(head.center)) * Vec2::new(1.0, -1.0) * scale;
                parent.spawn((
                    Face,
                    Sprite {
                        image: images.add(image),
                        custom_size: Some(size * scale),
                        ..default()
                    },
                    Transform::from_xyz(offset.x, 4.0 + offset.y, 0.2),
                ));
            }
            None => {
                for x in [-7.0, 7.0] {
                    parent.spawn((
                        Mesh2d(art.circle.clone()),
                        MeshMaterial2d(art.dark.clone()),
                        Transform::from_xyz(x, 7.0, 0.2).with_scale(Vec3::splat(3.2)),
                    ));
                }
            }
        }
    });
}
```

# Rust

Use `gamenight-sdk` for the WebSocket connection and typed events. The SDK is engine-independent. It does not create windows, pause systems, draw faces or apply controller state for you.

Making a Bevy game? Use the [Bevy plugin](https://splitscreen.club/docs/bevy) instead: it is built on this SDK and also handles the window, audio, per-seat controllers, settings, phone screens and faces.

## Add the SDK

For a project in this workspace, use the workspace dependency. For a separate project, pin a reviewed public repository commit:

```toml
[dependencies]
gamenight-sdk = { git = "https://github.com/ontola/gamepad-party", rev = "YOUR_REVIEWED_COMMIT" }
tokio = { version = "1", features = ["rt-multi-thread", "macros"] }
```

Replace `YOUR_REVIEWED_COMMIT` with an actual commit hash. Do not treat the placeholder as a published release.

## Receive lifecycle events

This compilable example shows the connection and session transitions. It has no renderer or simulation, so it reports Ready only for its empty sample session. Put your real loading and first-frame work before Ready.

```rust
//! Protocol-only skeleton, compiled by the documentation CI.
use gamenight_sdk::{GameEvent, GameNight, SdkError};

#[tokio::main]
async fn main() -> Result<(), SdkError> {
    if !GameNight::launched_by_daemon() {
        println!("Standalone mode: open your game's menu here.");
        return Ok(());
    }
    let mut host = GameNight::connect_from_env().await?;
    while let Some(event) = host.next_event().await? {
        match event {
            GameEvent::Prepare {
                session,
                seats,
                players,
            } => {
                // Replace this with hidden loading, roster setup and first-frame work.
                println!(
                    "Prepare {} seats and {} profiles",
                    seats.len(),
                    players.len()
                );
                host.participation(session, false).await?;
                host.ready(session).await?;
            }
            GameEvent::Start { .. } | GameEvent::Resume { .. } => {
                // Show the prepared window; enable simulation and audio.
            }
            GameEvent::Pause { .. } => {
                // Freeze simulation and audio, then hide the window.
            }
            GameEvent::ControllerFrame { controllers } => {
                // Store receipt time. Match controllers by token, never list order.
                println!("{} controller states", controllers.len());
            }
            GameEvent::PartyUpdated { seats, players, .. } => {
                // Apply the roster and changed profiles without restarting the round.
                println!(
                    "Update {} seats and {} profiles",
                    seats.len(),
                    players.len()
                );
            }
            GameEvent::Dispose { .. } => {
                // Release session resources. Keep listening for another Prepare.
            }
            _ => {}
        }
    }
    // Host disconnected: leave no window or background game running.
    Ok(())
}
```

[Source: crates/gamenight-sdk/examples/docs_lifecycle.rs](https://github.com/ontola/gamepad-party/blob/main/crates/gamenight-sdk/examples/docs_lifecycle.rs#L1)

Run it from the public repository with `cargo run -p gamenight-sdk --example docs_lifecycle`. Without a host launch it exits through the standalone branch. In a game, that branch starts your normal menu.

## Connect to your game loop

Run the network task separately and pass events into your engine through a channel. Apply Prepare and PartyUpdated to the roster. Store ControllerFrame data with a receipt time, then have your input system look up each seat’s exact controller token.

In an engine loop, gate simulation systems on your session state (the [Bevy plugin](https://splitscreen.club/docs/bevy) does this with `gameplay_runs`). Do not pause the network task or the systems that receive Resume. Drain messages every frame, including while loading, paused or displaying results. Send Ready after assets and a rendered frame are ready, not immediately after receiving Prepare.

## Controllers and faces

`GameEvent::ControllerFrame` contains `Vec<ControllerState>`. Clear input after 250 ms without a frame, on an empty frame, or when a token disappears. [Controllers & players](https://splitscreen.club/docs/controllers) covers axes, button bits and ownership.

Use `gamenight_protocol::Avatar::parse`, `to_rgba()` and `head_layout()` for artwork. Draw a skin-coloured circle underneath and use the head centre as the texture origin. [Faces & colours](https://splitscreen.club/docs/faces) describes the coordinates.

# Godot 4

The Godot addon handles lifecycle messages, runtime controller frames and live
player profiles over the native WebSocket connection or a browser host. Your game connects these to its simulation and
rendering.

## Install

Copy `sdk/godot/addons/gamenight` into your project’s `addons` directory and enable Splitscreen Club in Project Settings → Plugins. The plugin registers `GameNight` and `GameNightScreen` autoloads.

Godot has no package manager, so every game keeps its own copy of the addon, and copies fall behind. Run `python sdk/godot/sync.py path/to/your/game` from a Splitscreen Club checkout to update it, and add the drift check to your game's CI. It fails as soon as your copy differs from the SDK on `main`:

```yaml
jobs:
  gamenight-sdk:
    uses: ontola/splitscreen-club/.github/workflows/godot-sdk-check.yml@main
    with:
      path: .  # the folder that holds project.godot
```

The connection reads the launch environment automatically. Keep standalone menus separate from the managed path using `GameNight.launched_by_daemon`.

A game you start by hand stays offline, so a test run never joins the party
on your machine. To connect it to a development host anyway, set
`GAMENIGHT_ADDR=127.0.0.1:7912`, or call `GameNight.connect_to_host()`.

Use the `GameNight` autoload and connect to its signals; don't subclass it and
override its message handling. A subclass that replaces `_handle` silently
loses performance reports, settings replay and future protocol features.

## Embed a web export in the browser lobby

Use a Godot Web export preset. Set **HTML → Head Include** to `<script src="bridge.js"></script>` and copy `addons/gamenight/browser_transport.js` to `bridge.js` beside the exported HTML. The script must load before the game starts. Opening that HTML as its own page uses the standalone game. When the host embeds it in an iframe on the same origin, the addon connects to the parent and sets `GameNight.launched_by_daemon`.

The child announces its `game_id` in `hello`. Match the catalog ID, including hyphens. The autoload defaults to the lowercased project name. A game can set `GameNight.game_id` in its main scene's `_ready()` before the deferred browser handshake.

A browser host sends and receives the usual protocol objects in a `postMessage` envelope with `channel: "splitscreen-club-webgame-v1"` and `payload`. Address messages to the exact origin and verify both the origin and iframe window on receipt. After `hello`, send `welcome` and `prepare` with the session, seats and player profiles. Wait for `ready` before sending `start`. Route controller frames by their seat's controller token. On return to the lobby, pause and retain the iframe so a later `resume` continues the same match. The host owns iframe visibility and focus. `GameNightScreen` still manages audio and the warm frame budget.

## Lifecycle signals

These declarations come directly from the addon:

```gdscript

signal started(session_id: String)
```

## Controllers and live profiles

Use the runtime stream in managed play. A seat's controller token is opaque;
it is not a Godot joystick index. `frame_for_seat` resolves the token from the
latest roster, returns a copy, and returns an empty frame while paused or when
input is more than 250 ms old.

```gdscript
func _physics_process(delta: float) -> void:
    if GameNight.phase != "running":
        return
    var frame = GameNight.frame_for_seat(0)
    var movement = GameNight.stick(frame, 0)          # left stick, deadzone applied
    var throttle = GameNight.trigger(frame, 1)        # right trigger, 0 to 1
    if GameNight.just_pressed(0, GameNight.BUTTON_A): # one press, one jump
        jump(0)
    if GameNight.button(frame, GameNight.BUTTON_X):   # held
        charge(0)
    if movement != Vector2.ZERO:
        GameNight.report_activity(0)
```

The SDK names every button and axis (`BUTTON_A` to `BUTTON_RIGHT`,
`AXIS_LEFT_X` to `AXIS_RIGHT_TRIGGER`). `stick` and `trigger` apply the
deadzones our games settled on (`STICK_DEADZONE` 0.15, `TRIGGER_DEADZONE`
0.06); pass your own as the last argument. `just_pressed` is true on the
physics tick a button went down; read it in `_physics_process`. After Start
and Resume, a button still held from the lobby must be released first, so the
press that started the game does not also fire in it.

Rumble a seat's pad with `GameNight.rumble(seat, weak, strong, seconds)`:
`weak` is the light motor, `strong` the heavy one, both 0 to 1. Each call
replaces the last, so call it a few times a second while an effect lasts and
with zeros to stop. Standalone it drives the local joypad.

`frame_for_seat` is empty while the session is not running. Your own Start
menu can read input while paused with `frame_for_seat(seat, true)`.

Use `GameNight.roster_changed` to refresh seat ownership, names, skin colour
and avatar artwork. The current snapshot is available in `GameNight.party`.

Connect `GameNight.players_updated` too. It fires when someone picks up a
profile in the lobby mid-match: the same players in the same seats, with a new
name, colour, face or `profile_key`. Update labels and faces in place and keep
the match going; never restart over it. Every game gets it, opted in or not.

Split-screen and other left-to-right layouts follow the couch, not the seat:
`GameNight.couch_order(seats, players)` returns the seats left to right as the
players sit (they pick their place in the lobby's Start menu). Call it again on
`players_updated`, because people can move mid-match; slide the views over.
`devices_for_local_seats()` is only for standalone play and returns no native
devices in managed mode. Back/Select belongs to the host; do not bind native
Back to a second pause/resume handler.

For circular faces, use `face.gd` with a head centre and radius. See the
[face helper example](https://splitscreen.club/docs/lobbies#faces-and-names). The helper draws the skin
circle under the artwork and supports historic avatar anchors.

## Screen ownership

`GameNightScreen` follows Start, Pause, Resume and Dispose. OS focus does not
request Start or Resume. A game preparing in the background stays quiet until
the runtime explicitly starts it. The helper handles the window and master
audio bus; your lifecycle callbacks must still pause the simulation and timers.

### Keep the window hidden at launch

For a game that prepares before being played, set `display/window/size/mode` to
`1` (Minimized) and `display/window/size/no_focus` to `true` at engine startup.
Minimizing in `_ready()` is too late to prevent the initial window appearing.
Use `GameNightScreen` for Start/Resume and explicitly claim the screen in your
standalone launch path. OS focus must never request gameplay.

For a Windows game that keeps its normal standalone window settings, pass
`--position -30000,-30000` as engine arguments in its managed launch entry,
before any `--` separator for game arguments. This parks the initial window
before the SDK runs. `GameNightScreen` also parks a warming Windows window and
disables focus before minimizing, so the minimize animation stays off-screen.
Start/Resume restores focus and fullscreen.

The Windows host also launches games with a hidden initial window and no
console window, before the SDK connects. Console wrappers inherit the managed
environment; the host owns their entire child process tree. This suppresses
the first native show request, not later explicit requests made by the game.
Keep the minimized/no-focus startup settings or off-screen engine arguments,
and let `GameNightScreen` control visibility until Start/Resume. The persistent
lobby itself launches normally.

On Windows, a focused game grants foreground permission through the host's
`GAMENIGHT_FOREGROUND_HELPER` before minimizing on Pause. Warmup, disposal,
repeated pauses and games behind another app never grant that permission.
The Game Room retries a new host focus handoff for at most one second because
the pause and focus messages arrive in different processes. Acquiring or losing
native focus cancels the retry; Alt-Tab never starts another handoff. Alt-Tab
away from a running game is a pause the host makes on its own (see
[Switching windows is a pause](https://splitscreen.club/docs/protocol#switching-windows-is-a-pause));
the game only sees `pause` and, when the party switches back, `resume`. The same
ordering applies when a game uses `automatic = false` and calls
`take_the_screen()` / `go_quiet("pause")` itself. The Windows helper and native
desktop focus policy still need real-device validation; headless tests cover
the lifecycle ordering, not Windows foreground-lock behavior.

While warming, a minimized window never draws, so never await
`RenderingServer.frame_post_draw` before `notify_ready()`: it does not return
and the lobby waits on "preloading" forever. Await `get_tree().process_frame`
instead whenever `DisplayServer.window_get_mode()` is `WINDOW_MODE_MINIMIZED`.
Leave the window itself to `GameNightScreen`. Godot refuses `hide()` on the main
window, and on Windows setting `borderless` shows the window again.

## Yield your soundtrack to host music

The welcome snapshot and subsequent `GameNight.party_updated` snapshots include
`now_playing` when Splitscreen Club detects a host music player. Check `playing`, not
just whether a track exists: paused tracks still have metadata. When it is true,
mute your music bus only. Keep effects audible and preserve the player's own
music preference. Restore that preference when host music pauses or disappears.

```gdscript
func _ready():
    GameNight.party_updated.connect(_host_music)
    _host_music(GameNight.party)

func _host_music(party: Dictionary):
    var track = party.get("now_playing", {})
    var playing = track is Dictionary and bool(track.get("playing", false))
    AudioServer.set_bus_mute(AudioServer.get_bus_index("Music"), playing)
```

Use a dedicated `Music` bus. Growing Guns uses `MusicA` and `MusicB` for its two
soundtrack layers. Do not mute `Master`: that also silences game effects.

## Lifecycle

Subscribe once. The package re-declares your settings, phone buttons, phone
screen and plain-text requests after every reconnect, so declare them in
`Connected`:

```csharp
void Wire()
{
    var gn = GameNight;
    // Declaring once is enough: the SDK re-declares after every reconnect.
    gn.Connected += () =>
    {
        gn.DeclareSettings(Settings);
        gn.DeclareActions(Actions);
        gn.DeclareCommands("Change Orb Rush while you play: the number of orbs, the round length, or a new round.",
            "8 orbs", "rounds of 90 seconds", "new round");
        PhoneScreenFolder?.Invoke();
    };
    gn.Prepared += OnPrepared;
    gn.Started += _ => SetPaused(false);
    gn.Resumed += _ => SetPaused(false);
    gn.Paused += _ => SetPaused(true);
    gn.Disposed += _ =>
    {
        Session = "";
        MenuOwner = -1;
        SetPaused(true);
        Trace("disposed");
    };
```

[Source: examples/unity-demo/Assets/OrbRush/OrbRushGame.cs](https://github.com/ontola/gamepad-party/blob/main/examples/unity-demo/Assets/OrbRush/OrbRushGame.cs#L118)

Prepared loads the level while hidden and silent, then reports Ready. Start
begins play at once. Pause must freeze gameplay, timers and sound; Resume

follow later in the night, in the same process:

```csharp
void OnPrepared(string session, IReadOnlyList<Seat> seats, IReadOnlyList<Player> players)
{
    Session = session;
    // Live roster updates; a newcomer can join this match at once.
    GameNight.NotifyParticipation(session, instantJoin: true);
    GameNight.NotifyProgress(session, 10, "building the arena");
    SeatRunners(seats);
    NewRound(log: false);
    SetPaused(true);
    GoldUnlocked = GameNight.PartyUnion().Contains(GoldFloor);
    var names = new List<string>();
    foreach (var r in Runners) names.Add(r.Bot ? "bot" : $"{r.Name} (seat {r.Seat})");
    Trace("seated " + string.Join(", ", names));
    GameNight.NotifyProgress(session, 100);
    // Ready only once the first frame can be drawn: the level is built above.
    GameNight.NotifyReady(session);

```

[Source: examples/unity-demo/Assets/OrbRush/OrbRushGame.cs](https://github.com/ontola/gamepad-party/blob/main/examples/unity-demo/Assets/OrbRush/OrbRushGame.cs#L172)

Call `NotifyReady` only when the first frame can be drawn. `NotifyProgress`
is optional: send it when loading takes more than a moment, so the lobby can
show a real bar. `NotifyParticipation` from Prepared opts into live roster
updates; pass `instantJoin: true` only when a running match can take a new
player at once.

`NotifyFinished(session)` reports a round. It changes nothing else: your game
keeps its own results screen and starts the next round itself.

## Controllers

Seats are players. A seat's controller token is opaque; it is not a Unity
joystick index, and the order of pads Unity sees means nothing under
Splitscreen Club. `FrameForSeat(seat)` returns that seat's input from the host. It is
neutral while the session is not running and when the input is more than
250 ms old:

```csharp
(float x, float y) Read(Runner r)
{
    PadInput input;
    if (r.Bot) input = BotInput(r);
    else if (r.Seat >= 0)
    {
        // GameNight's input for this seat: neutral while paused or stale.
        var frame = GameNight.FrameForSeat(r.Seat);
        var (sx, sy) = Pad.Stick(frame);
        input = new PadInput { X = sx, Y = sy, Buttons = frame.Buttons };
    }
    else input = _localInput != null ? _localInput(r) : default;
    var mx = input.X;
    var my = input.Y;
    var held = input.Buttons;
    // Menu navigation uses the stick like a d-pad: one step per push.
    if (mx < -0.6f) held |= 1 << Pad.Left;
    if (mx > 0.6f) held |= 1 << Pad.Right;
    if (my < -0.6f) held |= 1 << Pad.Up;
    if (my > 0.6f) held |= 1 << Pad.Down;
    r.Pressed = held & ~r.Held;
    r.Held = held;
    var length = (float)Math.Sqrt(mx * mx + my * my);
    return length > 1f ? (mx / length, my / length) : (mx, my);
}
```

[Source: examples/unity-demo/Assets/OrbRush/OrbRushGame.cs](https://github.com/ontola/gamepad-party/blob/main/examples/unity-demo/Assets/OrbRush/OrbRushGame.cs#L503)

`Pad` names every button and axis (`Pad.A` to `Pad.Right`). `Pad.Stick` and
`Pad.Trigger` apply the deadzones our games settled on (0.15 and 0.06). On the
wire, up on a stick is negative y; `GameNight.Stick(seat)` gives a `Vector2`
with up positive, as Unity expects. `GameNight.JustPressed(seat, Pad.A)` is
true in the one frame a button went down; read it in `Update`, not
`FixedUpdate`. After Start and Resume, a button still held from the lobby must
be released first, so the press that started the game does not also fire in it.

Back/Select belongs to Splitscreen Club: the host pauses you and shows the lobby.
Never bind it. F1 does the same from a keyboard; the package handles it.

`ReportActivity(seat)` on a press or a stick past its deadzone keeps the
player from being marked asleep. It sends at most once a second per pad.
`Rumble(seat, weak, strong, seconds)` vibrates a seat's pad, both strengths 0
to 1; standalone it drives the local pad through the Input System.

Standalone, read your own pads and keyboard. Orb Rush does that in
`OrbRushView.ReadLocal`, and only there.

## The Start menu

Every Splitscreen Club game has the same Start menu: the game's name, Resume, New
round (which applies the options), then the settings. No button hints. Play
waits while it is open:

```csharp
bool Menu()
{
    if (MenuOwner < 0)
    {
        for (var i = 0; i < Runners.Count; i++)
        {
            if (Runners[i].Bot || !Runners[i].Pressing(Pad.Start)) continue;
            MenuOwner = i;
            MenuRow = 0;
            Trace("menu open");
            return true;
        }
        return false;
    }
    var p = Runners[MenuOwner];
    var rows = MenuItems.Length + MenuSettings;
    if (p.Pressing(Pad.Start) || p.Pressing(Pad.B)) { CloseMenu(); return true; }
    if (p.Pressing(Pad.Up)) MenuRow = (MenuRow + rows - 1) % rows;
    if (p.Pressing(Pad.Down)) MenuRow = (MenuRow + 1) % rows;
    if (p.Pressing(Pad.A) && MenuRow < MenuItems.Length)
    {
        if (MenuItems[MenuRow] == "New round") NewRound();
        CloseMenu();
        return true;
    }
    var step = (p.Pressing(Pad.Right) ? 1 : 0) - (p.Pressing(Pad.Left) ? 1 : 0);
    if (step != 0 && MenuRow >= MenuItems.Length)
    {
        var setting = Settings[MenuRow - MenuItems.Length];
        var value = setting.Key == "round_seconds" ? RoundSeconds + step * 10 : OrbCount + step;
        OnSetting(setting.Key, value);
        // Tell GameNight, so the phones and the assistant see the same value.
        if (GameNight.LaunchedByHost) GameNight.SetSetting(setting.Key, setting.Key == "round_seconds" ? RoundSeconds : OrbCount);
    }
    return true;
}
```

## Players joining and leaving

After `NotifyParticipation`, `RosterChanged` brings the new seats and players
when someone joins or leaves during your session. Keep everyone else's score:

```csharp
void OnRoster(IReadOnlyList<Seat> seats, IReadOnlyList<Player> players)
{
    var kept = new List<Runner>();
    foreach (var seat in seats)
    {
        if (!seat.IsPlayed) continue;
        var r = Runners.Find(x => x.Seat == seat.Index && x.Bot == seat.IsBot && (x.Bot || x.Profile?.Id == seat.PlayerId));
        if (r == null)
        {
            r = new Runner { Bot = seat.IsBot, Seat = seat.Index };
            Place(r, kept.Count, Math.Max(seats.Count, 1));
            Trace("joined seat " + seat.Index);
        }
        Dress(r, GameNight.PlayerForSeat(seat), kept.Count);
        kept.Add(r);
    }
    if (kept.Count == 0) return;
    Runners.Clear();
    Runners.AddRange(kept);
    if (MenuOwner >= Runners.Count) MenuOwner = -1;
}
```

## Saved progress

## The screen

`GameNightScreen` comes with the package and needs no code. When Splitscreen Club
launched the game it mutes and minimises the window at startup, drops to 10
frames a second once you report Ready, takes the screen in borderless
fullscreen with sound on at Start and Resume, and gets out of the way on Pause
and Dispose. Window focus never starts or resumes a game; only the host does.
Set `Automatic` to false to call `GoQuiet`, `Settle` and `TakeTheScreen`
yourself.

On Windows it minimises without taking focus and parks a warming window off
screen; on macOS it hides the app. On Linux there is no portable way to hide a
window, so it only mutes and throttles. Unity creates its window before any
script runs, so a warming game may show for a moment at launch; starting
windowed and without a splash screen keeps that short.

# Unreal Engine

The Splitscreen Club plugin for Unreal Engine 5 lives in `sdk/unreal/GameNight`. It
covers the whole game contract: the connection and lifecycle, input per seat,
the window and audio, the world pause, match and per-player settings, saved
progress, faces and phone screens. **Dash Derby** in `examples/unreal-demo` is a
complete demo game built on it, and every snippet on this page comes from
that game or the plugin.

The plugin is written for Unreal Engine 5.3 and later on Windows, macOS and
Linux. Its protocol core is plain C++17 and runs in CI on every change; the
Unreal side has no Unreal build in CI yet. See [What is tested](https://splitscreen.club/docs/unreal#what-is-tested).

## How it fits together

Everything goes through `UGameNightSubsystem`, a game instance subsystem that
lives from boot to quit and ticks also while the game is paused. Get it from
any actor with `UGameNightSubsystem::Get(this)`, or in Blueprint with the
**Splitscreen Club Subsystem** node. It talks to Splitscreen Club over the plain TCP
transport (one JSON message per line) on the same port as the WebSocket one.

The contract is the same as in every SDK:

1. **OnPrepared**: build the level for `GetSeats()` and `GetPlayers()` while
   hidden, then call `NotifyReady()`. Show nothing yet.
2. **OnStarted**: you are on screen. Start the match at once.
3. **OnPaused** and **OnResumed**: the party went to the lobby and came back.
4. A round ends: call `NotifyFinished()`, show the results, play the next
   round. Rounds repeat until the party picks another game.
5. **OnDisposed**: tear the session down. Another `OnPrepared` may follow.

The plugin takes care of the window and sound on its own: muted and off the
screen while warming, a lower frame cap once ready, borderless fullscreen in
front on Start and Resume, and away again on Pause. It also pauses the world
whenever the session is not running, so physics, timers and game sounds stop
without code from you. Both are settings. F1 returns to the party; the
controller's Back button is Splitscreen Club's own and reaches the host directly.
When the host goes away, a launched game quits.

## Read input per seat

Splitscreen Club routes every controller and phone to a seat. Read the seat, never
local device order: `GetPad(Seat)` gives the sticks (deadzone applied, up is
negative Y as on the wire) and buttons, and `JustPressed(Seat, Button)` is
true on the frame a button went down. A button still held from the lobby
must be released first, so one press never does two things.

```cpp
if (Runner.Seat >= 0)

	UGameNightSubsystem* GN = GameNight();
	const FGameNightPad Pad = GN->GetPad(Runner.Seat, true);
	Move = Pad.LeftStick;
	for (const EGameNightButton Button : {EGameNightButton::A, EGameNightButton::B, EGameNightButton::Start,
	                                      EGameNightButton::Up, EGameNightButton::Down, EGameNightButton::Left,
	                                      EGameNightButton::Right})
	{
		if (GN->JustPressed(Runner.Seat, Button)) OutPressed |= Bit(Button);
	}
	if (Pad.Buttons != 0 || !Move.IsNearlyZero(0.3)) GN->ReportActivity(Runner.Seat);
}
```

## Settings and the Start menu

Declare the settings the party may change. Phones, an LLM and your own menu
change the same values; every change arrives in `OnSettingChanged`, also the
ones you make yourself. A setting with `"scope": "player"` is every player's
own choice, here the shape of their body.

```cpp
// Declared to GameNight: the phones, an LLM and the Start menu change them.

	                  .set("default", 60).set("min", 20).set("max", 180));
```

## Rounds, results and saves

A round ends with `NotifyFinished()`; the session goes on. `AddRoomLog` writes
one short line to the room log in the app. Each player's own progress is saved
with their profile between nights, and `UnlockForPresent` gives an unlock to
everyone who was there; `PartyUnion` reads what the people here tonight have.

```cpp
void ADashDerbyGameMode::EndRound()
{
	Results = ResultsSeconds;
	TArray<const FOrbRunner*> Ranking;
	for (const FOrbRunner& Runner : Runners) Ranking.Add(&Runner);
	Ranking.StableSort([](const FOrbRunner& A, const FOrbRunner& B) { return A.Score > B.Score; });
	const FOrbRunner& Winner = *Ranking[0];
	Trace(FString::Printf(TEXT("round %d won by %s"), Round, *Winner.Player.Name));
	UGameNightSubsystem* GN = GameNight();
	if (GN && GN->IsLaunchedByGameNight())
	{
		// The session goes on: results now, then the next round, until the
		// party picks another game.
		GN->NotifyFinished();
		GN->AddRoomLog(FString::Printf(TEXT("%s won round %d with %d orbs"), *Winner.Player.Name, Round, Winner.Score));
		SaveProgress();
		// What the group earns counts for everyone who was there.
		if (Winner.Score >= 10) GN->UnlockForPresent(TEXT("crown"));
	}
	SendPhoneViews();
}

void ADashDerbyGameMode::SaveProgress()
{
	// Each player's own progress, kept with their profile between nights.
	UGameNightSubsystem* GN = GameNight();
	for (const FOrbRunner& Runner : Runners)
	{
		if (Runner.Player.Id.IsEmpty() || Runner.bBot) continue;
		const std::string Id = UGameNightSubsystem::ToUtf8(Runner.Player.Id);
		Json Data = GN->Core().player_data(Id);
		if (!Data.is_object()) Data = Json::MakeObject();
		Data.set("best", FMath::Max(static_cast<int64>(Data["best"].integer()), static_cast<int64>(Runner.Score)));
		Data.set("orbs", Data["orbs"].integer() + Runner.Score);
		Data.set("rounds", Data["rounds"].integer() + 1);
		GN->Core().SavePlayerData(Id, Data);
	}
}
```

```cpp
void ADashDerbyGameMode::HandlePhone(const FString& PlayerId, const FString& DataJson)
{
	// Phone messages are untrusted input: check them against the rules.
	const Json Data = Json::parse(UGameNightSubsystem::ToUtf8(DataJson));
	if (Data["tap"].str() != "boost") return;
	for (FOrbRunner& Runner : Runners)
	{
		if (Runner.Player.Id != PlayerId || Runner.BoostCooldown > 0.0f || bHostPaused) continue;
		Runner.Boost = BoostTime;
		Runner.BoostCooldown = BoostCooldownTime;
		Trace(TEXT("boost ") + Runner.Player.Name);
		SendPhoneView(Runner);
	}
}

void ADashDerbyGameMode::HandlePhonePresence(const FString& PlayerId, bool bConnected)
{
	// Phones reload and sleep: send the whole view again on connect.
	for (FOrbRunner& Runner : Runners)
	{
		if (Runner.Player.Id != PlayerId) continue;
		Runner.bPhone = bConnected;
		if (bConnected) SendPhoneView(Runner);
	}
}

void ADashDerbyGameMode::SendPhoneView(const FOrbRunner& Runner)
{
	UGameNightSubsystem* GN = GameNight();
	if (!GN || Runner.Player.Id.IsEmpty()) return;
	// The game decides, the phone draws: send the view, not the history.
	Json View = Json::MakeObject();
	View.set("name", ToJson(Runner.Player.Name))
	    .set("color", ToJson(Hex(Runner.Player.Color)))
	    .set("score", Runner.Score)
	    .set("round", Round)
	    .set("clock", FMath::CeilToInt(FMath::Max(Clock, 0.0f)))
	    .set("results", Results > 0.0f)
	    .set("boost", Runner.BoostCooldown <= 0.0f);
	GN->SendCompanionMessage(View, Runner.Player.Id);
}
```

# Build a lobby

A lobby is a persistent party interface, implemented as a separate executable.
The runtime owns players, controller bindings and game sessions. The lobby
chooses how to present them. The Godot Living Room is a runnable example with
names, custom faces, guest joining, game selection, queueing and resume.

## Run the Godot example

Install Godot 4.5 or newer and the [development dependencies](https://github.com/ontola/gamepad-party/blob/main/docs/development.md).
From the repository root:

```sh
python scripts/run-local.py --lobby godot --godot /path/to/godot --shelf /path/to/games.json
```

On Windows, pass the Godot executable path. With no shelf, the script supplies
the terminal SDK demo. `--skip-build` reuses existing Rust binaries. The default
lobby is the bundled Game Room (`--lobby game-room`); this option selects
`godot-lobby`.

Open `sdk/godot/project.godot` in the editor to change the example. Start it
through the runtime to get an authenticated connection. Opening the project
alone displays a connecting screen, not a synthetic party.

Controls: press A on a controller to join. LT/RT cycle games; the
selected game is larger in the centre of its two neighbours. Only games the
seated players fit are listed. The stick/D-pad
moves between controls. On a game card, A queues the game after earlier picks;
X plays it now (it goes on top of the queue and starts once it has loaded). The
merged queue panel shows its first entry as Up next, with the remaining games
alongside it. Select Start game to launch the head of the queue. Back returns to
the lobby (when it is let go) or resumes an overlay-paused game. Hold Back to
see the chords:
Back+RB skips straight to the next game, Back+LB goes back to the previous
game, Back+B (press B twice) leaves the party and Back+Y reports a bug (a
screenshot goes to Splitscreen Club, the phones at the table are asked what
went wrong). Lobbies draw the host's
`back_menu` while someone holds Back. Y leaves that controller's seat.

The controller hint bar shows **X Play now · A Queue · LT Previous · RT Next**
with Xbox-style face-button and trigger icons. These hints are not selectable;
focus stays on the game cards and the other lobby controls.

## Talk to the assistant

When `GAMENIGHT_ASSISTANT_URL` supplies an authenticated session entry, select
**Talk to assistant** and hold A, or hold the control with the mouse. Keyboard
users can hold C. A pulsing microphone shows when recording is active. Release
to transcribe and send; B or Escape cancels before submission. The Menu/Start
button has no assistant shortcut. The lobby remains open throughout the request
and shows the assistant's result. Closing a submitted request's panel does not
undo a game change already sent to the host.

This source example currently transcribes with the installed Windows speech
recognizer. Enable microphone access for desktop apps and install a Windows
speech language. Recording lasts at most 20 seconds and stops on release,
focus loss, controller disconnection or loss of the runtime connection. Audio
is transcribed locally; only the text reaches the existing assistant API. The
temporary WAV is deleted after transcription. A process crash may leave that
file in Godot's user-data directory. The recording effect only runs while the
talk control is held, up to the 20-second limit.

The current native sign-in path supports the disposable preview's loopback
`/start/…` entry. It keeps its session cookie in memory and uses the existing
CSRF-protected assistant endpoints. Redirects are not followed. An ordinary
hosted `/agent` page cannot share a browser's login with a native process;
production native sign-in and non-Windows speech adapters remain unimplemented.
Local AI requests send on release. Paid requests first show the maximum credit
estimate and require explicit confirmation in the lobby.

`lobby/assistant.gd` and `lobby/transcribe-windows.ps1` belong to the example,
not the ordinary game addon. The current runner uses the source project;
packaged exports still need helper extraction and packaging support.

Run `python scripts/test-lobby-assistant.py --godot /path/to/godot` for the
loopback authentication, transcript, result and credit-confirmation checks.
Add `--check-windows-speech` to also transcribe generated speech and check that
the temporary recording is removed, without opening a microphone.
The lobby flow tests hold/release ownership and disconnect cancellation with
simulated controller frames. These tests do not validate a physical microphone
or speech accuracy in a noisy room.

## Queue behaviour

The queue works like a music player's. Games players pick form the player
queue, first come, first played. Behind it the host keeps autoplay picks, so
the queue never runs dry: games the host can start, not played yet tonight
first, then the ones played longest ago, preferring games whose best player
count is closest to the party. Autoplay drops its own entries that no longer fit the party
and tops up after every change. `playlist.queued` says how many entries after
`current` players picked; everything after those is autoplay.

The lobby sends `queue_game` with `first: false` for A, and `queue_game` with
`first: true` followed by `next` for X (Play now). `queue_game` is one atomic
host command, so simultaneous additions cannot overwrite each other's order. It
preserves the current game and its position, replaces the game's autoplay entry
instead of repeating it, and ignores a game that is already in the player queue.
`next` starts the prepared queue head. The older `play_next` command can start
an idle game and is not used for either catalog button.

## Register a replacement lobby

Set `GAMENIGHT_LOBBY_GAME` on the daemon to your shelf entry's ID. Include
`"GAMENIGHT_LOBBY_API": "1"` in that entry's `launch.env`. This declares runtime
input and party preservation before the executable connects, including when
it fails during startup. The launch command may be an exported executable or
Godot with `--path` pointing at a project.

The runtime supplies `GAMENIGHT_ADDR`, `GAMENIGHT_GAME_ID` and `GAMENIGHT_TOKEN`.
Use one WebSocket connection (plain JSON lines also work):

```json
{"type":"hello","role":"lobby","game":"my-lobby","token":"<GAMENIGHT_TOKEN>"}
```

Only the configured ID with its launch token can claim this role. Unlike the
game development handshake, a tokenless lobby is rejected. The welcome carries
the complete party snapshot. Send `{"type":"lobby_ready"}` after building the
first usable frame. The runtime then sends `lobby_focus` with screen ownership.
The lobby does not receive disposable game sessions.

This is an additive extension of protocol v1. Older daemons do not support the
lobby role; deploy the updated daemon and lobby together. A launch token binds
the connection to the selected process; it does not sandbox native code.
Existing overlay connections retain their [trusted local scope](https://github.com/ontola/gamepad-party/blob/main/SECURITY.md).

## State and commands

The lobby receives `party_state`, `lobby_focus`, `controller_frame` and `error`.
It may issue the existing [party commands](https://splitscreen.club/docs/protocol#party-commands-overlay-daemon),
plus `lobby_ready`, `quit_party`, `apply_update` and `switch_lobby`. It cannot report another game's session
lifecycle or publish physical controller frames.

| Request | Meaning |
|---|---|
| `join_party`, `leave_party`, profile and seat commands | Change runtime-owned players |
| `queue_next {game}` | Put a chosen game on top of the player queue and prepare it, without starting it |
| `play_next {game}` | Choose the next game; starts when ready only if no game is active |
| `queue_game {game,first}` | Add a game to the player queue, at the bottom or with `first` on top; never starts playback |
| `next` | Start the prepared next game, or wait for its preparation |
| `move_playlist_entry {expected,from,to}` / `remove_playlist_entry {expected,index}` | Edit an occurrence using the latest playlist snapshot; stale edits are rejected |
| `open_overlay` | Pause the active game and return to the lobby |
| `close_overlay` | Resume only the pause caused by opening the lobby |
| `set_setting {game,key,value}` | Apply a setting validated by the runtime |
| `quit_party` | Explicitly shut down the runtime and its children |
| `apply_update` | Restart into the downloaded host update named by `update_ready`, keeping the party; refused while a game is played |
| `switch_lobby {lobby}` | Make one of `party_state.lobbies` the host's lobby and restart into it, keeping the party; refused while a game is played |

On the packaged Windows host, `party_state.update_ready` holds the version of a
host update that finished downloading. Offer it between games. After
`apply_update` the runtime saves players, seats, controllers, phone links,
the queue and settings, the launcher covers the screen and installs, and the
new runtime restores the party with the same player IDs. The cover stays until
the new lobby sends `lobby_ready`. With the lobby on screen and nobody touching a
controller for about two minutes, the runtime updates by itself. Updates never
interrupt play; a game paused behind the lobby is closed by the restart.

Use `party_state` as the authoritative result. Commands currently have no
request IDs or individual success acknowledgements. Do not blindly replay
commands after a lost connection. Reconnect with the launch token and rebuild
from the new snapshot. The SDK never queues disconnected writes.

Use `remove_from_queue(index)` or `move_in_queue(from, to)` to edit the queue.
The Godot SDK serializes the snapshot cursor as an integer, including after
receiving JSON (which Godot parses as floating-point numbers). Custom clients
must also send integer indices and an integer or null `expected.current`.

The Godot client lives in `addons/gamenight/lobby.gd`. Instantiate it directly;
do not enable the game plugin's `GameNight` or `GameNightScreen` autoloads in a
lobby. Its signals supply snapshots, controller frames, connection status,
focus and errors. The example displays embedded or HTTPS catalog artwork.

## Minimal Godot client

Attach this script to your lobby scene. Connect signals before adding the client,
so the view receives the initial welcome. The client sends `lobby_ready` after
one scene-tree frame; finish any asynchronous screen setup before adding it.

```gdscript
extends Control

var lobby = preload("res://addons/gamenight/lobby.gd").new()
var party: Dictionary = {}

func _ready() -> void:
    lobby.party_changed.connect(func(snapshot):
        party = snapshot
        queue_redraw())
    lobby.rejected.connect(func(message): push_warning(message))
    add_child(lobby)

func add_to_queue(game_id: String) -> void:
    lobby.queue_game(game_id)        # A: after earlier picks

func play_now(game_id: String) -> void:
    lobby.queue_game(game_id, true)  # X: on top of the queue...
    lobby.start_next()              # ...and switch once it has loaded

func start_queue() -> void:
    lobby.start_next()              # Separate Start action
```

This is the connection and queue portion only. A complete lobby must also handle
`focus_changed` and `controllers_changed` as described below. The runnable scene
is `sdk/godot/lobby/main.gd`.

The same game can appear more than once, for example once in the player queue
and once among the games already played. Use playlist indices to move or remove one occurrence; game IDs alone are ambiguous.
The `expected` field must contain the full latest `party.playlist` value. On a
stale-edit error, redraw from the latest snapshot instead of silently retrying.
The SDK's `move_in_queue` and `remove_from_queue` helpers include this guard.

For loading feedback, read `warm_session.phase`, `progress` and `progress_label`,
plus `installs` for downloads. An entry being in the queue does not mean it is
ready. Keep the selected next game's artwork visible while it prepares. Autoplay
keeps the queue filled, so it never stops the night by running out.

## Input and screen ownership

Replacement lobbies receive runtime-sampled controller frames. Device tokens
are opaque, and must be matched against `seats[].controller`. The runtime
joins a controller when A is pressed on it, in the lobby and in a running game
(any other button, a stick or the D-pad never joins: a drifting stick cannot
bring back a player who just left, and a stray press only jiggles the pad),
handles controller activity and Back/Select. It consumes
an A press held during connection and Back before broadcasting frames so clients cannot accidentally
start a game while joining or immediately reopen a resumed game.

Controller frames use a sampler-owned delivery path, separate from party-state
serialization. Large catalog snapshots must not block stick updates. Back is
consumed by the host; an A button held when a controller connects is suppressed
until release. The stream retains opaque controller tokens and full analog axes.

Render the active lobby at a normal frame rate. On `lobby_focus: false`, mute,
release the screen and reduce background work while keeping the connection
alive. Only explicit player requests start or resume games; window focus is
not such a request. The Godot example uses window minimisation and restoration.

Accept controller input only while the SDK is both connected and active.
On disconnect, clear held input and close controller menus. The SDK revokes
its previous screen-ownership grant; a reconnecting `welcome` does not restore
it. Wait for a fresh `lobby_focus: true`, then require neutral controls before
accepting presses so actions held in the game cannot spill into the lobby.

Player and controller state survives a replacement lobby disconnect. A socket
failure can reconnect to the same process. A dead process gets up to three
restart attempts before opening the local recovery page. The game is paused
and players remain registered. Recovery offers Retry lobby, Resume game and
End game night. Retry resets the restart budget; it does not erase the party.
The installed launcher keeps browser requests available throughout the session.
Development hosts need `GAMENIGHT_WEB=1` to serve the recovery page. `quit_party`
is the deliberate exit path.

## Faces and names

Read names, skin colours, clothing colours and avatar payloads from the current
snapshot. The reusable `addons/gamenight/face.gd` implements the canonical
[face coordinates](https://splitscreen.club/docs/faces), transparent pixels, historic 16/32 pixel
anchors and nearest-neighbour artwork. It caches decoded textures, bounds its
cache and falls back to a default face for missing or malformed artwork.

```gdscript
var faces = preload("res://addons/gamenight/face.gd").new()

func _draw():
    faces.draw_face(self, player, Vector2(100, 100), 32)
```

Call it from a CanvasItem's drawing callback. Set that CanvasItem's
`texture_filter` to `TEXTURE_FILTER_NEAREST`. Supply the head centre and radius;
leave space around the head for hats and hair. Repaint when a party snapshot
changes a profile. The example keeps names and portraits beside each other.

## Phone joining and profile pickup

The public local-web server supplies `GET /api/player-links`. Its `room`
contains the current `code`, `join_url` and `qr_svg`; the URL uses the actual
LAN host and web port for a local room, or the registered cloud room's origin.
Do not build a QR from the lobby's WebSocket address. Unregistered rooms do not
get a QR. `scripts/run-local.py --lobby godot` starts local-web automatically.

The Godot view defaults to `http://127.0.0.1:7913`. Set `GAMENIGHT_LINKS_URL`
only when running a different local-web bridge. Phone profiles waiting for
pickup are returned in the same response. A local controller selects its
profile and the native lobby posts to
`/api/room-pickup/{pending_id}/{player_id}` with
`X-GameNight-Local-Pickup: 1`. Pickup requires a loopback connection and this
header; a phone cannot assign itself to another controller through this API.

## Game settings and artwork

The Settings button opens the selected game's declared settings. Toggles,
bounded integers and choices map to `set_setting`; the view reads the accepted
values from `party.settings`. A game must connect and declare its settings
before they appear. Queue it to load them. The host validates values, and the
game receives `setting_changed`.

`addons/gamenight/artwork.gd` loads PNG, JPEG and WebP asynchronously. It accepts
embedded images and HTTPS URLs, plus loopback HTTP for development. Downloads
are limited to two at a time, eight seconds and 8 MiB each; decoded images must
fit within 4096 × 4096. The texture cache holds 32 entries. Missing, invalid or
failed artwork leaves the game title visible instead of blocking navigation.

## Choose a lobby in the installed app

Register an installed executable in `local-games.json` in the Splitscreen Club data
directory, alongside the launcher's `shelf.json`. Use an absolute executable
path and an absolute existing `cwd` when supplied:

```json
[{"id":"my-lobby","title":"My lobby","launch":{
  "command":"/absolute/path/to/my-lobby",
  "env":{"GAMENIGHT_LOBBY_API":"1"}
}}]
```

On Windows the installed app passes `GAMENIGHT_APP_ID` to the lobby (and only
the lobby). Call `SetCurrentProcessExplicitAppUserModelID` with it before you
create a window, so the lobby shows up on a pinned Splitscreen Club taskbar button
instead of as a separate app. Send `lobby_ready` once your first frame is on
screen: that closes Splitscreen Club's welcome window.

In the installed app, `party_state.lobbies` lists the lobbies the host can run
(bundled, then registered ones), the running one marked `current`; with only
one lobby the list is empty. Game Room has **Switch lobby** in its Start menu,
a page that lists them. Picking
one sends `switch_lobby`: between games the host saves the choice, covers the
screen and restarts into that lobby with the same players, seats, controllers,
phone links and queue. During a game it is refused. A host that cannot
restart itself saves the choice for its next start.

Game Room only gives a walking character to players with a controller. Phone
players, and anyone else seated without one, are listed bottom left. When a
character's controller goes, it sleeps with a countdown and leaves the party
after 30 seconds in the room, unless the controller comes back; a listed player
with neither a controller nor a phone counts down the same way. **Remove a
player** in the Start menu takes anyone else out (press A twice).

Living Room shows **Current game** and **Up next** side by side, or stacked in a
narrow window. Current game shows the game's screenshot and **Resume**, even
when other games are queued. If there is no current game, only Up next is shown.
Resume keeps the current session and queue intact;
**Start game** under Up next advances the queue.

Launch `gamenight-launcher --choose-lobby`, or open
`http://127.0.0.1:7913/host/lobby` on the host while the installed app runs.
Choose the bundled Game Room or a registered replacement. The choice is saved
in `selected-lobby.json` and applies on the next launch. Missing executables,
and a saved choice of the retired Clubhouse (`lobby`), fall back to the bundled
Game Room. Registration does not download or install a
third-party lobby. Only install code you trust.

The preference and recovery controls are host-only. They reject LAN requests;
mutations also require `X-GameNight-Host: 1`. The recovery page uses
`retry_lobby`, `close_overlay` and `quit_party` through a trusted local overlay.
Retry is available only after the automatic restart budget is exhausted.

## Automated coverage

`python scripts/test-godot-sdk.py --godot /path/to/godot` checks the shared game
adapter's seat mapping, profile updates, lifecycle guards, stale input and
focus behaviour. `python scripts/test-lobby-recovery.py` checks the actual
daemon's crash budget, retry and party retention. Set `GAMENIGHT_TEST_DAEMON`
to a built daemon binary to use a non-default build directory.

Run `python scripts/test-host-lobby.py` for host preference and room-link HTTP
checks (requires local port 7913). The lobby flow also checks settings and
artwork fallback. These checks do not
certify physical controller drivers, TV focus handoff, media sessions or phone
camera scanning. Those still need device tests on each release platform.

## Closed games and failed launches

Read `party.game_issues` before showing loading or ready status. Each item has a
`game` ID and a `kind`: `closed`, `disconnected`, `exited_unexpectedly`,
`failed_to_start`, or `startup_timeout`. `warming` still identifies the intended
next game; an issue means its process is stopped, not currently loading.

The host clears the lost session and broadcasts the issue to connected lobbies
and overlays. It also checks every 200 ms for processes that exit before sending
`hello`. Startup has a ten-minute connection deadline to allow development builds.
A missing executable is reported immediately. Games remain stopped until an
explicit queue/start command retries them. Show a Retry action using `next` for
the head of the queue, or `queue_next` for a specific game without starting it.

A clean process exit can be labelled “Game closed”. A broken connection alone
cannot prove a crash or a deliberate quit; show “Game disconnected”. An observed
nonzero exit is “Game exited unexpectedly”. These states describe evidence, not
user intent. Reconnecting games clear their issue and must prepare again before
being shown as ready.

# C / C++

`sdk/c/gamenight.h` is a single-header TCP client for C99 and C++. It uses newline-delimited JSON on the same port as the WebSocket transport. POSIX and Winsock are supported.

## Add the header

```c
#define GAMENIGHT_IMPLEMENTATION /* In exactly one translation unit. */
#include "gamenight.h"
```

Copy the header into your project. Link Winsock (`ws2_32`) on Windows. Keep calling `gn_poll` from your loop, including when gameplay is paused. It returns 1 for an event, 0 when nothing is available and -1 on disconnection.

## Connect from the launch environment

This is the startup path in the checked-in C example:

```c
int main(void) {
    gn_client gn;
    gn_event ev;
    char playing[GN_ID_LEN] = "";
    double match_ends = 0.0;
    gn_result rc = gn_connect_from_env(&gn, "c-game");

    if (rc == GN_ERR_NOT_LAUNCHED) {
        /* Nobody launched us into a party: this is where a real game boots
         * its own title screen and plays standalone. */
        printf("[c-game] no GameNight in the environment; standalone\n");
        return 0;
    }
    if (rc != GN_OK) {
        fprintf(stderr, "[c-game] could not reach the daemon (%d)\n", rc);
        return 1;
    }
```

[Source: examples/c-game.c](https://github.com/ontola/gamepad-party/blob/main/examples/c-game.c#L42)

`GN_ERR_NOT_LAUNCHED` selects standalone mode. Other connection errors should stop the managed launch rather than open a disconnected game window.

## Event data

The current adapter’s event types are:

```c
typedef enum {
    GN_NOTHING = 0, /* gn_poll found no complete message this tick */
    GN_WELCOME,
    GN_PREPARE,
    GN_START,
    GN_PAUSE,
    GN_RESUME,
    GN_DISPOSE,
    GN_SETTING_CHANGED,
    GN_ERROR,
    GN_UNKNOWN /* a message type from a newer daemon: ignore it */
} gn_event_type;
```

[Source: sdk/c/gamenight.h](https://github.com/ontola/gamepad-party/blob/main/sdk/c/gamenight.h#L280)

On Prepare, load your level while hidden, then call `gn_ready`. Start shows play. Pause freezes simulation and audio; Resume restores them. Dispose frees session resources. Keep the socket alive for the next Prepare.

## What the header does not supply

The current `gn_seat` carries index, occupant, player ID and name. It does not expose controller tokens, controller frames, clothing colours, skin colours or face artwork. Implement those fields and message handling, or use a JSON client that preserves the full [protocol](https://splitscreen.club/docs/protocol). Do not assign local joystick enumeration to seat indices as a workaround.

The built-in name parser also replaces JSON `\\uXXXX` escapes with `?`. Extend it if your game needs complete escaped Unicode names. The fixed buffers limit message size; face payloads need appropriate storage and parsing.

## Compile the transport example

```sh
cc -std=c99 -Wall -Wextra -Werror -I sdk/c -o /tmp/c-game examples/c-game.c
```

This builds a timer-based protocol example on POSIX. It is not a playable reference with controller or face support. The docs CI compiles it to detect API drift; release confidence comes from [testing the actual packaged game](https://splitscreen.club/docs/testing).

The C client grows its receive buffer for player artwork, up to 8 MiB. Call `gn_close()` when the connection ends to release it. Receiving artwork does not imply that the adapter renders faces; that remains a separate capability.

# Other engines

Unreal Engine 5 has a [plugin](https://splitscreen.club/docs/unreal) and Unity has a [package](https://splitscreen.club/docs/unity). For any other engine, use the open protocol to write an adapter, or [ask for integration help](https://splitscreen.club/developers#help/new). Do not assume a game is supported because its engine can open a socket. [Engine support](https://splitscreen.club/docs/engines) lists what an adapter must cover. The [Unity package](https://splitscreen.club/docs/unity) is plain C# at its core and the [Unreal plugin](https://splitscreen.club/docs/unreal) has a plain C++17 core; both show a complete adapter, feature by feature.

## Open the connection

Read `GAMENIGHT_ADDR`, `GAMENIGHT_GAME_ID` and `GAMENIGHT_TOKEN` from the environment. Connect over WebSocket or newline-delimited JSON over TCP. The usual address is `127.0.0.1:7912`.

```json
{"type":"hello","role":"game","game":"my-game","token":"THE_LAUNCH_TOKEN"}
```

Use the actual game ID and launch token, then wait for Welcome and check the protocol version. The token is a launch credential, not a value to commit into your game.

## Keep the adapter alive

Receive messages independently of your simulation. Make sure your connection handler still runs while gameplay is paused. Dispatch engine operations to the appropriate game thread.

Handle Prepare, Start, Pause, Resume and Dispose explicitly. Send Ready after preparing the first frame. Window focus is not a Start or Resume command. Use borderless fullscreen to avoid display-mode switches.

## Decode host input

Use the host’s `controller_frame` stream. Match each state to `seats[].controller`, preserve button release edges and neutralise stale frames. The wire representation is defined in the implementation:

```rust
pub struct ControllerState {
    pub controller: String,
    /// left x/y, right x/y, left/right trigger; signed values / 32767.
    pub axes: [i16; 6],
    /// A B X Y LB RB Back Start LS RS Up Down Left Right (bits 0..13).
    pub buttons: u32,
}
```

[Source: crates/gamenight-protocol/src/lib.rs](https://github.com/ontola/gamepad-party/blob/main/crates/gamenight-protocol/src/lib.rs#L1272)

Treat player IDs and controller tokens as opaque values. See [Controllers & players](https://splitscreen.club/docs/controllers) for the matching rules and [Faces & colours](https://splitscreen.club/docs/faces) for rendering player artwork.

## Prove the integration

Use the [protocol reference](https://splitscreen.club/docs/protocol) for message fields and the [test guide](https://splitscreen.club/docs/testing) for build-specific evidence. A custom adapter needs the same pause, input, window and cleanup checks as a bundled game.

# Controllers & players

A controller belongs to a seat through its host token. A profile belongs to a player through its ID. Those associations must survive switching games and reconnecting devices.

## Match tokens, not array positions

For each local seat, find the `controller_frame.controllers` entry whose `controller` equals `seat.controller`. Look up the profile using `seat.occupant.player_id`. Neither list order nor a token such as `ordinal:2` tells you an SDL, Godot or engine device index.

The host frame uses these fields:

```rust
pub struct ControllerState {
    pub controller: String,
    /// left x/y, right x/y, left/right trigger; signed values / 32767.
    pub axes: [i16; 6],
    /// A B X Y LB RB Back Start LS RS Up Down Left Right (bits 0..13).
    pub buttons: u32,
}
```

[Source: crates/gamenight-protocol/src/lib.rs](https://github.com/ontola/gamepad-party/blob/main/crates/gamenight-protocol/src/lib.rs#L1272)

Axes are left X/Y, right X/Y and left/right trigger. Divide signed axis values by 32767. The button bits are A, B, X, Y, LB, RB, Back, Start, LS, RS, Up, Down, Left and Right, beginning at bit zero.

## Release stale input

An empty frame releases every controller. A missing token releases that device. More than 250 ms since the last frame means neutral input. Never borrow another device to fill a gap.

The LÖVE runner already applies this rule:

```lua
function M.updateHost(controllers)
    local previous={}
    for _,pad in ipairs(M.hostPads) do previous[pad.controller]=pad;pad.connected=false end
    local nextPads,seen={},{}
    for _,state in ipairs(controllers or {}) do
        if type(state.controller)=='string' and not seen[state.controller] then
            seen[state.controller]=true
            local pad=previous[state.controller] or {controller=state.controller}
            pad.axes,pad.buttons,pad.at,pad.connected=state.axes or {},state.buttons or 0,love.timer.getTime(),true
            function pad:isConnected() return self.connected and love.timer.getTime()-self.at < .25 end
            function pad:isGamepad() return true end
            function pad:getGamepadAxis(axis)
                if not self:isConnected() then return 0 end
                return (self.axes[axisIndex[axis]] or 0)/32767
            end
            function pad:isGamepadDown(...)
                if not self:isConnected() then return false end
                for _,button in ipairs({...}) do
                    local index=buttonIndex[button]
                    if index and math.floor(self.buttons/2^index)%2==1 then return true end
                end
                return false
            end
            nextPads[#nextPads+1]=pad
        end
    end
    M.hostPads=nextPads
    if M.players then M.bind(M.players,nextPads) end
end
```

[Source: games/love-party/shared/input.lua](https://github.com/ontola/gamenight-games/blob/59afa33129507a745b1bcef2a42b59dc0016d105/love-party/shared/input.lua#L19)

AI seats receive bots. Empty seats receive no controllable pawn. Keep standalone device enumeration separate from managed input.

## Joining and changing profiles

After Prepare, send `participation` before Ready (`GameNight.notify_participation` in Godot). Set `instant_join` only if the match can accept new players immediately. Handle `party_updated` without resetting the running match. Update names, clothing, skin and face artwork independently.

What our games do with a changing roster:

- **Fixed roster per round** (`instant_join: false`) is the simple default: a
  racing or sports game applies the new seats when the next round starts.
- **Drop in mid-round** (`instant_join: true`) suits games where one more
  player does not break fairness: spawn the newcomer near the others, or
  behind the leader in a race, rather than at the start.
- **A joining player replaces a bot**, never the other way round. AI never
  takes a seat a person holds.
- **A player who leaves** keeps their score until the round ends; their pawn
  can stand still, fade out or become a bot.
- **Colours can collide.** Two profiles may pick the same colour. Keep each
  player's own colour where you can and only shift the later duplicate.
- **Read the seat count from Prepare.** Don't assume a maximum. Declare
  `players_min` and `players_max` honestly in your catalog entry.

`controller_input` reports activity for presence and joining. It does not send movement to the game. The runtime samples physical controllers and publishes the frames; no lobby or game injects its own. See [Build a lobby](https://splitscreen.club/docs/lobbies#input-and-screen-ownership).

## Start opens your menu, Back leaves

Back/Select belongs to Splitscreen Club and always returns to the party, even from
inside your pause menu. Start opens and closes your game's own menu with its
settings and the controls. In managed play, leave out anything Splitscreen Club
already chose (players, game mode picked in the lobby).

Use press edges for every menu and action button, and require a release after
Start and Resume, so the press that started the game does not also act in it.
Hold-to-confirm (about a second) suits actions that end a round or reset
progress.

## Back must toggle once

Request the lobby with `request_overlay`. Use press/release edges and the shared one-second release gate. The same held press must not reopen the game after focus changes. Never issue Resume or `request_start` from a focus callback. When the runtime samples controllers itself it also sees that Back; it treats a press within 600 ms of your request as the same one, so the lobby does not close again.

## Check real devices

Test two different profiles, reversed connection order, unplugging one pad and reconnecting it. Then switch between games. Synthetic frames can check token matching, but they do not prove that a physical controller belongs to the right player on your machine.

# Drawing a Splitscreen Club face

Put the head where you want it. Pass its centre and radius, not a texture corner.

```lua
local Face = require("shared.face")
Face.drawFace(player, x, y, 24)
-- Optional: point left or rotate the entire head, including its hat.
Face.drawFace(player, x, y, 24, { facing = -1, rotation = angle })
```

The helper draws the circular skin, transparent artwork and a default face when
there is no drawing. It caches textures, follows profile changes and restores
the graphics state. `skin_color` stays separate from the artwork.

## Guest faces from the host

When joining a new guest, omit `avatar` in `join_party`. Splitscreen Club generates a
face with hair or a hat from its shared guest collection, chooses a skin tone,
and assigns an unused clothing color while the eight-color palette has room.
The resulting `avatar`, `skin_color`, and `color` arrive together in the player
snapshot. Render those fields with the normal face helper in any engine.

The appearance stays on that player through lobby and game transitions. Do not
regenerate it when the screen redraws or the player list changes. A saved avatar,
including an explicitly empty drawing, is preserved when supplied at join.

Rust integrations can also use
`gamenight_protocol::guest_face::avatar(&seed)` with a 16-byte seed to create the
same artwork. It returns an `Avatar`; call `.encode()` for the wire payload.
Skin remains a separate field so the entire head circle receives its color.

## Coordinates

The studio uses a 48 x 48 canvas. The head centre is **(24, 28)** and its radius
is **12** source pixels. Positive Y points down. The default expression looks
three-quarter right. Mirror the complete drawing around the head centre to look
left. Do not mirror around the canvas centre or crop to the painted bounds.
Hats and hair may extend outside the circle; leave that space transparent.

The wire payload remains `{v:1,w:48,h:48,px:[...]}`. Null pixels are transparent.
No skin is baked into it. Face details and accessories share this canvas, so
existing artwork is preserved without a destructive layer conversion.

For Rust, parse `gamenight_protocol::Avatar`, then call `head_layout()`.
Upload `to_rgba()` as a texture. To place the head at `(x,y)` with radius `R`:

- Scale = `R / layout.radius`.
- Texture origin = `layout.center` in source pixels.
- Translate to `(x,y)`; rotate and mirror around that origin.

Never centre the visible pixels: a tall hat would move the eyes down.
The SDK also supplies the historic origins for old 16/32 pixel drawings.
Use nearest-neighbour filtering for the pixel artwork. Draw the skin circle
at the game's output resolution.

## Choosing where to draw it

Godot's reusable `sdk/godot/addons/gamenight/face.gd` draws the same head layout.
See the [Godot lobby example](https://splitscreen.club/docs/lobbies#faces-and-names) for usage. The
Living Room shows each current player's name beside their face and repaints
when a profile changes.

Blast Party and Bubble Buddies draw the face on the character. Neon Trails
and Neon Siege use player portraits beside their names, preserving
the shape of the vehicle or trail. Stack Together uses its player cards.

Pass `{outline = player.color}` for a small clothing-coloured portrait rim.
The circle itself remains skin-coloured. This is optional and does not change
the head centre or radius. Live profile changes invalidate the image cache.

The store's 0–5 integration score counts essential playability checks and the
three independent profile checks: names, colours, and faces. Optional party
features do not affect that score. Development-only results remain unverified
until the evidence matches the platform and downloadable artifact.

# Phone screens

A game can give every seated player a screen of their own on their phone: a
hand of cards, a private vote, a god's view of the map. This is how Splitscreen Club
does asymmetric play. The TV stays the shared screen; the phone shows what only
that player may see. The wire format is in the
[protocol reference](https://splitscreen.club/docs/protocol#phone-screens); this page is how to build one.

## How it fits together

1. The game declares a folder with a web page in it.
2. Splitscreen Club serves that page to each signed-in phone at the table, on the
   LAN or through a hosted room.
3. The page and the game exchange small JSON messages. Splitscreen Club tags every
   message from a phone with the player who sent it; a phone cannot pretend
   to be someone else.

The page loads `/assets/companion.js`, which the host provides:

```js
const game = GameNight.connect((data) => render(data), (status) => showStatus(status));
game.send({ action: "roll" });
```

## Phones count as players

If your game is played on phones, say so in `gamenight.json`, so Splitscreen Club
counts phones and not just controllers:

```json
"players": { "min": 2, "max": 6, "best": 4, "play_with": "phone" }
```

Use `"controller_and_phone"` when every player needs both, and
`"controller_or_phone"` with `"min_phones": 1` when only some players are on a
phone, like one god among controller players. Two controllers and four phones
then fit a four-player phone game: people without a controller tap **Play on
this phone** in the Splitscreen Club app and get a seat of their own. Such a player
leaves the party about 10 seconds after their phone leaves the room. See
[controllers and phones](https://splitscreen.club/docs/protocol#controllers-and-phones).

Phones join late all the time: someone's battery died, someone walked in.
Nobody is too late. Seat everyone you were given in `prepare`, play the ones
without a phone with a bot, and hand the seat back the moment
`companion_presence` says their phone connected. With `instant_join: true`, a
new phone-only player also arrives mid-round in `party_updated`; otherwise on
the next round.

## In Godot

Keep the page in a folder of your project, such as `res://phone`, and declare
it once from `_ready()`:

```gdscript
func _ready():
    GameNight.companion_presence.connect(_on_phone)
    GameNight.companion_message.connect(_on_phone_message)
    GameNight.declare_companion_folder("res://phone", "index.html")
```

The host serves pages from a real directory, and an exported game has none:
`declare_companion_folder` copies the folder to `user://` and declares that
copy. It re-declares after every reconnect. Two export settings decide whether
the files are there at all:

- Add the folder to the export preset's include filter
  (`include_filter="phone/*"`), or HTML, JavaScript and CSS files are left out.
- Set images and fonts in that folder to the **Keep File** importer
  (`importer="keep"` in their `.import` files). Otherwise Godot exports only
  its own imported copy and the page loses them. The helper warns about files
  that were imported instead of kept.

Test the exported game, not only the editor project: these settings only show
up there.

`GameNight.send_companion_message(data, player_id)` reaches one phone, or every
phone when `player_id` is empty. Other engines send the same
`declare_companion` and `companion_message` messages; see the
[protocol reference](https://splitscreen.club/docs/protocol#phone-screens).

## In Unity

Keep the page under `Assets/StreamingAssets`, which stays a real folder in a
desktop build, and declare it when the connection opens:

```csharp
GameNight.Client.Connected += () => GameNight.DeclarePhoneScreen("phone");
GameNight.Client.CompanionPresence += (playerId, connected) => { if (connected) SendView(playerId); };
GameNight.Client.CompanionMessage += (playerId, data) => OnTap(playerId, data);
```

`GameNight.Client.SendCompanionMessage(data, playerId)` answers one phone.
The [Unity guide](https://splitscreen.club/docs/unity#phone-screens) has the Orb Rush example.

## In LÖVE

The shared runner declares the page and routes messages when a mode sets
`phone`. A `.love` file is a zip, so the runner copies the folder to the save
directory first and warns when it would not fit a hosted room:

```lua
M.phone = {
    folder = "games/cards_phone",
    message = function(state, player, data, send)
        -- a tap from `player`; answer with send(view, player)
    end,
    presence = function(state, player, connected, send)
        if connected then send(view_for(state, player), player) end
    end,
}
```

## Keep the game in charge

The pattern that worked in Hexstead:

- **The game decides, the phone draws.** After every change, send each player
  their whole view: their hand, what they may do now, whose turn it is. The
  page renders that and sends taps back. Never keep game rules in the page.
- **Send the view again on connect.** Phones reload, sleep and reconnect. On
  `companion_presence` with `connected = true`, send that player their current
  view. Count presence per player: one person can open the page twice.
- **Answer bad moves.** Phone messages are untrusted input. Check every action
  against the rules and send an error back for the page to show.
- **Don't stall the table.** A player without their phone open should not
  block the others. Give them a grace period, then let a bot take the turn.
- **Show the phone player's choices on the TV.** Highlight the places or cards
  the current phone player can pick, so the rest of the table can follow along.
  Private information stays on the phone; the TV shows shared state.

## Fit a hosted room

Hosted rooms forward the page to phones that are not on the PC's network. The
bundle must fit:

| Limit | Value |
| --- | --- |
| Files | at most 128 |
| Each file | at most 512 KiB once base64-encoded (about 384 KB raw) |
| Whole bundle | at most 2 MiB base64-encoded (about 1.5 MB raw) |
| File types | HTML, JavaScript, CSS, JSON, SVG, PNG, JPEG, WebP and WOFF2 |

Use WOFF2 for fonts, not TTF or OTF, and subset them to the characters you use.
Use relative paths only. The page runs in a browser sandbox: no cookies, local
storage, external scripts, forms or navigation of the parent app.
`declare_companion_folder` warns when a file or the folder would not fit.

Keep messages under 16 KB. Send the view, not the history.

## Native phone apps

When the phone side is a whole game of its own, such as a 3D view, declare a
native Android app instead of, or next to, a page:

```gdscript
GameNight.declare_companion(apk_folder, "", {
    "name": "The Voice and the Will",
    "android": "io.ontola.godgame",
    "download": "voice-and-will.apk",
})
```

The Splitscreen Club app installs the APK from the PC and opens it. The app then
connects to the game by its own means, for example LAN discovery. Hosted rooms
do not relay that connection, so a native app needs the phone on the same
network as the PC. Ship the APK inside the game's package next to the
executable, and give both the same version, because the game and the app must
speak the same protocol. iOS apps are only possible through the App Store.

Two things that bit us: on macOS, binding a socket to `*` listens on IPv6
only, so bind `0.0.0.0`; and a game with mouse capture needs a way to the
"join as phone" option from a controller.

# Performance

A Splitscreen Club PC is often a living-room machine, not a gaming rig, and it runs
the lobby next to your game. This page collects what our own games learned
about staying smooth there. Numbers come from those games; they are examples,
not guarantees.

## Pick the renderer for the weakest machine

In Godot, `gl_compatibility` runs on the most hardware and is what Ballkickers,
Spellstorm, Downhill Rush and Bombing Bugs use. Forward+ looks better but needs
a capable GPU; choose it on purpose and measure it on a modest one. A game
that also runs on phones can develop on the Mobile renderer, so every day of
development tests the renderer players will get.

The compatibility renderer has low per-object light limits. Raise
`rendering/limits/opengl/max_lights_per_object` and
`max_renderable_lights` when you need more, and split large floors into
chunks so each chunk only receives the lights near it.

## Load everything before Ready

Prepare happens while the game is hidden. After `ready`, the Godot SDK
throttles a hidden game to 10 frames a second so it does not slow the lobby,
so anything still loading after Ready loads slowly. Do the heavy work first:

- Load levels, meshes and sounds in Prepare.
- **Compile shaders before Ready.** Draw every material variant once, for a
  few frames, somewhere the player won't see it, and enable Godot's shader
  cache. Otherwise the first explosion stutters while it compiles.
- Report progress with `notify_progress` when loading takes more than a
  moment, and stay responsive: keep handling roster changes and Dispose while
  you load. For very long loads, report a stage at least every five seconds.
- A minimized window never draws. Don't wait for `frame_post_draw` before
  Ready; see [Godot](https://splitscreen.club/docs/godot#screen-ownership).

## Smooth motion on 120 Hz TVs

When physics runs at 60 ticks and the screen at 120 Hz, moving characters
judder or appear twice. Turn on physics interpolation
(`physics/common/physics_interpolation`), and make the camera follow the
interpolated positions rather than the raw physics ones.

## Keep heavy work off the frame

- **Generate in the background.** Build terrain or level chunks on a
  low-priority thread and add at most one finished chunk per frame. Downhill
  Rush builds its mountain in 60 m chunks while you ride; a large shared
  worker pool starved the engine in another game.
- **Time-slice expensive work.** Spend a fixed budget per frame (a few
  milliseconds) and continue next frame.
- **Cap catch-up.** If a fixed-step simulation falls behind, run at most a few
  steps per frame instead of spiralling.
- **Debounce rebuilds.** Rebuild meshes a few times a second at most, not on
  every change.
- **Batch input-driven work.** High-rate input (touch, mouse) can deliver
  events faster than frames; accumulate and apply once per frame.

## Draw less

- In split-screen the bottleneck is usually CPU draw submission, not the GPU.
  Every extra view draws the scene again: narrow the camera, cut shadow
  cascades and drop optional effects per view.
- Merge static geometry by material. Ballkickers went from about 555 to 260
  draw calls this way.
- Use MultiMesh for crowds, grass and particles, and leave their shadows off.
- Pool effects and cap them: a fixed number of explosions, lights and
  shadow-casting lights at once.
- Keep expensive features (global illumination, screen-space reflections)
  optional, and measure what each one costs before turning it on by default.
- Offer quality presets that change render scale and keep the HUD at native
  resolution.

## Hidden and paused cost nothing

While warming or paused, a game shares the PC with the lobby. Stop
simulation, disable extra viewports, cap the frame rate and mute audio. Use
the game clock for effects and tweens too, so smoke and sound freeze with the
game. The Godot `GameNightScreen` helper does the window, frame rate and master
bus; the simulation is yours.

## Measure

- **Build a repeatable benchmark**: a fixed seed, a fixed camera, a warm-up of
  a few seconds, vsync off, and a way to turn single features off to see what
  they cost. Compare against the same scene every time.
- **Measure before optimising.** One game went from 2.5 to 60 frames a second
  late in a match by caching a single repeated lookup; the profiler found it,
  guessing would not have.
- **Check the result stays the same.** When you speed up generation, compare a
  checksum of the output before and after.
- **Measure on modest hardware.** A laptop with integrated graphics is a fair
  stand-in for a living-room PC. Numbers from a fast desktop say little.
- The SDKs report frame times, slow frames and the machine's CPU, GPU and
  memory to Splitscreen Club while your game runs. See
  [session diagnostics](https://splitscreen.club/docs/protocol#session-diagnostics). A Godot game that
  overrides the SDK's message handling must still let it see Prepare, Start and
  Pause, or these reports stop.

Headless runs (`--headless`) don't render, so they say nothing about frame
rate. Use them for logic, and real windows for performance.

# Game contract verification

The wire contract is `docs/protocol.md`. Executable release requirements live in
`contract/requirements.json`. Neither a catalog integration label nor a protocol
handshake is proof of the complete implementation.

## One matrix, including missing integrations

`scripts/game-contract.py` discovers **every** `catalog/games/*.json` entry. Each
feature gets `passed`, `failed`, `untested`, or (only for optional requirements)
`not_applicable`. Missing runners stay visible as `untested`; they are never omitted.
Packaged `.love` games are discovered from the package directory, not a second
hardcoded certification list. A package with no catalog entry or an empty pack fails.
SpaceRacer has a separate native runner. CI downloads the exact catalog ZIP,
checks its SHA-256, checks out the matching probe source at its fixed release commit,
and runs the packaged executable against its synthetic-host integration test.

Each run emits `matrix.json`, `matrix.md`, raw certifier JSON, and command logs.
Evidence is tied to the source commit, operating system and SHA-256 of the tested
package. Logs have their own hashes. Dirty worktrees are marked and cannot provide
release evidence. Never reuse an output directory from an earlier run.

The current automatic runners verify, per packaged LÖVE game:

- protocol lifecycle against a real embedded daemon;
- rendering a real frame from the package;
- authenticated prepare with sparse seats, followed by process exit on host disconnect.

Protocol subchecks are included individually. Skipped subchecks remain untested.
The protocol pause check only observes host state. It does **not** prove simulation
or audio paused. First-frame rendering does **not** prove prewarming or correct
player artwork. The instrumented `scripts/test-love-integration.py` runner also observes live
names, colours and avatar draw calls, synthetic host controller ownership,
hidden/silent preload, gameplay start, frozen simulation while paused, resume,
Back press/release debounce through the real event handler, and native process
switching/cleanup. Volley names are checked on its winning-side score screens,
where the game actually displays them. Its feature results can fail independently.
Physical controller ownership still requires hardware testing; synthetic frames
and roster assertions are not proof of hardware behavior.
For SpaceRacer, the packaged native probe covers protocol connection, start,
pause/resume, synthetic controller ownership, host disconnect, names and avatar
updates. Start opens the in-game pause menu; Back requests the host lobby. A separate headless test changes skin and clothing colours during play
and checks that only the matching player's face layer is rebuilt. It explicitly
disables extra AI racers so the probe observes only its two seated players. Another runs
an AI race through finish, then checks that the game starts a fresh race in the
same process and session. The optional
`--spaceracer-window-probe` runs the same pinned test
with a real window to check hidden and silent preparation, then captures and
inspects a gameplay frame from the packaged executable. The pinned probe also
verifies that live settings take effect on the next race. Use the window probe on a
Vulkan-capable Windows host. GitHub's hosted Windows runner lacks that GPU
support and stalls during renderer warmup, so CI leaves this check untested.
The hosted matrix does not verify a rendered SpaceRacer frame or physical pads;
the colour test checks the face layer's live data, not sampled display pixels.
Cross-game switching remains untested. Back/Select is
handled globally by the lobby, so the synthetic native host does not certify
that input path. A passing game-specific CI run is not blanket certification.

## Running it

From the repository (Python 3.10+):

```sh
python scripts/package-love-party.py --output dist/party
cargo build --locked -p gamenight-certify
python scripts/game-contract.py --output dist/contract --pack dist/party \
  --love /path/to/lovec --certifier target/debug/gamenight-certify
python scripts/game-contract.py --candidate-gate --output dist/contract --pack dist/party
```

On Windows, use `.exe` for the certifier. Inventory-only runs need no game runtime:
`python scripts/game-contract.py --output dist/inventory`.

`gamenight-certify GAME --report report.json -- COMMAND ...` exports protocol-only
JSON, including failures. It no longer calls an automated-only pass “party-ready”.
Manual questions are explicitly untested in that report, including CI runs.

## CI and publication

The LÖVE workflow runs on every main push and PR, including protocol, SDK, host,
catalog and test changes. It uploads Windows evidence and puts the matrix in the
Actions summary. A Linux job then verifies the downloaded Windows evidence and
package hashes with the candidate gate, catching path or packaging differences
before the installer finishes. The main workflow tests the gate and publishes the full catalog
inventory. The Linux render smoke test is separate; a Windows pass is never reused
as Linux or macOS proof. Windows CI installs checksum-pinned Mesa beside its test
runtime because hosted runners expose only OpenGL 1.1. OpenAL uses its null output
device in CI; source playback and muting are observed, not speaker audibility.
Neither test driver is shipped in the installer. The synthetic host drains game
replies, as the production daemon does, and kills its own process tree on timeout
while retaining failure logs.

The Windows publication workflow calls the same LÖVE workflow at the same revision,
downloads that run's packages and evidence, and runs the strict gate **before**
creating the release draft. PR builds may differ from the published downloads, but still require all mandatory
and claimed checks to pass. Publication fails on any missing game, required untested
feature, failed mandatory/claimed check, stale commit, wrong platform, changed requirements, changed
package, or missing/modified evidence. There is no override for a catalog label.

The matrix covers the whole catalog. The Windows installer release gate covers
every bundled `.love` catalog game and requires an exact package match. Native
games are downloaded separately; their artifact-specific probe results remain
in the matrix but do not become installer-bundle requirements. The lobby
(host) and SDK example have explicit roles in `game-policies.json`; they are not
game downloads. A macOS-only download is not certified by a Windows run. These
rows remain untested, with no Windows rating credit. A new bundled Windows game,
missing bundle package, or extra unverified bundle package blocks publication.

## Extending coverage

Add a narrowly scoped runner that executes the actual packaged game. Record a
feature as passed only after it observes that feature, retaining logs/artifacts.
The existing `run_games` adapter handles LÖVE. SpaceRacer's pinned native
adapter runs its released ZIP; other native/Godot games still need their own
artifact runner. Unavailable sources stay untested until their tested package
is supplied. Volley Trouble is part of the public shared LÖVE package.
Use a distinct feature when a unit test covers only part of a hardware behavior;
do not relabel an entire shared test suite as proof of every game feature.

When a requirement changes, change `requirements.json`. Old reports then fail the
gate automatically. Add a regression to `scripts/test-game-contract.py` for every
new way an incomplete integration could accidentally be accepted.

Contract v2 separates player-name sync, skin/clothing colour sync, and drawn face/hat sync. Previous combined appearance evidence does not satisfy any of these independently.

## Grouped ratings (contract v4)

The numeric catalog score runs from 0 to 5. It counts the eleven essential checks
and three independent personalisation checks: names, colours and faces. Each
verified check has equal weight. Party extras do not affect the score.

The playability label is separate: all essentials must pass for Ready to play.
A failing essential check means Integration issues. Partial or missing proof
remains visible. Development, dirty-worktree or unmatched-build results do not
increase the verified score or playability label.

Start, resume and switching are distinct from a handshake. Old aggregate lifecycle
or appearance evidence cannot satisfy granular checks. The source of truth for
groups and counts is `contract/requirements.json`.

`contract/game-policies.json` records first-party ownership and explicit feature
claims. First-party games require personalisation as well as essentials for
release. Claiming an optional feature also makes its passing proof mandatory.
Unclaimed optional failures remain visible but do not block compatibility.
Changes to requirements or policy invalidate release reports. The registry is
explicit: ownership is not guessed from a developer's display name.

## Continuous play

`gameplay.continuous` is essential. Round endings do not end a host session.
Games show their results briefly (normally three seconds) and start a fresh round
in the same session with the current roster and settings. Pause freezes both the
simulation and this results countdown. `finished` is an optional round notification;
it must not hide the window, request the lobby or advance the playlist.
Back/Select opens the lobby and pauses; Resume continues the same round or results.
Play next explicitly switches games. Skip only replaces the upcoming game.
The host retains the preloaded next session across round notifications, even with
no seated human players. Test multiple round endings and a pause during results.

## CI builds versus publication

Normal pull-request and main-branch CI uses `--candidate-gate` to verify the
newly built packages. It checks the commit, platform, source cleanliness,
catalog coverage, required features, artifact hashes and evidence hashes.
It allows those new packages to differ from the catalog's older published
version. A passing candidate is not release approval.

Publication still uses `--gate`, including in the Windows installer release
job. That additionally requires the tested artifact hashes to match the
catalog downloads. Update the release catalog and verify the corresponding
packages before publication. Never substitute `--candidate-gate` in a release
job.

## Your game's own tests

The contract checks cover the protocol. Your game also needs tests of its own
that a person would otherwise do by hand. What worked in our games:

- **A fake host.** A small script plays Splitscreen Club: it starts the game with
  `GAMENIGHT=1`, `GAMENIGHT_ADDR`, `GAMENIGHT_GAME_ID` and `GAMENIGHT_TOKEN`,
  answers `hello`, sends Prepare, waits for Ready, sends Start, controller
  frames, Pause, Resume and Dispose, and checks what the game did. The
  [Godot template](https://splitscreen.club/docs/playbook) includes one in `tests/lifecycle.py`.
  Godot games also get a reusable one with the SDK:
  `addons/gamenight/fake_host.py`, Python standard library only and kept
  current by `sync.py --all`. It already does the next three points.

  ```python
  import sys; sys.path.insert(0, "addons/gamenight")
  from fake_host import FakeHost, frame, BUTTON_A

  with FakeHost("godot", game_id="my-game", path=".") as host:
      host.welcome()
      host.prepare([host.local_seat(0, "ada")], [{"id": "ada", "name": "Ada"}])
      host.start()
      host.hold(frame(BUTTON_A), 0.1)
      host.saw("jump Ada")   # a line your game printed with GAME_TRACE=1
  ```

  Pass `pack=` to run the exported game, or `command=` to start it another
  way (a packaged `.exe`, a launcher, a window). `host.disconnect()` plays a
  Splitscreen Club that goes away; `host.exit_code()` then checks the game quit
  cleanly. `HostClient` connects to a real Splitscreen Club as the overlay does.
- **Install Godot the same way everywhere.** In GitHub Actions use
  `ontola/gamepad-party/.github/actions/setup-godot@main` with your project's
  `version`; it verifies the download's sha256, works on Linux and Windows,
  and with `export-templates` installs the templates an export needs.
- **Keep sending frames.** Input older than 250 ms counts as released, so a
  test that holds a button must repeat the frame, about every 50 ms.
- **Listen on a free port.** Bind port 0 and pass the port in
  `GAMENIGHT_ADDR`, so a test never meets a real Splitscreen Club on the same machine
  and tests can run side by side.
- **Write the game's output to a file on Windows.** Godot on Windows writes
  stdout synchronously; an unread pipe blocks the game before it connects.
- **Trace what players would notice.** Print a line per event behind an
  environment variable (`GAME_TRACE=1`), and wait for those lines in the
  test. Pause state and menus are not visible over the protocol.
- **Run the exported game too.** Run the same test against the exported
  build in CI. Exports leave out excluded folders and non-resource files,
  which only shows there.
- **Bots play whole rounds.** Seeded bots playing a full match catch broken
  rules and stuck rounds. Count every mechanic and fail when one never
  happened.

Then test with real controllers and real people. Use the
[desktop checklist](https://github.com/ontola/gamepad-party/blob/main/docs/desktop-integration-checklist.md): two profiles, reversed
connection order, a pad unplugged and plugged back in, repeated Back and
Resume, and several game switches. Tuning against bots alone misses how the
controls feel.

# Publish a game

Reference for steps 4 to 6 of [Share your game](https://splitscreen.club/docs/share): builds, CI, the API, the store page, pricing and review.

Use the [developer portal](https://splitscreen.club/developers) to add your game, upload builds, manage versions, edit your listing and create API keys. Splitscreen Club hosts accepted packages. You keep your own build tools, CI and source repository.

## Where your game's data lives

Keep two things in your repository and let Splitscreen Club production hold the rest:

- `gamenight.json` holds the facts about the game: id, title, tagline, developer, players, round length, tags, emoji, colour, requirements and links. Start it with `"$schema": "https://raw.githubusercontent.com/ontola/gamepad-party/main/catalog/schema.json"` so editors check it.
- `assets/gamenight/` holds the store artwork: `cover.png`, `icon.png`, `gameplay.png` and an optional `screenshots/` folder.
- `preview.json` is the recipe for the five-second gameplay clip. `gamenight-publish.py clip` renders the clip from it and `--publish` uploads it; the clip itself stays out of the repository (see the [store clip guide](https://splitscreen.club/docs/store-clip#keep-the-recipe-not-the-video)).

Builds, the store page, ownership and visibility live in production. `gamenight-publish.py push` (or the GitHub Action) sends builds and `gamenight-publish.py store` sends `gamenight.json` and the media. Do not put store text or media anywhere else. Hosts pick up a stable release from the hosted catalog; a new game needs no entry in the Splitscreen Club repository.

## Prepare a release

For a new game, sign in to the [developer portal](https://splitscreen.club/developers) and choose **Add your game**. Free games can upload builds right away; ask for integration help from the game's **Help** tab. Existing catalog games need Splitscreen Club to register the correct owner once; matching a game name does not establish ownership.

1. Choose your game, then **Builds**.
2. Enter a version and platform. Upload a ZIP containing your exported executable and assets, or a standalone executable. Alternatively, import a direct HTTPS URL from S3 or another host. URL imports require the filename; signed URLs must remain valid throughout the import and must not redirect.
3. Set the executable path relative to the ZIP root, such as `Game.exe` or `Game.app/Contents/MacOS/Game`. For a bare file, use its filename. Add release notes.
4. After package verification, choose **Use as preview** and [playtest](https://splitscreen.club/docs/publishing#playtests) the exact build at real tables, then **Send for review** in the **Review** tab. Once approved, choose **Publish to players**.

Packages may be at most 512 MiB, with at most 2 GiB extracted from a ZIP. Use a ZIP for executables with DLLs, PCK files or other assets. LÖVE packages need a platform runtime registered by Splitscreen Club. Splitscreen Club copies URL imports into its own storage; gamers never depend on an expiring source URL.

A version identifies immutable bytes for one game and platform. Retrying the same version and checksum returns the same build. Changed bytes require a new version. Interrupted uploads can be retried. Choosing an older ready build for stable rolls back that platform without uploading again.

Previews are private to the owner, their game-scoped keys and tables with a tester seated. Public releases remain downloadable after rollback so cached catalogs still work. The portal shows upload failures and publishing activity.

## Playtests

Play your preview with real people before it reaches the store. In the portal, open your game's **Playtest** tab and create an invite link. Anyone who opens it and signs in with a Splitscreen Club account becomes a tester; you are always one yourself.

When you or a tester join a Splitscreen Club table with your phone, the host downloads the current preview build and shows it in the lobby under its own title, with "Test build" in its description. Everyone at that table can play it, testers or not. After the game, every phone at the table asks how it went: a thumbs up or down and an optional comment. Answers appear in the **Playtest** tab with the version and the player's name.

Every new preview, from CI or by hand, becomes the playtest build. A new invite link stops the old one from working; testers who joined stay until you remove them. A playtest build stays on a host's shelf until Splitscreen Club restarts, even after the tester leaves. When tables like it, send the build for review.

## Connect GitHub Actions

In **API keys**, create a named key for your game. Every key can upload builds and publish stable releases for that game, so keep it secret and revoke it when you no longer need it. Copy the secret immediately: it is shown once. Store it as `GAMENIGHT_API_TOKEN` in repository Actions secrets, or an environment secret when using a protected environment.

Add this step after packaging and testing:

```yaml
- name: Upload Splitscreen Club preview
  id: gamenight
  uses: ontola/gamepad-party@main
  with:
    token: ${{ secrets.GAMENIGHT_API_TOKEN }}
    game: my-game
    file: dist/my-game-windows.zip
    platform: windows
    entrypoint: Game.exe
    version: ${{ github.sha }}
    channel: preview
```

Pin the action to a reviewed commit SHA for reproducible CI. It calculates the checksum, streams the upload, promotes the preview and adds a portal link to the Actions summary. Outputs are `build-id`, `sha256` and `portal-url`.

Use `channel: stable` for automated public releases. That requires a publish-scoped key and Splitscreen Club distribution approval. Never provide secrets to pull-request code from untrusted forks. Build/test PRs without publishing; publish from trusted main or version-tag workflows.

Keys are restricted to one game. The portal lists expiry and last use. Create a replacement, update your CI secret, then revoke the old key. Revocation is immediate, including before an upload completes. Keys expire after 90 days by default; choose 30 days or up to one year. CI keys cannot create more keys or edit account details.

Games that build in one workflow and publish from a second `workflow_run` workflow can call the reusable workflow instead of copying these steps. It only uploads successful `main` or `v*` builds from your own repository:

```yaml
on:
  workflow_run:
    workflows: [Build and release]
    types: [completed]
permissions:
  contents: read
  actions: read
jobs:
  upload:
    if: vars.GAMENIGHT_PUBLISH_ENABLED == 'true'
    uses: ontola/gamepad-party/.github/workflows/publish-game.yml@main
    secrets:
      GAMENIGHT_API_TOKEN: ${{ secrets.GAMENIGHT_API_TOKEN }}
    with:
      artifact: my-game-windows   # artifact uploaded by the build
      game: my-game
      file: my-game-windows.zip   # path inside that artifact
      entrypoint: Game.exe
```

Pass the named secret explicitly when calling across repository owners:
`secrets: inherit` does not reach a reusable workflow in another organization. The reusable job selects your `gamenight` environment, where you can store the key.

The shared first-party pack uses a `gamenight-<game-id>` GitHub environment per game, each holding its `GAMENIGHT_API_TOKEN`. Native repositories use a `gamenight` environment. Set the repository variable `GAMENIGHT_PUBLISH_ENABLED=true` after registering ownership and configuring secrets. These workflows upload previews; CI does not silently replace a public release.

### CI pitfalls we hit

- **Every preview needs a new version.** A version identifies immutable bytes,
  so a rebuilt commit cannot reuse `${{ github.sha }}`. Add the run:
  `ci-${{ github.sha }}-${{ github.run_id }}-${{ github.run_attempt }}`.
- **Pin what you run with your key.** Pin `ontola/gamepad-party` actions and
  reusable workflows to a reviewed commit, and check out a pinned copy of
  `scripts/gamenight-publish.py` for the store step. Keep both on the same
  commit, and update them together.
- **Pin and checksum your engine.** Download a fixed Godot version and check
  its SHA-256, in CI and in the export templates.
- **Test the exported build in CI.** Run your lifecycle test against the
  exported game, not only the editor project. Files under an excluded folder
  (such as `tests/`) and raw files outside the include filter are missing
  there, and the game only breaks in Splitscreen Club.
- **Agents often cannot push tags.** Trigger releases with a workflow input
  instead of a tag push.

## Other CI systems and local previews

[Download the Python uploader](https://splitscreen.club/developers/gamenight-publish.py). It requires Python 3.11 or later and no third-party packages. Set `GAMENIGHT_API_TOKEN` in your shell or CI secret environment, then:

```sh
python gamenight-publish.py push --game my-game --file dist/game.zip --platform windows --entrypoint Game.exe --version 1.2.0 --channel preview --changelog "New arenas"
```

Download and verify a native preview without publishing it:

```sh
python gamenight-publish.py preview --game my-game --output .local/preview
```

Point `GAMENIGHT_LIBRARY` at the printed `shelf.json` when running a development host. On Windows the local launcher accepts this file through `-Shelf`. Downloading does not execute the game; start it through Splitscreen Club and test the [lifecycle](https://splitscreen.club/docs/lifecycle). Runtime-based games use the registered LÖVE runtime alongside the `.love` file; the preview catalog includes the runtime checksum and entrypoint.

## Publishing API

Authenticate with `Authorization: Bearer YOUR_API_KEY`. Browser operations use the existing session and CSRF protection. Browser and CI requests use the same release service.

| Endpoint | Purpose |
| --- | --- |
| `POST /v1/developer/games/{game}/builds` | Create or recover an immutable build |
| `PUT /v1/developer/builds/{build}/content` | Stream and verify package bytes |
| `POST /v1/developer/builds/{build}/import` | Copy a direct HTTPS URL into Splitscreen Club |
| `GET /v1/developer/builds/{build}` | Read state, checksum, size and processing error |
| `POST /v1/developer/games/{game}/releases` | Promote a ready build to preview or stable |
| `GET /v1/developer/games/{game}/preview-catalog` | Get your private preview manifest |
| `GET /v1/game-catalog` | Get public game updates |

Create a build with:

```json
{
  "version": "1.2.0",
  "platform": "windows",
  "filename": "game.zip",
  "entrypoint": "Game.exe",
  "sha256": "YOUR_64_HEX_SHA256",
  "changelog": "New arenas"
}
```

The response contains `id` and `state`. Upload to the content endpoint, or import with `{"url":"https://your-storage.example/game.zip"}`. For imports the expected checksum is optional; Splitscreen Club always records the actual checksum. Promote with `{"build":"BUILD_ID","channel":"preview"}`. Build states are `awaiting_upload`, `uploading`, `ready` and `failed`; release results are `preview_ready` or `live`. Invalid input returns 422, immutable-version conflicts return 409, and invalid/revoked keys return 401. Retry network failures using the same version and package.

## Catalog updates

New desktop builds refresh the trusted HTTPS publishing catalog in the background at launch and every 15 minutes. Downloads are checksum-verified and extracted into separate version directories. The shipped catalog and last valid cached update keep offline play available. Updates download during play; existing shelf entries keep their launch path until the next Splitscreen Club launch. Restart Splitscreen Club to activate updates. Failed downloads leave the previous installed version available.

Store metadata and artifact hashes use the promoted release. Uploads do not inherit old certification. Package verification checks hashes, ZIP safety and the entrypoint; it does not execute uploaded code or certify gameplay. Test controllers, player joining/leaving, return to lobby and continuous rounds against the actual release.

The first public release requires distribution approval. Subsequent updates can use the same approved game and publish-scoped key. **Store page** edits update title, description, player counts and website without rebuilding the app. Choose **Free** or **Paid**. Selling opens to the first developers soon. You set a price from €0.99 to €100 including VAT and keep 85% after VAT. Splitscreen Club is the seller and handles checkout, VAT, receipts and refunds; your share goes to your Stripe account with every sale. Players buy once, and one owner unlocks the game for the whole couch. Refunds are automatic within 14 days for buyers who played less than 2 hours. Ask about it from the portal's **Earnings** page.

Private repository access, AI-assisted code processing and game distribution each need agreement. Sharing a repository does not grant permission to distribute the game. Listing is free.

## Required gameplay video

Before publishing to players, upload a **five-second gameplay video** on the
Store page and save. Use MP4 or WebM, up to 32 MiB. It appears first and loops
silently; reduced-motion and data-saving preferences keep playback manual.
Screenshots, cover art and YouTube links are optional extras. A YouTube link does
not replace the gameplay clip. Drafts and private preview builds need no media.

Splitscreen Club measures the uploaded file on the server. It accepts 4.9–5.1 seconds
for frame and container rounding, and rejects unreadable or longer videos.
A live game must keep a clip: use **Replace gameplay video**, then save.
Show real gameplay and check the loop on a phone. Follow the
[gameplay preview guide](https://splitscreen.club/docs/store-clip); duration validation does not
establish that the footage is good or representative.

### From the command line or CI

One command fills the store page with a publish key (the same key CI uses for
releases):

```sh
GAMENIGHT_API_TOKEN=gn_pub_... python3 gamenight-publish.py store
```

Run it in your game's folder. It reads `gamenight.json` (title, tagline,
developer, players, tags, round length, links) and uploads what it finds in
`assets/gamenight/`:

| File | Becomes |
| --- | --- |
| `preview.mp4` or `preview.webm` | the five-second gameplay clip (prefer `clip --publish` from a recipe) |
| `preview.jpg` | the clip's poster |
| `cover.png` | portrait cover |
| `icon.png` | square icon |
| `gameplay.png` | TV screenshot, and the gallery image when there is no `screenshots/` folder |
| `screenshots/*.png` | gallery images, in name order |

Use `--manifest`, `--media`, `--video`, `--cover` (and so on) or a repeated
`--image` for other paths. Rerunning with the same files reuses the uploads and
costs no media quota. Pricing is never changed from the command line.

The script uses two endpoints, which accept a publish key or an owner session:

1. `POST /v1/developer/games/{game}/uploads` with the raw file bytes. The response
   contains `url` and `kind`. Invalid video returns `422` with an explanation.
   Uploading the same bytes again returns the same `url`.
2. `PUT /v1/developer/games/{game}/store` with any of `title`, `tagline`,
   `players_min`, `players_max`, `tags`, `match_minutes`, `homepage`, `source`,
   `cover`, `icon`, `screenshot`, `video`, `poster` and `images` (up to 9 URLs).
   Fields you leave out stay as they are; an empty string removes artwork or a
   link. `video` replaces the gameplay clip and `images` replaces the gallery
   images; YouTube trailers added in the portal are kept. The response says
   whether `preview_ready` is true.

The portal editor uses `PUT /v1/developer/games/{game}` with the full listing,
pricing and a `media` array. `GET /v1/developer/games/{game}` includes
`media.preview_ready` and `media.required_duration`. A stable release returns
`422` if no verified gameplay clip is saved. Existing approved clips remain valid.

Send the usual CSRF header for cookie authentication. Pasting an external video
URL or setting `duration: 5` yourself does not verify it, and a clip uploaded for
another game cannot satisfy this game's requirement.


### Saved progress

If your game saves progress with `save_player_data`, describe it in `save-schema.json` next to `gamenight.json`: a JSON Schema with one object type in `$defs`, one property per top-level key. `store` sends it along (or run `gamenight-publish.py schema`) and writes `save-schema.lock.json`; commit both. Players' progress is then kept field by field and merges cleanly between their devices. When a later version renames or retypes a field, say so in the schema with `"x-gamenight-lenses": [{"from": "wins", "to": "victories", "op": "rename"}]` or `"x-gamenight-dropped": ["wins"]`, otherwise the upload is refused. Give a field with a new type a new name. Your game always gets back the same JSON it saved.

## Optional artwork

Use a portrait cover for the next-game display, a square icon for game spines and a gameplay screenshot for the TV. These are separate assets. If artwork is absent, the title remains readable; a random icon is not a substitute for a cover.

```json
{
  "id": "my-game",
  "title": "My Game",
  "cover": "art/cover.png",
  "icon": "art/icon.png",
  "screenshot": "art/gameplay.png"
}
```

This is a local shelf artwork example. Downloadable catalog packages use the manifest format in the [catalog guide](https://github.com/ontola/gamepad-party/blob/main/catalog/README.md), including platform download hashes and entrypoints.

## Review the exact build

Run the [integration checks](https://splitscreen.club/docs/testing) against the package players will download. Evidence from a different operating system or build does not count for this release. Missing checks remain untested.

The integration rating separates smooth play, player personalisation and optional extras. Faces are checked separately from colours and names. Staff review the build and distribution permission before publication; sending a message or submitting a build does not publish it automatically.

# Five-second gameplay previews

Every playable Splitscreen Club store entry needs an engaging five-second gameplay
montage. Its job is to show how much fun the game contains before someone scrolls
past. Technical validity alone is not acceptance.

Upload the clip on the developer portal's Store page before publishing. Use MP4
or WebM, up to 32 MiB. The server measures its length (4.9–5.1 seconds to allow
frame rounding). Screenshots and YouTube links are optional. Private preview
builds and drafts can be saved before the clip is ready.

## Plan the five seconds

Before recording, write a short shot list with the action, players, weapon/item,
setting or arena, and intended payoff for each cut. Use **4–6 quick cuts**, usually
about **0.6–1.3 seconds per shot**. Aim for four or more clearly different action
beats. Cut into action already starting and leave enough time to see its result.
Use straight cuts; transitions, logos and menus must not consume the five seconds.

Show as much meaningful variety as remains readable:

- **Weapons and abilities:** show several distinct attacks, tools or abilities
  when available. For an arsenal game, aim for at least three visibly different
  weapons; changing the gun without showing what it does does not count.
- **Players and characters:** show multiple identifiable players/characters,
  their interactions and multiplayer chaos. Use different colors or silhouettes;
  include different player counts or layouts when those are selling points.
- **Settings:** switch arenas, environments, modes or gameplay configurations
  where available. Aim for at least two visibly different settings.
- **Items and surprises:** show a pickup, power-up, throwable, hazard or another
  usable object affecting play when the game has them.
- **Signature mechanics:** include what makes this game distinctive—grappling,
  physics, destruction, racing, teamwork, scoring, transformations, etc.
- **Payoffs:** show impacts, escapes, explosions, goals or other satisfying
  outcomes. Open with an immediate hook and finish with a strong beat that loops
  cleanly back to the opening.

Adapt categories to the actual game. A sports game can show tackles, passes,
shots, saves and team sizes instead of weapons. Do not invent features to fill a
checklist. If a category does not exist, spend its time on another real mechanic.
Avoid repeated shots that all communicate the same thing.

## Make the action legible

Frame the relevant players and effects large enough to recognize in a store card
and on a phone. Mix close action with a useful wider shot; a distant whole-map view
with tiny characters is not a substitute for showing gameplay. Keep subjects in
frame through the payoff. Remove setup, countdowns, idle traversal, pauses and
empty aftermath. Do not simply take the first five seconds of a match or publish
one uninterrupted wide shot because it is easy to capture.

Watch the entire montage at its actual five-second speed, at desktop-card and
phone sizes. Inspect every cut: the viewer should immediately understand what is
new and see the action land. Shorten or replace dull shots, and lengthen confusing
ones. Do not accelerate gameplay to force too much into the time budget.

## Capture real gameplay

Use the listed release's simulation and renderer. Never use generated gameplay,
animated cover art or fabricated effects. Deterministic bots or staged starting
positions, legitimate loadouts and real input sequences are useful for getting
clear moments. Keep mechanics, damage, physics and effects faithful to the game.
Record any staging in the capture notes; do not present it as a live competitive
match. Work in a scratch copy without affecting active player sessions.

Retain a reproducible capture harness and edit decision list: source version/commit
and package hash, seed, staging, each source in/out frame, shot length, and what each
shot demonstrates. Record hashes for the encoded clip and its poster.

## Keep the recipe, not the video

The clip is built, not kept: put a `preview.json` recipe next to your
`gamenight.json` and commit that. Never commit the clip itself. When the game
looks better, run the recipe again. Every cut is a command from your own game
that writes numbered PNG frames into `{dir}` (a headless capture, a scripted
run with a fixed seed), followed by how many frames to use:

```json
{
  "render": "1920x1080",
  "env": {"MYGAME_NO_HUD": "1"},
  "cuts": [
    {"name": "arena", "note": "four players, first clash",
     "run": ["./mygame", "--capture", "{dir}", "--size", "{w}x{h}", "--seed", "3", "--frames", "{frames}"],
     "skip": 20, "frames": 60},
    {"name": "boss", "note": "the boss slam lands",
     "run": ["./mygame", "--capture", "{dir}", "--level", "boss", "--frames", "{frames}"],
     "frames": 90}
  ],
  "poster": {"cut": "boss", "frame": 40}
}
```

The cuts' `frames` add up to exactly 150. `{frames}` is `skip` plus `frames`,
and `{w}` and `{h}` are the render size. `cwd` (relative to the recipe) sets
where a command runs, and `env` (on the recipe or on one cut) adds environment
variables.

```sh
python3 gamenight-publish.py clip                        # render, cut, encode, check
python3 gamenight-publish.py clip --render-size 480x270  # a quick draft
python3 gamenight-publish.py clip --only boss            # redo one cut
GAMENIGHT_API_TOKEN=gn_pub_... python3 gamenight-publish.py clip --reuse --publish
```

`clip` works in `build/preview/` (keep it out of git). It encodes to the
delivery format below and runs the checks below. It writes `provenance.json`
with the commit, the recipe hash, every cut and the hashes of the clip and its
poster. Nothing leaves your machine until you add `--publish`. That uploads the
clip and the poster to the store's media storage through the API and makes them
the store page's gameplay video, using the publishing key of your game. Render
on a real GPU; a software renderer is fine for drafts only. A CI job that runs
`gamenight-publish.py store` must not have a `preview.mp4` lying around to
upload, or it puts the old clip back.

## Delivery and acceptance

- Exactly **5 seconds / 150 frames**, **960×540**, **30 FPS**.
- Silent H.264 MP4: `libx264`, CRF 24, preset slow, YUV420P, limited video range,
  `+faststart`. Use an actual gameplay frame as the JPEG poster.
- Decode the full clip successfully; verify frame count, duration, dimensions and
  at least 100 distinct frame hashes. These checks do not replace visual review.
- Publish to a new immutable versioned path; retain `SHA256SUMS.txt` and provenance.
- Add a video media item with `preview: true`, `duration: 5` and an HTTPS poster.
  Retain useful existing screenshots. The clip must lead the game's media.
- Verify MP4 MIME type, HTTP byte ranges, muted looping playback in the catalog
  card and details, and manual playback with reduced motion. Check desktop and
  phone. Closing or changing games must unload the previous video.
- Run the catalog preview-coverage/model tests and cloud tests before deploying.

**Review gate:** Does the clip visibly cover different players, weapons/abilities,
settings, items and signature mechanics wherever the game supports them? Are there
several quick, readable cuts with satisfying outcomes? Would someone understand
why this game is fun without reading its description? If not, revise the edit.

The hosted service's `deploy/cloud/previews/README.md` contains engine-specific
capture commands and publishing steps. Its `PREVIEWS.json` records shipped clips.

# Game settings

Splitscreen Club can display a game's settings in the lobby and phone interface. Games
must declare their options and implement the changes. Having the protocol or SDK
in a project does not expose its gameplay rules automatically.

## Available controls

The shared LÖVE pack and the Mineclonia catalog game declare these settings. These are source capabilities;
installed releases need newly built packages before the controls appear.

| Game | Controls | When they apply |
| --- | --- | --- |
| Neon Trails | Speed 50–175%; round pause 0.5–5 seconds | Next round |
| Blast Party | Crate density 20–85%; crate pickup chance 0–60%; bomb fuse 1–4 seconds | Next round |
| Neon Siege | Relaxed, standard or intense enemy pressure; gravity 0–175% | Next run, not the next wave |
| Volley Trouble | Court; exploding ball; rotating rules; 1–21 points to win | Next match, not the next point |
| Stack Together | 4–40 rows to win; falling speed 50–175% | Next round |
| Bubble Buddies | 2–12 shared hearts; 1–10 waves; 30–150 seconds per wave | Next run |
| Mineclonia | Gravity, jump, movement speed, air steering, sneaking speed, clock time, day/night speed and bounce pads; [ranges and effects](https://github.com/ontola/gamenight-mineclonia#reversible-live-changes) | Live, after the world acknowledges the change |

The default values preserve the existing games. Blast Party's pickup chance
controls drops from crates; its two opening prizes remain. Neon Siege's enemy
count remains capped. Disabling gravity also removes the black hole.

## Godot game controls

These independent game repositories use the same typed contract. Source builds
have been tested against the real daemon, including setting changes and Undo.

| Game | Controls | Timing and reference |
| --- | --- | --- |
| SpaceRacer | Laps, difficulty, world, seed, graphics; boost cost and duration, energy regeneration, crash recovery, weapon pickups | Boost, energy and recovery controls work during a race. Track rules and pickup stations wait for the next race. [All ranges](https://github.com/joepio/spaceracer/blob/main/docs/gamenight-settings.md) |
| Growing Guns | Rounds to win, modifier chance, card choice time; gravity, bullet drop, body shot damage, random pickup rate | Match goal waits for a new match; physics and combat wait for the next round; card time affects the next choice. [All ranges](https://github.com/ontola/growing-guns/blob/main/docs/gamenight-settings.md) |
| Ballkickers | Match length, matchup; running speed, shot speed, rolling friction, goalkeeper movement, passive super charge, super shots | Match structure waits for a new match. Movement and ball physics are live; shot changes affect the next shot. [All ranges](https://github.com/joepio/ballkickers/blob/main/docs/gamenight-settings.md) |
| Frog Fighter | Mode, arena, lives; running speed, jump impulse, frog gravity, damage, supply interval, bot reaction delay | Mode, arena and lives wait for a new round. Physics are live; jumps, hits, supplies and aiming use the new value on their next event. [All ranges](https://github.com/joepio/frog-fighter/blob/main/docs/gamenight-settings.md) |

Defaults preserve the existing games. Percentages are relative to those defaults,
not raw engine units. Growing Guns multiplies its round modifiers and replicates

Run each game's headless settings suite in its own repository. For the complete

~~~sh
export GODOT=/path/to/godot
export GAMENIGHT_GODOT_SOURCES='{"spaceracer":"/path/to/spaceracer","growing-guns":"/path/to/growing-guns","ballkickers":"/path/to/ballkickers","frog-fighter":"/path/to/frog-fighter"}'
python3 scripts/test-godot-settings.py
~~~

This launches isolated game processes and a daemon without using physical
controllers. It verifies the declared controls, received values and Undo.
The games' simulation tests separately check gameplay effects and apply timing.
Source checks do not certify older downloadable binaries or physical input.

Ion Rush still has source declarations for laps and graphics quality in a local
game import; it is not a catalog release. The lobby and retired demo games are
not playable catalog entries and are excluded.

## Declare and apply

The wire protocol accepts `toggle`, `choice` and integer `number` settings. Labels
must include units and say when a change takes effect. For fractional durations,
use readable choices such as `"1.4 s"` and convert inside the game. Unknown keys, wrong types and
out-of-range values must leave the last valid value intact.

In a shared LÖVE game:

```lua
local Game = { id = "my-game" }
require("shared.settings").bind(Game, {
    { key = "speed", label = "Speed % (next round)",
      kind = "number", default = 100, min = 50, max = 175 },
    { key = "pickups", label = "Pickups (next round)",
      kind = "toggle", default = true },
})

function Game.new(players)
    return { players = players, settings = Game.preferences() }
end

function Game.update(state, dt, inputs)
    local speed = 200 * state.settings.speed / 100
    -- Use speed in your movement simulation.
end
return Game
```

The helper provides `settings`, `setting(key, value)` and `preferences()`. The
shared runner declares the specs after `welcome` and forwards `setting_changed`.
`preferences()` returns a copy. A running round keeps its copy until the game
creates the next round. Call it in an internal reset too if the game starts
rounds without returning to the runner. Do not mutate active state just to make
a slider look responsive.

A declaration makes controls available once the game connects, usually during
preloading. It is not static catalog metadata. Splitscreen Club remembers party choices
and sends them back when a game declares settings again. It does not yet have a
separate acknowledgement for "applied in gameplay". A saved value may therefore
be pending the next round. See the [protocol reference](https://splitscreen.club/docs/protocol).

A game's own menu can change its settings too: send `set_setting` for one of
your keys (Godot `GameNight.set_setting(key, value)`, Rust
`GameNight::set_setting`). Splitscreen Club validates it, stores it as the party's
choice and echoes `setting_changed`, so the app and the assistant show the
value players picked in the game.

Mineclonia maps its integer percentages onto the existing world physics factors.
It applies them on a worker, coalesces repeated edits and retries mailbox
conflicts. Mod installation waits for an in-flight settings update. These two
controls do not install arbitrary mods. Edits made directly through the separate
world bridge are not automatically republished into Splitscreen Club's setting values.

## Per-player settings

Some choices belong to one player, not the party: their character, their stick
sensitivity, inverted look. Declare those with `"scope": "player"` in the same
`declare_settings` call. Kinds, ranges and validation are the same.

```gdscript
GameNight.declare_settings([
    {key = "rounds", label = "Rounds to win", kind = "number",
     default = 3, min = 1, max = 9},
    {key = "sensitivity", label = "Stick sensitivity %", kind = "number",
     default = 100, min = 40, max = 250, scope = "player"},
    {key = "character", label = "Character", kind = "choice",
     default = "frog", options = ["frog", "cat", "robot"], scope = "player"},
])
GameNight.player_settings_changed.connect(func(player_id, values):
    aim_speed[player_id] = values["sensitivity"] / 100.0)
```

- Every player has their own value. The game receives `player_settings
  {game, player_id, values}` (all per-player keys, defaults merged in) after
  `declare_settings`, with every `prepare` and `party_updated`, and whenever the
  player changes one. In Godot: the `player_settings_changed` signal and
  `GameNight.player_setting(player_id, key, fallback)`.
- Change one from the game's own menu with `set_player_setting {player_id, key,
  value}` (Godot `GameNight.set_player_setting`, Rust `set_player_setting`).
  Phones send the same message for their own player.
- A player with a profile keeps their values between nights: the host saves them
  in its [player store](https://github.com/ontola/gamepad-party/blob/main/docs/player-store.md). A guest's values last for the night;
  when the guest signs in, they move to their profile.
- Party writes (`set_setting`, `control_settings`) cannot change a per-player
  key, and `GameSettings.values` only holds party values. `GameSettings.players`
  shows each present player's own values, for the apps.

## Saved progress

Settings are knobs. Progress (unlocked characters, a spell book, best times)
is data only the game understands. Save it per player and per game:

```gdscript
GameNight.player_data_changed.connect(func(player_id, data):
    grimoire[player_id] = data.get("spells", []))
GameNight.save_player_data(player_id, {"spells": grimoire[player_id]})
```

- `save_player_data {player_id, data, expected_revision}` stores any JSON up to
  64 KB, replacing what was there. The host answers with `player_data
  {game, player_id, data, revision}`, and sends the same with every `prepare`,
  `party_updated` and `players_updated` for players that have any. No message
  means nothing is saved yet. Godot: `player_data(player_id)`,
  `save_player_data(player_id, data)` and the `player_data_changed` signal; Rust
  `save_player_data` and `GameEvent::PlayerData`.
- `expected_revision` is the revision of the last `player_data` you got (0 for
  none). A save against an older copy is refused, so two hosts never silently
  overwrite each other: merge in the newer data and save again. The Godot addon
  fills it in for you.
- Unlocks belong to a person. While playing, everyone in the room may use what
  anyone has unlocked (`GameNight.party_union("unlocks")`), but never save that
  union into a player's own data. What the group earns together counts for
  everyone present: `GameNight.unlock_for_present(item)` adds it to each of
  their `unlocks` lists.
- Like settings: a guest's progress lasts the night and moves to their profile
  when they sign in (unless that profile already has progress in this game).
  Worlds and other large saves do not belong here.

## Phone and lobby assistant

The standard desktop cloud bridge and the custom lobby relay publish these same
declarations for the active game, or the prepared game if none is running. Numeric
values, toggles and named choices all use the same contract. No engine-specific
model integration is needed: declare your settings and handle `setting_changed`.

The assistant sends a typed batch through `control_settings`. The daemon checks
the player, game session and settings revision, then validates every value before
changing any of them. Undo restores the preceding batch; Keep clears that undo.
A stale request is refused instead of overwriting a newer change. Normal
`set_setting` writes also advance the revision.

Host acceptance does not mean a next-round setting is already active in gameplay.
Keep the timing in the label and description. The assistant must not promise an
immediate gameplay change when your game waits for a new round or match. Account
configs store these scalar values, not world saves or arbitrary mod code.

Voice and account features belong to the optional Splitscreen Club service. The public
game contract remains usable offline, without an AI provider.

# The Splitscreen Club Protocol (v1)

The protocol is the product. Engine plugins are convenience wrappers around
what is written here. Anything that can open a WebSocket and speak JSON can be
a Splitscreen Club game or overlay — Godot, Unity, Bevy, a shell script, a browser.

This document is the formal wire reference. **If you're integrating a game,
start with [Integrating your game](https://splitscreen.club/docs/lifecycle)** — it walks the
lifecycle in build order and links the checks and runnable examples. The
canonical type definitions live in
[`crates/gamenight-protocol`](https://github.com/ontola/gamepad-party/blob/main/crates/gamenight-protocol/src/lib.rs).

The same types, as one machine-readable JSON Schema with every message tag,
field, enum value and protocol constant, are in
[`contract/protocol.schema.json`](https://github.com/ontola/gamepad-party/blob/main/contract/protocol.schema.json). The SDK
bindings are generated from it by `scripts/build-protocol.py`: `GN_MSG_*` in
`sdk/c/gamenight.h`, `protocol.gd` in the Godot addon,
[`sdk/js/protocol.mjs`](https://github.com/ontola/gamepad-party/blob/main/sdk/js/protocol.mjs),
[`sdk/python/gamenight_protocol.py`](https://github.com/ontola/gamepad-party/blob/main/sdk/python/gamenight_protocol.py),
`mobile/lib/protocol.g.dart` and `Protocol.cs` in the Unity package. Use one of them, or the schema, rather than
retyping tag strings.

## Transport

The daemon listens on one port (default `127.0.0.1:7912`) and accepts two
framings of the same protocol. It tells them apart from the first four bytes
a client sends — `GET ` means WebSocket, anything else means plain — so
there is nothing to configure on either side.

| | **WebSocket** | **Plain** |
|---|---|---|
| address | `ws://127.0.0.1:7912` | `tcp://127.0.0.1:7912` |
| framing | one JSON object per text frame | one JSON object per line, `\n`-terminated |
| handshake | HTTP upgrade (`Sec-WebSocket-Key`, SHA-1, base64) | none — send your `hello` |
| use it when | your engine or runtime already has a WebSocket client: browsers, Godot, Rust, Node | your engine doesn't, and you'd rather not vendor one: most C/C++ engines |

Both are first-class and can share one party — a WebSocket overlay and a
plain-socket game see exactly the same messages. The plain form exists
because "anything that can open a socket can be a Splitscreen Club game" has to be
literally true: WebSocket's handshake and masked frame codec are several
hundred lines of ceremony before the first byte of protocol, which is free
in Godot and expensive in a C++ engine with no such dependency. Blank lines
on the plain transport are ignored, so a `\n\n` keepalive is safe.

Common to both:

- Every message carries a `"type"` field (snake_case).
- Receivers **must ignore unknown fields** and should ignore unknown message
  types. That is how the protocol grows without breaking old SDKs.
- `protocol_version` (currently `1`) only bumps on breaking changes. Adding a
  transport is not a breaking change: a v1 WebSocket client keeps working
  untouched.

## Roles

A connection announces itself with its first message, a `hello`:

| role | who | sends | receives |
|---|---|---|---|
| `game` | a game process (via an SDK) | `ready` (mandatory), `finished` + `declare_settings` + `set_setting` (its own) + `declare_companion` + `companion_message` (optional) | session lifecycle commands, `controller_frame`, `setting_changed`, `companion_message`, `companion_presence` |
| `overlay` | party UI / controller surface / LLM (via `gamenight-mcp`) | party commands | `party_state` snapshots |
| `lobby` | selected replacement lobby executable | party commands, `lobby_ready`, `quit_party`, `apply_update`, `switch_lobby` | full snapshots, `lobby_focus`, runtime controller frames |

The replacement lobby role requires the configured lobby ID and launch token,
including on reconnect. Declare `GAMENIGHT_LOBBY_API=1` in its launch environment
so the runtime owns input and retains the party if that process fails before
hello. Send `lobby_ready` after initial rendering; `quit_party` explicitly ends
the runtime. A disconnect alone preserves players and bindings. When the
packaged host has downloaded an update, snapshots carry `update_ready` (its
version); `apply_update` between games saves the party, restarts into that
version and restores players, seats, controllers, phone links and the queue.
Snapshots also list the host's `lobbies`; `switch_lobby {lobby}` between games
restarts into another one the same way. See
[Build a lobby](https://splitscreen.club/docs/lobbies) for the lifecycle, example and current limits.

```json
{ "type": "hello", "role": "game", "game": "my-game", "token": "<GAMENIGHT_TOKEN>" }
{ "type": "hello", "role": "overlay" }
```

The daemon answers with a `welcome`:

```json
{ "type": "welcome", "protocol_version": 1, "godot_sdk": 3, "party": { ... } }
```

`godot_sdk` is the version of the Godot addon this host ships. The addon
compares it with its own `SDK_VERSION` and warns when a game's vendored copy
is older; other engines can ignore it.

One connection per game id: a second `hello` for the same game is answered
with an `error` and the connection is closed. Identity is per *title*, not per
session — one process hosts many disposable sessions over the night.

After three automatic replacement-lobby restarts fail, the host pauses the
game and opens its local recovery page. A trusted overlay may then send
`retry_lobby` to reset the restart budget, or `quit_party` to end the session.
Games cannot issue these commands. A retry preserves players and the playlist;
`party_state` acknowledges the request, not successful rendering of the new
lobby. A later `lobby_ready` confirms readiness.

## Session lifecycle

Sessions are disposable. They move strictly forward:

```
created → preparing → ready → running ⇄ paused
   (any live phase) ──────────→ disposed
```

The daemon drives the lifecycle; games only ever *report* two facts.

### Daemon → game

| message | meaning | game must |
|---|---|---|
| `prepare` | warm up this session for these seats | load everything, then send `ready`. Show nothing. |
| `start` | the transition landed on you | start the match **instantly** |
| `pause` / `resume` | party paused the night | freeze / unfreeze |
| `dispose` | session over, id never reused | tear down; a new `prepare` may follow |
| `setting_changed` | the party turned one of your declared knobs | apply it live, or from the next match — whichever is sensible |
| `action_triggered` | a player pressed one of your [phone buttons](https://splitscreen.club/docs/protocol#phone-buttons) | do it, like starting a new round |
| `lobby_focus` | *(lobby games only)* some other game took the screen, or gave it back | mute and step out of the way on `active: false`; take over again on `true` |

`lobby_focus` only ever reaches the game registered as the party's lobby
(the one the daemon launches on a controller press with nothing else
running). It is not session-scoped — the lobby has no tracked session to
hang it off — so it carries just the flag:

```json
{ "type": "lobby_focus", "active": false }
```

```json
{
  "type": "prepare",
  "session": "9be2…",
  "game": "my-game",
  "seats": [
    { "index": 0, "occupant": { "kind": "local", "player_id": "41af…" } },
    { "index": 1, "occupant": { "kind": "ai" } },
    { "index": 2, "occupant": { "kind": "empty" } },
    { "index": 3, "occupant": { "kind": "empty" } }
  ],
  "players": [ { "id": "41af…", "name": "Ada" } ]
}
```

Games receive seats with occupant identities and optional opaque controller tokens.
Preserve player ownership across games; do not map seats to engine device order.
See [authoritative input](https://splitscreen.club/docs/protocol#bundled-games-authoritative-controller-input).
Occupant kinds are `local`, `remote` (reserved for network play), `ai`, `empty`.

`min_players` and `max_players` describe supported human participants. The
daemon skips games outside that range when preparing the next game, and
replaces an incompatible prepared session after someone joins or leaves.
The full library remains available for browsing. Before anyone joins, the
host may prewarm a game; the first join rechecks its eligibility.

A title that supports one human against its own AI advertises
`min_players: 1`. A higher minimum does not imply bot support: the daemon
does not invent AI occupants to fill it. Explicitly assigned `ai` seats are
preserved in `prepare` only within the game's maximum capacity, with humans
taking priority. AI occupants do not count toward the human minimum.

### Controllers and phones

Some games are played on phones, so the range above counts what each player
holds, not just who is seated. A game says so with `play_with`:

| `play_with` | counts |
|---|---|
| `controller` (default) | players holding a controller |
| `phone` | players with a linked phone; a controller is optional |
| `controller_and_phone` | players holding both |
| `controller_or_phone` | players holding either; pair with `min_phones` for asymmetric games (one god on a phone, the rest on controllers) |

A player's phone is linked once their phone joined the room and is bound to
them, whichever way (lobby door, QR, hosted room). The host's web server sends
the daemon that list with `set_phones`, and every snapshot carries it as
`phones`. A seat with a phone and no controller is a **phone-only player**:
someone who joined with only a phone because there were more phones than
controllers. A player with neither a controller nor a phone (a development
keyboard, an older client) counts as holding a controller.

So two controllers and four phones fit a four-player phone game, and a
phone-only player never fills a seat in a controller game: such games receive
that seat as `empty` in `prepare` and `party_updated`, and phone-only players
do not hold up a vote. Screens show why a game does not fit ("Needs 2 phones"),
mirroring `GameMeta::shortfall` in the Rust crate.

Nobody is too late. Before a game starts, a new player or a newly linked phone
re-prepares the warm game like any other join. While it runs, a player's phone
can link at any time and the game hears `companion_presence`, so it can hand
their seat back from a bot. A new phone-only player joins a running game with
`instant_join: true` at once, and other games on their next round.

Party snapshots include optional `next_game_index`, the exact upcoming
playlist occurrence even before its process connects. Use it for the Up Next
preview: two queued entries can have the same game ID. Older hosts omit it.

The seats are the whole player list. A game running under a daemon should
**not** also run its own "press X to join" — the party decides who is
playing, in the lobby, and a second route in makes the two disagree.

### Game → daemon

| message | meaning |
|---|---|
| `ready` | assets loaded, inputs mapped — this session can start instantly |
| `finished` *(optional)* | a round ended — keep session, focus and pause state unchanged |
| `progress` *(optional)* | how far along warming is, so screens can stay truthful while the party waits |
| `request_overlay` *(optional)* | "get me back to the party" — a player asked to leave your game |
| `request_start` *(optional)* | explicit player request to start or resume; never a focus callback |
| `declare_settings` *(optional)* | the match settings this game exposes (see [Match settings](https://splitscreen.club/docs/protocol#match-settings)) |
| `set_setting` *(optional)* | change one of this game's own settings, from its in-game menu (see [Match settings](https://splitscreen.club/docs/protocol#match-settings)) |
| `declare_companion` *(optional)* | a phone screen for this game (see [Phone screens](https://splitscreen.club/docs/protocol#phone-screens)) |
| `companion_message` *(optional)* | JSON for one player's phone screen, or every phone |
| `rumble` *(optional)* | vibrate the controller on one of your seats (see [Rumble](https://splitscreen.club/docs/protocol#rumble)) |
| `room_log` *(optional)* | one line for the room log players read back on their phones (see [Room log](https://splitscreen.club/docs/protocol#room-log)) |
| `declare_actions` *(optional)* | buttons on the players' phones, like "New round" (see [Phone buttons](https://splitscreen.club/docs/protocol#phone-buttons)) |

```json
{ "type": "ready",    "session": "9be2…" }
{ "type": "finished", "session": "9be2…" }
```

`progress` reports loading between `prepare` and `ready`. Send it as often as
is useful; the daemon keeps the latest and republishes it on the session in
every snapshot, so overlays can show a real bar instead of a spinner:

```json
{ "type": "progress", "session": "9be2…", "percent": 40, "label": "loading track" }
```

`percent` is a whole number, clamped to 0–100 by the daemon; `label` is
optional. A game that loads instantly should never send this — "loading"
with no number is a legitimate state, and screens must stay honest without
it. This matters most for games with genuinely slow warm-ups: a kart racer
loading a track for eight seconds is a fine Splitscreen Club citizen if it *says*
so, and a mystery if it doesn't.

`request_overlay` takes no arguments. Games are not allowed to drive the
party in general — this is the one exception, because a player stuck inside
a game with no route back to the party is the single failure the party can't
recover from on its own. Wire it to a Back/Select button, never to Guide/Home
(the OS reserves that one). The daemon pauses your session and gives the
lobby the screen.

```json
{ "type": "request_overlay" }
```

`request_start` requests starting or resuming this game after an explicit user
action. It takes no arguments:

```json
{ "type": "request_start" }
```

Never send it automatically when a window gains focus. Host focus changes can
otherwise bounce straight back into the game. Only Start/Resume commands authorize
gameplay. See the [integration guide](https://splitscreen.club/docs/lifecycle) for Back release
handling and borderless windows.

Ready completes preparation. Release acceptance additionally requires the
behaviors in [the contract](https://github.com/ontola/gamepad-party/blob/main/contract/requirements.json), including pause,
resume, input ownership, clean switching and continuous play.

Session snapshots include [diagnostics](https://splitscreen.club/docs/protocol#session-diagnostics). Consumers must
treat absent diagnostics from older hosts as unavailable, not zero measured
play time.

### Rumble

The host owns the pads, so a game asks it to vibrate one:

```json
{ "type": "rumble", "session": "9be2…", "seat": 0, "weak": 12000, "strong": 40000, "ms": 150 }
```

`seat` is a seat index from `prepare`. `weak` drives the light, buzzy motor
(road surface, texture) and `strong` the heavy one (impacts, grip loss), each
0 to 65535 as in XInput. `ms` is how long it lasts, at most 5000. Every
message replaces what that pad was playing, so send short pulses a few times a
second while an effect goes on, and zeros to stop at once. The host only
honours it from the running game in front, for a seat that has a pad; a warm
or paused game, or the lobby being open, is silently ignored. Pads without
motors ignore it too. In Godot, call `GameNight.rumble(seat, weak, strong,
seconds)` with 0 to 1 strengths.

`finished` is an optional round notification. It never advances the playlist,
opens the lobby, pauses the game or hides its window. The game owns its score
screen and starts the next round itself. Players can keep playing indefinitely.
Back/Select pauses and opens the lobby when it is let go; Resume continues.
The host owns Back chords, games need no code: while Back is held, RB skips
straight to the next game in the queue (RB then Back works too), LB goes back
to the previous game, B twice takes that controller's player out of the
party, and Y reports a bug: the host screenshots the game on screen, sends it
to the cloud room and opens the lobby, and the phones at the table are asked
what went wrong. After a chord, letting go of Back does nothing, so the lobby never shows
in between. A game's own `request_overlay` for that same Back press is folded
into it. In the lobby a Back tap closes it; holding Back for 160 ms shows
`back_menu` in the party state (the controller, its player and the chords that
work right now) for lobbies to draw. RB, LB, B and Y under a held Back never reach
games or lobbies. Play next explicitly
switches games, while Skip changes only the queued next game. A prepared next
session stays ready across rounds. Pausing also freezes the game's results timer.

## Party commands (overlay → daemon)

The authenticated replacement `lobby` role may also send these commands.
Game lifecycle reports and physical input publication are excluded from that
role; the runtime supplies its controller stream.

| message | effect |
|---|---|
| `join_party {name, seat?}` | new player; the requested seat if free, else the first empty one |
| `join_phone_player {name, color?, avatar?}` | new player who plays on a phone and holds no controller; takes a free seat, or adds one past the controller seats (eight at most) |
| `leave_party {player_id}` | player leaves; their seat empties |
| `rename_player {player_id, name}` | change a player's display name |
| `set_player_color {player_id, color}` | game-controlled clothing/team colour (`#rrggbb`); independent of skin |
| `set_player_skin_color {player_id, skin_color}` | saved personal skin preference (`#rrggbb`); exposed as `Player.skin_color` |
| `set_player_avatar {player_id, avatar}` | set their pixel-art face (opaque string — see [avatars](https://splitscreen.club/docs/faces)) |
| `set_player_profile {player_id, profile}` | tie a player to the profile behind them (`null` clears); sent by the host's web server, never shown to games as-is (see below) |
| `assign_seat {seat, occupant}` | re-seat a player / add a bot / empty a seat |
| `swap_seats {a, b}` | two people trade controllers: swap the occupants of two seats |
| `set_playlist {entries}` | set the night's queue; the next game starts warming |
| `play_next {game}` | make this game the next one up: it starts warming now (inserted into the playlist after the current entry if needed) |
| `queue_game {game, first}` | append a new occurrence, or insert first among upcoming games when `first` is true; preserves the current game and never starts playback |
| `queue_next {game}` | select an existing or new upcoming game without starting playback |
| `next` | skip to the warm session immediately, no vote |
| `previous` | start the game played before the current one (Back+LB does the same) |
| `pause` / `resume` | pause/resume the active session |
| `open_overlay` / `close_overlay` | the party overlay came up / went away (see below) |
| `vote {player_id, option}` | stand on `replay` \| `skip` \| `next_game` \| `quit` |
| `set_setting {game?, key, value}` | change a match setting; `game` defaults to the active game (see [Match settings](https://splitscreen.club/docs/protocol#match-settings)) |
| `media_control {action}` | `play_pause` \| `next_track` \| `previous_track` \| `resume` on the host's background music; `resume` also works with nothing showing and starts the player the host used last (see [The host's music](https://splitscreen.club/docs/protocol#the-hosts-music)) |

`download_grants {grants}` is for the trusted local web server only: it hands the
daemon the cloud's current download grants (game id to token) for paid games
someone seated owns. Each message replaces the previous set. A paid catalog game
downloads only while it has a grant, which is appended to its download URL as
`?grant=` (or `&grant=`); a newly granted game is fetched next. Other roles get an
`error`. Tokens are secrets and never appear in logs or `party_state`.

`set_phones {players}` comes from the host's web server, which pairs phones with
players: the players whose phone is linked now, replacing the previous list.
It appears in the snapshot as `phones` (see [Controllers and
phones](https://splitscreen.club/docs/protocol#controllers-and-phones)).

`playtests {playtests}` is also for the trusted local web server only. Each item
is a game's preview build that this table may play because someone seated owns
or tests the game: `entry` (a catalog entry whose downloads point at the
preview), `versions` (platform to version) and `grant` (sent with the download
even for free games). The daemon installs the build apart from catalog installs
and puts it on the shelf under its own title with a "Test build" tagline,
replacing a released version of that game for the rest of the night. The same build announced again does
nothing; a failed download is retried a minute later. Other roles get an `error`.

### The overlay is party state

Whether the overlay is up is **server-authoritative** (`overlay_open` in the
snapshot), so every screen shows the same thing. The rules:

- `open_overlay` pauses the active session (if it was running) — opening the
  party never costs anyone gameplay.
- `close_overlay` resumes **only if the overlay caused the pause**. An
  explicit `pause` stays paused.
- A transition (skip, vote consensus, auto-start) closes the overlay: the new
  game starts running and everyone is dropped straight into it.
- A `finished` racing an in-flight overlay pause preserves that pause.

```json
{ "type": "set_playlist", "entries": [
  { "game": "neon-trails", "title": "Neon Trails" },
  { "game": "neon-siege", "title": "Neon Siege" }
] }
```

### Switching windows is a pause

On Windows the host watches which window is in front. When the party switches
away from the running game (Alt+Tab, the Windows key, a click elsewhere) for
half a second, the host opens the overlay exactly as Back would: the game gets
`pause`, the lobby gets `lobby_focus` and the controllers. Switching back to
the game's window resumes it, but only a pause the host made this way; a game
paused on purpose stays paused. A game the host launched itself (the next one
warming up) taking the foreground does not count as switching away, and a game
whose window the host has never seen in front is never paused for it.

Games need no code for this: the host owns the decision, so `request_start`
on focus remains forbidden. On macOS games still report Cmd+Tab with
`request_start` themselves.

## Party state (daemon → overlays)

Every state change is broadcast as one snapshot — overlays are dumb renderers:

```json
{ "type": "party_state", "party": {
  "players": [ { "id": "41af…", "name": "Ada" } ],
  "seats": [ ... ],
  "playlist": { "entries": [ ... ], "current": 0 },
  "active_session": { "id": "9be2…", "game": "neon-trails", "phase": "running" },
  "warm_session":   { "id": "77c1…", "game": "neon-siege", "phase": "ready" },
  "history": [ "neon-trails" ],
  "vote": { "positions": [ [ "41af…", "next_game" ] ], "decided": null },
  "overlay_open": false,
  "library": [
    { "id": "neon-trails", "title": "Neon Trails", "players": "2–4" }
  ],
  "connected_games": [ "neon-siege", "neon-trails" ],
  "settings": [],
  "now_playing": { "title": "Hivernale", "artist": "Reynaldo Hahn",
                   "playing": true, "source": "Spotify" }
} }
```

The optional `onboarding_error` string is a host-owned failure of an explicitly
requested first game. Lobbies should show it visibly without inventing a library
or queue entry. It disappears when the request succeeds or another game is
chosen. Games cannot submit this field. See [catalog onboarding](https://github.com/ontola/gamepad-party/blob/main/docs/catalog-onboarding.md)
for saved-choice recovery and local game registration.

## Room log

The host keeps a log of the evening for phones to read back: who joined and
when, new names, controllers picked up or put down, phones linked, games
started, rounds ended (`finished`) and match settings changed. It is never
shown on the TV. Overlays find it as `activity` in the party snapshot, oldest
first and at most 200 lines; games and lobbies never receive it.

```json
"activity": [
  { "id": 0, "at": 1792785600, "kind": "joined", "text": "Ada joined" },
  { "id": 1, "at": 1792785660, "kind": "game_started", "text": "Started Neon Trails",
    "game": "neon-trails" }
]
```

`at` is in Unix seconds. `kind` is one of `joined`, `left`, `profile`,
`controller`, `phone`, `game_started`, `round`, `setting` or `game`; show
unknown kinds as plain lines. The host writes `text` so every phone reads the
same words. The local web server serves the log at `GET /api/activity?profile=…`
to a player in the room, and the cloud relays the newest 100 lines of an online
room at `GET /v1/rooms/activity`.

A setting changed from a phone names who did it ("Joep set Items to off
(Ballkickers)"), and so does a phone button ("Joep: New round (Ballkickers)").
The party snapshot's `settings[].changed_by` holds the player behind the last
change; it is absent when the game itself or the TV menu changed it.

A room nobody touches for three hours (no controller press, no change from a
phone or the overlay) closes by itself: any game stops, everyone leaves and the
log starts empty for the next evening. Games finishing rounds on their own do
not keep it open.

A game may add a line of its own about its running session, such as a new run
or a winner. Keep it to moments worth remembering: the host keeps one line per
two seconds per game and cuts text after 120 characters.

```json
{ "type": "room_log", "session": "9be2…", "text": "New run" }
```

In Godot, call `GameNight.add_room_log("New run")`.

## Phone buttons

Next to its settings, a game can offer buttons in the Splitscreen Club app for things
that happen once: "New round", "New run", "Skip level". Declare them any time
after `hello`, and again after a reconnect; an empty list removes them.

```json
{ "type": "declare_actions", "actions": [
  { "key": "new_run", "label": "New run",
    "description": "Ends this run for everyone.", "confirm": true }
] }
```

At most 12 buttons, keys of letters, digits, `_` and `-`, labels up to 40
characters. With `confirm` the phone asks first. Phones see the buttons only
while the game's session is the one being played, as `actions` in the party
snapshot. A press reaches the game as

```json
{ "type": "action_triggered", "key": "new_run", "player_id": "7f3c…" }
```

and the host writes "Ada: New run (Spellstorm)" in the room log, so the game
does not log it again. The local web server offers the buttons of the game
being played at `GET /api/actions?profile=…` (`{game, title, actions}` or
`null`) and presses one with `POST /api/actions {profile, game, key}`, as the
phone's own player. In Godot, call `GameNight.declare_actions([...])` and
connect `action_triggered(key, player_id)`.

## The host's music

Somebody puts a record on before the first match, and for the rest of the
evening they're the only one who can reach it — it's their laptop, in another
room, behind a lock screen. So the daemon watches whatever the host already
has playing and puts it in the snapshot as `now_playing`, and any screen can
send `media_control` to pause or skip it.

`now_playing` is **absent whenever nothing is on**, which is most nights.
That's the whole rendering rule: a screen draws its music controls only when
the field is there, because controls for a stereo that isn't playing are
worse than none. The [Game Room lobby](https://github.com/ontola/gamepad-party/blob/main/lobbies/game-room) shows the track on
its jukebox, where players pause or skip it, and has no music controls while the
field is absent.

A `play_pause` flips `playing` in the very next snapshot rather than waiting
for the poll to confirm: a pad that appears to do nothing for a second is a
pad people stand on twice, and two play/pauses are no play/pause at all. A
skip leaves the title alone until the OS says otherwise — guessing the next
track's name would only be wrong.

How the daemon reads it, per platform:

| platform | source | reached via |
|---|---|---|
| macOS | Spotify, Music | AppleScript, and only for apps already running (`pgrep`) — Splitscreen Club never launches a player to ask it what it's doing |
| Linux | any MPRIS player | `playerctl`, if installed |
| other | — | no music card, ever |

`source` is the app's own name, and it's the handle the daemon controls
through — so it's validated against the players it knows rather than trusted.
What this deliberately can't see is audio from a browser tab or a game;
reaching that on macOS needs a private framework Apple gates behind an
entitlement. Set `GAMENIGHT_NO_MUSIC=1` to switch the whole thing off — on
macOS, talking to another app is something the OS asks the host to approve,
and a host who'd rather not be asked should be able to say so.

## Match settings

Games expose the knobs a party may turn — items on/off, stock count, arena —
and **the daemon owns the values**: it validates every write, broadcasts them
in every snapshot, pushes changes to the game, and keeps them when the game's
process reconnects. Anything speaking the overlay role can turn a knob: the
party overlay, or an LLM through [`gamenight-mcp`](https://github.com/ontola/gamepad-party/blob/main/docs/llm-control.md) ("hey
Splitscreen Club, disable items").

A game declares its settings once, right after `welcome` (and again after
every reconnect — the daemon replays changed values in response):

```json
{ "type": "declare_settings", "settings": [
  { "key": "items", "label": "Items", "kind": "toggle", "default": true,
    "description": "Whether power-up items spawn during a match." },
  { "key": "stock", "label": "Stock", "kind": "number",
    "default": 3, "min": 1, "max": 99 },
  { "key": "arena", "label": "Arena", "kind": "choice",
    "default": "meadow", "options": ["meadow", "volcano", "space"] }
] }
```

Three kinds, all values plain JSON scalars: `toggle` (bool), `number`
(integer in `min..=max`), `choice` (one of `options`). Write `description`
well — it's what overlays show and what an LLM reads to map "no more
power-ups please" onto `items`.

Anyone in the party changes a value with:

```json
{ "type": "set_setting", "key": "items", "value": false }
```

`game` is optional and defaults to the active game — "disable items"
mid-match needs no lookup. The daemon validates against the declared spec;
rejections are `error` messages that spell out what would have been legal
(`"'towerfall' has no setting 'itemz'; available: items, stock, arena"`) —
written to be shown to a human or fed back to an LLM correcting itself.

A game may send the same `set_setting` for its own settings, for example from
its Start menu, so the party's apps and LLMs show what the players picked in
the game. The daemon takes the game from the connection and ignores `game` in
the message, so a game can never change another game's settings. The write is
validated and echoed like any other.

Valid writes land in the next snapshot's `settings` and are pushed to the
game:

```json
{ "type": "setting_changed", "game": "towerfall", "key": "items", "value": false }
```

Apply it live if you can (item spawners are easy to stop mid-match), or from
the next match if you can't — either is fine, and the choice is yours per
setting. Settings are **game-scoped, not session-scoped**: they survive
sessions, skips and replays, and because the daemon keeps the values they
also survive your process crashing. The `declare_settings` after your
reconnect answers with a `setting_changed` for every value the party had
moved off its default.

### Atomic settings batches

Remote controls should use `control_settings` rather than sending independent
`set_setting` writes. Read `revision` and `can_undo` from the game's entry in
`party.settings`, and use the current active/warm session ID and seated player ID:

```json
{
  "type": "control_settings",
  "game": "my-game",
  "session": "<session UUID>",
  "expected_revision": 4,
  "player_id": "<player UUID>",
  "action": "set",
  "values": {"items": false, "arena": "volcano"}
}
```

A game that is not active or warm (queued, or played earlier) can be set up
too, when `party.settings` has an entry for it: send the nil session
`00000000-0000-0000-0000-000000000000`. The values wait in the night's state
and reach the game as `setting_changed` after it declares its settings on
load. A game that is active or warm only takes its own session.

Every key and value is validated before any state or SDK notification changes.
Wrong types, unknown keys, stale revisions and departed players receive `error`.
A successful request sends **only its requesting overlay**:

```json
{"type":"settings_accepted","game":"my-game","session":"<session UUID>","revision":5}
```

Then the updated party snapshot is broadcast. This receipt confirms daemon
acceptance, not a rendered gameplay effect. Games still receive the existing
`setting_changed` messages and apply them at their declared time.

Use `action: "undo"` with empty `values` to restore the preceding change, or
`action: "keep"` to discard undo. Both require the current revision and advance
it once. Redeclaring settings clears undo and advances the revision. Setting
values survive sessions within the daemon; these revisions do not make them
durable across a daemon restart.

### How a game launches

The daemon is the launcher: when the next playlist entry needs warming and no
process for that title is connected, the daemon spawns one using the library
entry's `launch` spec:

```json
{ "id": "towerfall", "title": "TowerFall",
  "launch": { "command": "/games/towerfall/TowerFall.x86_64",
              "args": ["--windowed"], "cwd": "/games/towerfall",
              "env": { "SDL_VIDEODRIVER": "wayland" } } }
```

The handshake context travels in **environment variables, not CLI arguments**
— unknown flags break existing games, extra env vars are invisible:

| variable | meaning |
|---|---|
| `GAMENIGHT=1` | this process was launched by a Splitscreen Club daemon |
| `GAMENIGHT_ADDR` | the daemon's WebSocket address |
| `GAMENIGHT_GAME_ID` | the title this process was launched to serve |
| `GAMENIGHT_TOKEN` | per-launch secret; echo it in the `hello` |
| `GAMENIGHT_OVERLAY_URL` | *(optional)* the party overlay's URL/file path, forwarded from the daemon's own environment — lets a game raise the real overlay (e.g. on a controller Back/Select-button press — not Guide/Home, which iOS/macOS and most consoles reserve at the OS level) instead of building its own party UI |

SDKs auto-detect these, so the same binary boots into game-night mode when
the daemon launches it (skip the menu, connect, wait for `prepare`) and runs
as a normal standalone game otherwise. No flag plumbing.

Token rules:

- While the daemon has a launched process pending for a title, a `hello` for
  that title **must** carry the matching token — anything else is rejected.
  First-come-first-served ends where launching begins.
- With no pending launch, token-less hellos are accepted (dev mode: start
  your game by hand, connect, iterate).

Process lifetime: one process per title, resident all night — launching is
the expensive thing that happens once; sessions cycle cheaply inside the
living process. The daemon reaps processes when they exit (a crash rolls the
night to the warm session), retries a launch that never says hello within
15 s, and kills every child when the party votes to quit. Games without a
`launch` spec are simply awaited (externally managed).

### The library (cover art and all that)

The daemon owns a **game shelf**: presentation metadata for every title it
knows, playable right now or not. Overlays render next-game options from it —
this is what makes "what's next" feel like Netflix instead of a file picker.

- `cover` is portrait art; `icon` is the square case-spine image; `screenshot`
  is gameplay imagery for the TV. Missing artwork uses a readable title fallback.
- In the lobby's `party_state` the desktop host sends `screenshot` as a PNG
  data URI: the store's (it downloads HTTPS store images itself), or, for a
  game without one, the host's last capture of it from an earlier night.
  `live_screenshot` is the game as the party left it: when the host pauses
  the game in front for the lobby (Back, Alt+Tab), it captures that window
  (Windows) and keeps it until the game prepares a new match. Show
  `live_screenshot` first. Games never receive either.
- `connected_games` says which titles have a live process — overlays show the
  rest as offline (queueable, but they won't warm until their process
  appears).
- The daemon loads the shelf from `$GAMENIGHT_LIBRARY` (a JSON array of these
  objects) and falls back to a built-in demo shelf.

Separately, on startup the daemon also folds [the catalogue](https://github.com/ontola/gamepad-party/blob/main/catalog)
into the shelf: free entries with a direct, hash-verified binary for the
running platform that are already installed (from a previous run) join
`library` immediately, with a real `launch` spec resolved from the
catalogue's `downloads.<platform>.entrypoint` — no hand-written
`$GAMENIGHT_LIBRARY` entry required. An explicit `$GAMENIGHT_LIBRARY` entry
for the same id always wins; the catalogue only fills gaps. Anything not yet
installed downloads in the background (`gamenight-installer`) instead of
blocking this start, so it's ready to join the shelf on the *next* one. Set
`GAMENIGHT_NO_PREWARM=1` to disable both.

That background queue is live-reorderable, not fixed at catalogue order.
`maybe_warm` only ever emits `Effect::Launch` for a library entry that
already has a `launch` spec — a catalogue-only game that isn't installed yet
never reaches that path, so the daemon watches `play_next` directly instead:
the moment a `play_next` names a game with no launch spec, it calls
[`PrewarmHandle::prioritize`](https://github.com/ontola/gamepad-party/blob/main/crates/gamenight-installer/src/lib.rs) to
bump that game to the front of whatever's left in the queue. An in-flight
download always finishes first (no HTTP range support to resume a cancelled
one); reprioritizing only reorders what hasn't started yet.

## Phone screens

A game can give every seated player a screen of their own on their phone: a
hand of cards nobody else may see, a god's-eye map, a private vote. This is
how Splitscreen Club does asymmetric play. The phone screen is a small web page that
ships with the game; the host's local web server (`GAMENIGHT_WEB=1`, port
7913) serves it while that game is the active session, and the Splitscreen Club app
and the phone studio open it automatically.

Declare it once after `welcome`, and again after every reconnect:

```json
{ "type": "declare_companion", "root": "/abs/path/to/game/phone", "entry": "index.html" }
```

`root` must be an absolute directory and `entry` a path inside it. LAN phones load
`/play/<game>/<entry>?profile=…&game=<game>`, so relative links in the page
resolve inside `root`, and nothing outside it is served.

With hosted Splitscreen Club rooms, the host forwards the current game's phone bundle
and messages through an outbound encrypted connection. Phones do not need access
to the PC's LAN address. The signed-in app obtains its screen from
`GET /v1/rooms/companion`; the returned URL is a short-lived capability for that
account's seat and current game session, not an account login token. Treat this
URL as private. Changing the seat binding or game session revokes access.

Hosted bundles contain at most 128 files and 2 MiB of base64-encoded content;
each encoded file must fit within 512 KiB. Supported files are HTML, JavaScript,
CSS, JSON, SVG, PNG, JPEG, WebP and WOFF2. Use relative asset paths; symlinks and
parent-directory paths are rejected. The host replaces `/assets/companion.js`
with the hosted transport, so the same `GameNight.connect` API works in both
flows. Hosted screens run in a browser sandbox: do not depend on cookies,
local storage, external scripts, forms or navigating the parent application.
Bundles and private game messages are held in memory, not saved to the catalog.

Scanning and picking up a profile establishes identity. The phone must also
open the game's companion screen before the game receives `companion_presence`.
Games requiring private phone controls should wait for every human phone to
connect and confirm readiness before dealing cards or starting a round.

The page loads `/assets/companion.js` and exchanges plain JSON with the game:

```js
const game = GameNight.connect((data) => render(data), (status) => showStatus(status));
game.send({ action: "roll" });
```

The game receives what a phone sends tagged with the sender, and is told when
a phone opens or closes its screen. Send that player their current view on
`connected: true`; phones reconnect after a refresh or a host restart.

```json
{ "type": "companion_presence", "player_id": "7d0c…", "connected": true }
{ "type": "companion_message",  "player_id": "7d0c…", "data": { "action": "roll" } }
```

To answer, address one player, or leave `player_id` out to reach every phone:

```json
{ "type": "companion_message", "player_id": "7d0c…", "data": { "hand": ["wood", "wool"] } }
{ "type": "companion_message", "data": { "turn": "7d0c…" } }
```

Phones never name their own player: the web server knows which party member
each signed-in phone is and fills it in, so a player cannot read or play
another player's hand. Keep messages small (under 16 KB) and treat every one
as untrusted input. Overlays see declared screens in `party_state.companions`
and relay traffic with `companion_message` (`game` and `player_id` set) and
`companion_presence`; the lobby sees screens without their `root`.

### Native phone apps

Some phone sides are a whole game of their own, such as a 3D god view, and
don't fit in a web page. Declare a native app instead of (or next to) a page:

```json
{ "type": "declare_companion", "root": "/abs/path/to/game/phone",
  "app": { "name": "The Voice and the Will", "android": "io.ontola.godgame",
           "download": "voice-and-will.apk" } }
```

`download` is an `https://` URL or a file inside `root`; a file is served by
the Splitscreen Club PC over the LAN, so the PC is the phone's installer. The
Splitscreen Club app acts as the store: **Install** downloads the APK and hands
it to Android's installer (Android asks once to allow installs from
Splitscreen Club and confirms each first install; updates of apps Splitscreen Club
installed need no confirmation on Android 12+), and **Open** launches
`android`. In Godot: `GameNight.declare_companion(root, "", app)`. The app connects to the
game by its own means, for example LAN discovery; `companion_message` is for
pages only. iPhones can't install apps from outside the App Store, so there
the app must come from the App Store or TestFlight.

## Plain-text requests

A game can accept requests in plain words, such as "geef me 10 End Crystal",
from the Splitscreen Club app and the session assistant (which turns speech or loose
wording into a request the game understands). Declare it after `welcome`:

```json
{"type": "declare_commands", "description": "Ask for items for yourself or everyone.",
 "examples": ["geef me 10 End Crystal", "geef iedereen 5 Torch"]}
```

The daemon lists it in the party snapshot under `commands`. The local web server
then forwards a request from a seated player as

```json
{"type": "game_command", "game": "mineclonia", "player_id": "…", "id": "r-12", "text": "geef me 10 End Crystal"}
```

and the game answers once, in words for that player:

```json
{"type": "command_result", "id": "r-12", "ok": true, "message": "Alsjeblieft: 10× End Crystal."}
```

The game decides what text means; nothing is executed as code. Only the local
web server sends `game_command`, only for a player who is in the party, and
only to a game that declared commands. A declaration ends when the game disconnects.

### Live changes through the game's own tools

A game that serves [MCP](https://modelcontextprotocol.io) tools on this
computer while it runs (Warp's live control) can let the session assistant
change it during play: "make the enemies slower", "give the ship a red trail".
Add the path of its token file, a JSON file with `url` (a loopback
`http://…/mcp` address) and `token`, readable by the same user:

```json
{"type": "declare_commands", "description": "Change this game while you play: …",
 "mcp": "C:\\Users\\joep\\AppData\\Local\\Temp\\warp-live\\neon-siege.json"}
```

The local web server then sends no `game_command` for a request. It reads the
token file, lists the game's tools and carries out the request with them, one
model step at a time from the Splitscreen Club cloud, and the model's last words are
the answer. The token stays on the host. Such a change is temporary: the host
hides tools that save into the game's files (`write_file`, `load_mod`), asks
`set_knob` for `persist: false`, and offers `set_knob` only when the game
supports that. A restart brings back the saved game; keeping a change is the
game's own explicit tool, used only when the player asks to keep it. Warp games do this by themselves when
Splitscreen Club launches them.

## The night, end to end

```
overlay: set_playlist [neon-trails, neon-siege]
daemon → neon-trails: prepare      (warm the first game)
neon-trails → daemon: ready
daemon → neon-trails: start        (nothing was playing: auto-start)
daemon → neon-siege: prepare      (warm the next one behind it)
neon-siege → daemon: ready        (the party is now skip-proof)

neon-trails → daemon: finished     (round reported; game shows results and repeats)
players explicitly choose next_game
daemon → neon-trails: dispose
daemon → neon-siege: start         (instant transition)
daemon → neon-trails: prepare      (playlist wraps; warm again)
...repeat until someone wins the "quit" vote
```

## Rules the daemon enforces

- **Auto-start**: the first session to become `ready` while nothing is active
  starts immediately.
- **Warm behind the active game**: whenever the warm slot is empty and the
  next playlist entry's process is connected and free, a `prepare` goes out.
- **One process, one session**: if the next entry is the same game as the
  active one (single-entry playlists, replays), the active session is disposed
  first, then the fresh session warms.
- **Transitions wait for warmth**: `next` (or a vote) before the warm session
  is `ready` becomes pending and fires on its `ready`.
- **Voting is consensus of the seated**: everyone holding a seat must stand on
  the same option. Spectators don't vote. If the last holdout leaves, the vote
  resolves. Round completion never auto-advances, even with no seated players.
- **Crashes don't end the night**: if the active game's process dies, the
  daemon transitions to the warm session as soon as it can.
- `error` messages are informational; the connection stays open (except after
  a rejected `hello`).

## Errors

```json
{ "type": "error", "message": "no seat 9" }
```

## Future (kept off v1 on purpose)

Remote gameplay seats, voice and GPU/memory budgeting for multiple warm sessions
are not implemented. Downloads and host controller routing are implemented.

### Ready crossing Dispose

A host may replace a preparing session when seats change. A `ready` reply for
a recently disposed session can already be in flight. Splitscreen Club ignores these
late replies for the 64 most recent disposals; it never applies them to the
replacement session. Unknown session IDs still produce a protocol error.

## Player activity, sleep and joining during play

Presence is host-authoritative and separate from player identity. A controller-bound
player warns after 60 seconds without meaningful input and sleeps after 75 seconds.
Input wakes the same player immediately; their ID, name, controller binding and seat
remain intact. Sleeping players do not block votes and cannot activate lobby TV pads.
The lobby shows animated `zZz` while sleeping, without a warning on the player name.

After `prepare`, games opt in before replying `ready`:

```json
{"type":"participation","session":"<session UUID>","instant_join":true}
```

Use `instant_join:false` when a round has a fixed roster. Both values enable presence
notifications. Legacy games need no changes: their active matches do not advance AFK
clocks, and they receive no new lifecycle messages.

Report real human activity from **all** controllers, including unassigned devices:

```json
{"type":"controller_input","session":"<active session UUID>","controller":"ordinal:0"}
```

`ordinal:N` identifies a device in the resident host, as used by `seats[].controller`.
Treat it as an opaque token. Do not index an SDL or engine-local device list with it.
Bundled games consume the host controller frames described below. Apply a 0.25 stick/trigger
deadzone, ignore device-connect events, and throttle held input to once per second
per controller. Bots, animation, repeated network heartbeats and simulated input must
never report activity. A game may report only while its own session is running and
foreground; reports from stale sessions, warm games and other game IDs are ignored.
The persistent lobby can report through its overlay connection without `session`.

`controller_input` only keeps presence; it never seats anyone. A controller
nobody plays with joins the party when it presses **A**, in the lobby and in a
running game alike (any other button or stick does nothing: it only jiggles
that controller on the lobby table). The host's own input router does this, so
games need no code and must not run their own join. In a game, games with
`instant_join:true` receive the new player in their current match, subject to
the game's maximum player count; other games keep their prepared roster and
the new player joins on the next preparation. Repeated presses never create
duplicate players. The A press that joined is held back from the game until it
is released.

Nobody in front of a running game sees the lobby, so a game should say how to
join when a spare controller (a token in `controller_frame` that no seat of
this session holds) is touched: "Press A to join this game", or "Press A to
join; you play from the next game" for games without instant join. Warp games
do this in their HUD (`splitscreen_club::party::Party::watch_joins`) and name
the newcomer ("Nora joined the game") when their seat arrives.

Opted-in games receive a full snapshot on declaration and subsequent changes:

```json
{"type":"party_updated","session":"<session UUID>","seats":[],"players":[],"presence":[{"player_id":"<player UUID>","state":"warning"}]}
```

The actual message contains the full seat/player arrays. Presence states are `active`,
`warning`, and `sleeping`; absent presence means active/untracked. Overlays receive
these records in `party_state.party.presence`. Preserve match state and scores when
applying updates. Visually distinguish sleeping players without requiring warning text.
Games choose how sleeping characters behave (neutral input, safe removal, or AI).
Sleep is not a `leave_party`: never reassign the sleeping player's controller.

Rust games use `GameNight::participation`, `GameNight::controller_input`, and
`GameEvent::PartyUpdated`. The LOVE party pack implements these messages in its
shared lifecycle module; sleeping players use AI until they wake. Neon Siege is the
first instant-join implementation: a new pilot spawns centrally with three seconds
of protection, preserving the current wave and team score. Other pack games retain
fixed round rosters. Custom clients can send the JSON directly.

### Profile changes during a match

When someone goes back to the lobby mid-match and picks up a profile (or
changes name, colour, face or couch position), the active session gets the same people with new
details. Every game receives this, whether or not it sent `participation`:

```json
{"type":"players_updated","session":"<session UUID>","players":[{"id":"<player UUID>","name":"Joep","color":"#e94b3c","avatar":"…","profile_key":"…"}]}
```

`players` lists every player the session was prepared with. Apply it to the
running match: update names, colours and faces, and load that person's data
when `profile_key` changed. Never restart or reset the match over it. Seats do
not change; joins, leaves and seat swaps still arrive as `party_updated` (opted
in) or at the next `prepare`. Closing the lobby resumes the same session.

The character studio saves `skin_color` with the player profile and never changes
`Player.color` on sign-in. Games may assign clothing or team colours while retaining
the skin preference. Avatar paint is composited above skin and is not recoloured.

### Couch position

Every player has a place on the couch, `Player.couch`, counted from the left
(0 is the leftmost). Each player in the party has a different one. Players move
with left and right on **Couch position** in their own Start menu in the lobby;
the host sends `set_couch_position {player_id, position}` and shifts the people
in between one place over. Newcomers sit down on the right, and leaving closes
the gap.

Lay out anything that runs left to right by it: split-screen views, start
positions, scoreboards. Not by seat: a seat is a controller slot and does not
change when someone moves. Sort by `couch` rather than index with it, since a
session may have part of the party. A move during a match arrives as
`players_updated` (and in `party_updated`): move the views over, never restart.
Older hosts leave `couch` out; fall back to seat order. The Godot SDK has
`GameNight.couch_order(seats, players)`.

### Recognising a player between nights

`Player.id` lives as long as the party. To keep a player's own data (their
inventory in a world, settings, unlocks) between nights, key it on
`Player.profile_key` instead. Games receive it in `welcome`, `prepare`,
`party_updated`, `players_updated` and `party_state`; overlays and phones never do.

- It is a 32-character hex string, the same for that person every time, on any
  host where they use the same signed-in account (a remembered local profile
  only matches on its own host).
- It differs per game, so two games cannot match up their players, and it
  cannot be turned back into an account.
- Players without a profile (guests) have no `profile_key`: keep their data for
  the night only.

The daemon derives it as `gamenight_protocol::profile_key(game, profile)`. A
profile picked up on another character moves its key with it, and the warm game
is prepared again so it can load the right data.


### Bundled games: authoritative controller input

The runtime samples physical controllers for a lobby that uses the `lobby`
role and publishes `controller_frame` to the lobby and games. It consumes
Back/Select and the A press used to claim a seat. No client may inject
physical frames.
Each frame contains the full connected-device list, including released buttons.

```json
{"type":"controller_frame","controllers":[{"controller":"ordinal:0","axes":[16384,0,0,0,0,0],"buttons":1}]}
```

`controllers` contains `{controller, axes, buttons}` records. `controller` is an
opaque host token matching `seats[].controller`, not an index into SDL's joystick
list. The lobby keeps device IDs stable when another controller disconnects.
`axes` contains left X/Y, right X/Y, and left/right trigger, scaled by 32767.
Y is down-positive. Button bits 0 through 13 are A, B, X, Y, LB, RB, Back, Start,
left stick, right stick, D-pad up, down, left, right.

The shared LÖVE adapter uses these frames in managed sessions and never matches
local SDL enumeration against lobby ordinals. Standalone games still read local
controllers. The runtime-owned stream samples approximately every 16 ms. After 250 ms
without input, controls become neutral. TCP_NODELAY is enabled.
The Rust SDK exposes each frame as `GameEvent::ControllerFrame`. Use the seat's
opaque controller token to find its input record; an empty frame or missing
record means neutral input. `controller_input` reports actual human activity
for presence and joining. It does not move a game character by itself.

Regression checks: `host_controller_identity_survives_reordering_and_disconnects`
in the shared Lua suite, the daemon socket test
`games_cannot_inject_controller_frames`, and
`scripts/test-love-integration.py` with sparse, reversed host device IDs.

## Circular player faces

Use the [face API](https://splitscreen.club/docs/faces) for drawn faces and hats. LÖVE games call
`Face.drawFace(player, x, y, radius)` from `shared.face`; Rust games use
`Avatar::head_layout()`. Coordinates describe the head centre, not the image
bounds. Skin colour is separate. Keep transparent space for hats, and mirror
around the head centre. Refresh artwork when the player profile changes.

`profile.face` tests artwork rendering and live updates independently of
`profile.colors`. Carrying an avatar string without drawing it does not pass.
Faces may appear on characters or in a player portrait for games with vehicles.

## Session diagnostics

`SessionInfo.diagnostics` contains cumulative `active_ms`, `paused_ms` and
`rounds_reported`. The host counts time only for the active session, excluding
preloading. A long host suspension contributes at most two seconds per tick.
Round counts reflect optional `finished` notifications, not verified completion.

A game may also send cumulative application-frame measurements:

```json
{"type":"performance","session":"SESSION_UUID","sample":{"frames":600,"elapsed_us":10000000,"slow_frames":2,"max_frame_us":41000,"gpu":"GPU model","os":"Windows","width":1920,"height":1080}}
```

Reset counters on `prepare`. Count only running frames. Skip the first frame
after start/resume and suspension gaps over two seconds. `slow_frames` counts
intervals over 33,333 microseconds. Report roughly every ten active seconds.
The host accepts reports only from the game registered for the running session,
rejects invalid or decreasing counters, and exposes the latest sample as
`SessionInfo.diagnostics.performance`. An absent sample means unknown, never zero FPS.
Average application FPS is `frames * 1_000_000 / elapsed_us`; this is not a count
of display presents or a frame-time percentile.

Optional hardware fields are `cpu`, `gpu`, `os`, `memory_mib`, `width` and
`height`. Strings must be at most 256 UTF-8 bytes without control characters.
Use an empty string or zero for unavailable hardware. Never include serial
numbers, machine names, paths, network addresses or raw input.

The bundled LÖVE launcher reports frames, GPU, OS and pixel dimensions. The
Godot autoload also reports CPU and physical RAM. These are shipped source
adapters: already published game binaries need rebuilding to use them. Rust
games can call `GameNight::performance(session, sample)` with their own frame
measurements. C and other engines must send the JSON message themselves; there
is no automatic sampler for them yet.

These are factual diagnostics available to any host. The public runtime keeps
only the current session counters. It contains no behavioral database, account
profiling, recommendation model or training pipeline. An optional configured
cloud room relay includes session diagnostics in its discovery snapshot.

## Preferred player colours

Player profiles may carry an optional `preferred_color` (`#RRGGBB`). It is
separate from `skin_color`. The host applies this through `set_player_color`
and publishes the assigned colour in `Player.color`, which games should use for
clothing and player indicators. A preference is not a guarantee: when colours
conflict, the first player to join the party wins, regardless of seat order or
which phone's profile update arrives first. Other players receive distinct
fallback colours. When a colour becomes available, a player waiting for that
preference receives it. Games can still use team colours when required by their
rules. Older profiles without this field retain automatic colour selection.
